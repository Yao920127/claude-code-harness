# Agent Note: 路由模型上下文與壓縮策略

Status: implemented

[English](2026-07-20-routed-model-context-and-compaction-policy.md) | 中文

## 問題

當一個程序把請求路由到不同容量的模型時，壓縮（compaction）不能安全地應用同一個全域上下文視窗。相同模型 id 也可能存在於多個提供者下，介面卡還可能接受不在建議目錄中的動態 id。錯誤容量要麼讓壓縮觸發過晚並造成原本可避免的溢位，要麼讓壓縮觸發過早並丟棄有用上下文。

兩個直觀的設定歸屬方都無法獨立解決問題。Compact-basic 是可選外掛，不知道介面卡接受哪些模型。LLM（大語言模型）介面卡擁有模型路由，但不能依賴可選壓縮外掛，也不應吸收消費方專用的閾值、保留、摘要器與重試策略。該設計既需要權威容量事實和可選的逐目標壓縮策略，又不能建立第二套模型註冊表。

## 決策

### 介面卡擁有精確路由容量

`LlmAdapter.resolveModel(provider, model, signal?)` 返回一條精確路由的聚合中繼資料，其中可選的 `LlmModelContext` 位於 `context` 欄位下。`LlmRuntime.resolveModelInfo()` 選擇已註冊的路由所屬方，驗證 `contextWindow` 為正整數，並返回與介面卡內部狀態分離的中繼資料。該查詢獨立於 `listModels()`：不在目錄中的動態模型也可以擁有容量中繼資料，而缺少 `context` 只表示介面卡無法描述容量。

手寫 DeepSeek 介面卡允許每個已設定模型提供可選 `contextWindow`，並支援介面卡級 `defaultContextWindow`。精確模型容量優先；未提供容量的模型項與未列出的直接傳遞 id 會繼承介面卡預設值，若預設值也不存在則省略 `context`。內建模型項各自宣告 1,000,000 token 的上下文容量。pi-ai 介面卡從同一個目錄描述符解析容量，該描述符也用於權威解析請求模型。

### Token 計量保持模型無關

`dsh-token-meter` 沒有設定，也沒有模型 profile。它擁有一個固定回放摺疊，並返回絕對估算 token 壓力，以及按位置排列的表層節點 token 估值。移除全域容量後，未載入 compaction-basic 時仍可複用計量，同時避免讓回放核算變成另一套模型註冊表。

### Compact-basic 解析目標規格

Compact-basic 擁有消費方策略。頂層欄位定義預設值；`modelPolicies` 包含以精確 `{ provider, model }` 組合為鍵的部分覆蓋。重複目標、未知欄位或無效欄位都會讓外掛載入失敗。`thresholdRatio` 預設為 `0.8`，保留策略預設為 `retainRatio: 0.16`；呼叫方也可以改用絕對 `retainTokens`，但兩種保留形式互斥。完成繼承後，如果保留比例不小於閾值比例，外掛也會載入失敗，因為任何模型容量都無法讓該策略有效。

對於主動壓力檢查，compaction-basic 讀取最新持久路由，解析介面卡容量 `W`、請求輸出預留 `O` 和精確目標策略。觸發閾值為 `floor(min(W × thresholdRatio, W − O − headroomTokens))`，預設餘量為 65,536 tokens。視窗比例限制歷史增長，第二項則在一次完整輸出後為壓縮輸入與生成留出額外空間；它無法限制任意工具結果的增長。保留預算獨立按 `W − O` 縮放。`O` 取自生效信封的 `maxTokens`，否則取介面卡按請求的預設值，再退回到零。每次檢查都會重新解析，因此路由或輸出上限變化會立即影響策略。若壓力預算非正，或保留預算不低於觸發閾值，會在目標容量允許比較時失敗。

同一精確目標覆蓋還可以選擇摘要提供者/模型、摘要輸出上限、收斂重試次數與溢位重試上限。這些都屬於壓縮問題，不會進入任何 LLM 提供者。

### 目標專用壓力錯誤仍保留可選組合

缺少容量中繼資料的介面卡仍是有效 LLM 路由。手動主動壓力檢查會返回目標專用設定錯誤；自動監聽器按精確路由只警告一次，並繼續保留完整歷史。當輸出預留與餘量耗盡容量，或保留預算達到觸發閾值時，也會抑制重複警告；其他執行故障仍會各自對外可見。提供者已經確認的規範化溢位不需要容量中繼資料：它繞過主動閾值與普通保留預算，嘗試一次最大且平衡的縮減，並在替換無法證明進展時保留原始提供者錯誤。

## 測試

服務測試覆蓋與介面卡內部狀態分離的上下文中繼資料、無效介面卡輸出、目錄獨立性與預設缺失行為。介面卡測試覆蓋 DeepSeek 的精確容量、預設容量、未列出模型解析及無效容量，以及 pi-ai 的精確描述符解析。壓縮測試覆蓋兩項閾值上限、預設和覆蓋餘量、信封輸出上限與介面卡退回、獨立保留預算縮放、無效預算、精確目標覆蓋、提供者切換、警告抑制和不依賴容量的溢位恢復。無需金鑰的 `compaction-output-reserve` headless 情境記錄非零請求上限、下一步之前的主動壓縮和替換後的歷史。Loader fixture（測試前置資料）會拒絕已經移除的 token-meter 容量設定，範例則在介面卡上設定容量。

## 考慮過的替代方案

- **把容量與所有策略都放進 compaction-basic**——不予採納，因為 compaction-basic 會複製介面卡的模型知識，未列出的動態模型需要並行註冊，而且未安裝壓縮時容量也會消失。
- **把壓縮策略放進各個 LLM 介面卡**——不予採納，因為介面卡必須獨立於可選消費方，而摘要與重試策略也不是提供者事實。
- **讓 `listModels()` 成為權威來源**——不予採納，因為發現能力只是建議資訊，一些介面卡有意接受動態 id。正確性中繼資料不能把選擇器成員關係變成路由白名單。
- **給 token-meter 增加逐模型摺疊**——不予採納，因為回放演算法可以共享，變化的只有容量與消費方策略。多個摺疊會重複狀態，卻不會改善估算。
- **建立獨立模型上下文註冊表**——不予採納，因為介面卡已經擁有權威路由解析。第二套註冊表會引入生命週期順序、重複鍵與漂移問題，卻沒有獨立後端。

## 後果

- 容量在提供者約定上擁有唯一權威歸屬方，而壓縮策略留在可選消費外掛中。
- 同一個 compaction-basic 實例無需查詢發現中繼資料，就能安全處理不同視窗、提供者切換，以及不同提供者下的相同模型 id。
- 僅 LLM 與僅 meter 的組合仍然有效；載入 compaction-basic 不會讓介面卡產生反向依賴。
- DeepSeek 部署可以設定精確的逐模型容量，也可以讓未提供容量的模型項與未列出的直接傳遞 id 使用 `defaultContextWindow`。
- 比例預設值會隨模型自然縮放，並扣除每次請求預留的輸出 token；同時仍可按精確目標使用絕對保留值，以滿足部署專用行為。

本記錄取代[回放式 token 計量服務 Agent Note](../../archived/architecture/2026-07-15-replay-token-meter-service.md) 中的全域容量與無模型策略部分，單摺疊計量決策保持不變。
