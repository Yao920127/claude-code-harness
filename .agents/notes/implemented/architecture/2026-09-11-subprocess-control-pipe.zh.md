# Agent Note: Subprocess control pipe

Status: implemented

[English](2026-09-11-subprocess-control-pipe.md) | 中文

## 問題

受管 Node 程式可以向 stdout 和 stderr 寫入任意位元組。若主機協定共用其中任一流，就無法在不限制普通 Node 行為的前提下區分協定位元組和程式診斷。Windows 程序包裝器還要求在子執行時分配自身描述符前顯式設定描述符繼承。

## 決策

普通 subprocess 請求可以設定 `stdio.control: 'pipe'`，並透過 `handle.control` 收到原始 `Duplex`。目標透過 `@deepseek-ai/dsh-subprocess/control` 開啟 fd 7。提供者擁有環境標記；子程序輔助函式會消費它。消費方負責有界分幀、訊息驗證、背壓和端點關閉。標準輸出收集與受管範圍生命週期保留現有語義。提供者獨立跟蹤開啟的控制端點，直到它們關閉，包括受管範圍退出之後；銷燬時先嘗試受管範圍拆卸，再關閉剩餘端點。

POSIX 啟動器在 exec 時保留 fd 7。Windows 普通 Job 與受限權杖啟動器把管道放入 CRT 啟動描述符表的槽 7，保留標準控制代碼，並讓負載中的槽 3–6 保持關閉。每層包裝器在轉移所有權後關閉自身承載端。控制代碼繼承僅在程序建立期間啟用。該通道不授予任何主機能力：子程序仍不可信，每次主機工具請求都需要通常的分發與審批檢查。

控制管道使用 Node 的 `overlapped` stdio 處置方式：它在 POSIX 上等同於 `pipe`，在 Windows 上建立帶有 `FILE_FLAG_OVERLAPPED` 的控制代碼。因此讀寫可以獨立進行，包括子程序在主機傳送任何內容前發出第一條訊息。

Windows 受管範圍證明獨立觀察 runner 程序退出及其私有 IPC 結果，不依賴呼叫方排空流。收到結果且 runner 正常退出即可確認範圍結束；正常退出但未收到結果時，最多等待到 IPC 通道關閉。暫停的控制輸出不會延遲該證明，也不會阻止提供者銷燬時關閉端點。

檔案系統與 subprocess 服務仍可由遠端提供者成對替換。公共控制代碼和請求均不公開主機路徑、程序標識、執行世界標誌或傳輸協商目錄。終端分配保持非同步，且不增加額外描述符。

## 考慮過的替代方案

**Stdout 分幀。** 原生程式碼和普通 `process.stdout.write` 可以輸出任意位元組，因此協定完整性將依賴於攔截程式輸出。

**同步 Windows 管道。** 繼承的同步管道上的阻塞讀取可能阻止同一控制代碼上的並行寫入繼續執行。主機先傳送的回顯無法暴露該死鎖；子程序先報告就緒以及拆卸都需要重疊 I/O 控制代碼。

**Node IPC。** Windows 程序監督器已經使用私有 IPC 通道。把負載請求耦合到該管理協定會暴露監督器操作，並使遠端傳輸複雜化。

**在 Windows 啟動後替換描述符。** Node 啟動後替換 fd 7 可能覆蓋內部描述符。CRT 啟動表在執行時初始化前保留它，並保持各主機的子程序 API 一致。

**各平臺使用不同描述符。** 不同平臺的編號會增加引導分支，卻不能省去原生啟動工作。固定槽位也讓遠端提供者可以保留相同的子程序 API。

## 後果

原生包裝器必須顯式保留並關閉一條額外管道。subprocess 服務不解釋控制訊息，也不替呼叫方緩衝訊息，因此協定消費方必須自行限制保留的輸入和輸出。作業系統沙箱與受管程序擁有者仍負責限制和拆卸；獨立傳輸不是 JavaScript 安全邊界。
