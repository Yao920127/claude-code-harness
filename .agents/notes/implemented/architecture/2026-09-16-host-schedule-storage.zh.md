# Agent Note: Host 擁有的定時訊息

Status: implemented

[English](2026-09-16-host-schedule-storage.md) | 中文

## Problem

定時訊息必須能在重新啟動後被發現，無須載入每個 Session。掛在 live Agent 上的 timer 無法投遞目標 Session 仍為 cold 的任務。使用者還需要在不啟用對話的情況下檢視待投遞和已投遞任務；投遞後刪除任務會丟失這條管理記錄。

## Decision

現有 Schedule 包擁有一個 Host storage domain，儲存每個任務的原始 Session id、提醒記錄、`active` 或 `inactive` 狀態，最近一次投遞迴執，以及已儲存的投遞歷史。該 domain 是保留任務的權威來源。Host scheduler 僅為活動任務恢復 timer；到期任務使用 Session controller 現有的解析操作，在原 Session 中排入普通 follow-up。查詢和刪除任務不會解析 Agent。已儲存但缺少狀態的記錄規範化為 `active`，不掃描或重建歷史 Session。

任務 domain 宣告整 unit 佈局。任務是權威資料，因此 JSON 後端會把檔案不可讀、文件損壞、版本不受支援或任務非法作為整批載入失敗，而不是解釋為刪除。恢復失敗不會改寫 `schedule.json`，初始不存在的檔案則作為空 domain 開啟；修復該檔案後會保留任務身份。`Service.init` 等待儲存總和檢查碼執行時初始化，管理方法等待同一初始化結果；擁有方解除安裝時釋放遲到的儲存資源，而不開始投遞。投遞排程准入與初始化分開：任務變更提交後、執行時清理開始前，祖先可能關閉 Agent 准入。此類拒絕會記錄日誌而不自動重試，不會將已持久化的變更變成失敗的管理結果。儲存非法和清理註冊失敗仍拒絕啟動。

此決策替代[工作階段內提醒記錄](../feature/2026-08-05-durable-web-schedule.zh.md)中的 Session 日誌權威來源、僅 live 時啟用和只讀目錄決策。其中顯式絕對時間驗證、固定速率計算，以及區分排隊接納與模型完成的決策仍然適用。歷史 `schedule/change` 的建立、fold 和 invariant 型別透過 `LegacyScheduleRecord` 保持為 After、At 和 Every；獨立的主機解碼器接受包含 Daily、Weekly 與 Cron 的目前 `ScheduleRecord`。主機記錄解碼器要求已儲存的 `title` 去除首尾空白後非空、本身已去除首尾空白且不超過 120 個字元，嚴格的 task schema 會拒絕整個 domain 的開啟，而不是丟棄這樣的任務。歷史變更解碼器容忍缺失的 `title`，以便已寫入的 Session 日誌仍可讀取；該成員存在時，同樣按這三項檢查驗證。storage domain 保持版本 1。歷史事件不會填充該 domain，已有 `at` 任務也不會轉換為每日或每週規則。載入含有活動舊提醒的 Session 時，會警告需要重新建立提醒。

外掛來源的 `followup()` 同步將訊息追加到 Session 收件箱。Session flush 成功後確認持久投遞。一次任務記錄 put 儲存 `lastDelivery`，追加包含發生目標、確認時間、真實訊息 id 和指令快照的傳送記錄，並更新一次性任務的 `inactive` 狀態或重複任務的下一目標和狀態。因此，任務狀態與其儲存的歷史共用一次提交。未執行任務仍保留在儲存中，且不會再次安排投遞；顯式刪除會阻止後續投遞，並把該行連同其已儲存記錄一併移除。這些記錄確認收件箱投遞，不表示使用者收到訊息或模型執行完成。

新任務初始化空的 `deliveryHistory`。缺少該可選欄位的任務會展示已有的最近一次回執（如果存在），並標明更早記錄不可用。讀取不會重寫舊任務，也不會虛構已丟失的歷史或指令快照。下一次確認投遞時，保留已有回執並追加新記錄。嚴格解碼拒絕重複訊息 id，以及最近一次回執與歷史末項不一致的情況。歷史按追加順序排列，不按牆鍾排序，因此時鐘回呼不會顛倒已確認投遞的順序。

重複任務只投遞一次最新到期發生時點，Host 重新啟動後也一樣。Every 保持與建立時間對齊，直到修改間隔後建立新的起算時點；Daily 保留本地時間與顯式 IANA 時區，Weekly 另存非空 ISO 星期集合（唯一且升序）。Every、Daily、Weekly 與 Cron 均使用 `renderRecurringReminderBatchFraming`，同一 Session 的到期任務共用一條 follow-up 訊息及其真實訊息 id。沒有可表示的下一目標時，重複任務保留未執行狀態及最近一次回執。停止的 Host 不會傳送訊息。

Daily 是互斥的第四個建立選擇器，Weekly 是第五個，Cron 是第六個，三者都不是對 `every_seconds` 或 `at` 的轉換。Weekly 選擇本地日期 ISO 星期屬於其所存集合的每個日期；解碼器拒絕未規範化的已存集合，選擇器拒絕空、重複、超出範圍或非整數的集合。它們的首個目標嚴格晚於目前時間。缺失的本地時間或日期被跳過；重疊時間選擇較早時點，每個日期一次。下一目標晚於投遞判斷時刻，且其本地日期晚於所選發生時點的日期。僅 UTC 目標限制在 0001–9999 年；邊緣處的本地日期可以進入第 0 年或第 10000 年。Session 恢復後，執行時依據目前時鐘重新核對到期成員，避免時鐘回呼時接納未來任務。

受維護的 `@js-temporal/polyfill` 0.5.1 使用主機 IANA 資料解析本地日期及重疊或缺口；Schedule 不擁有偏移量取樣邏輯，也不增加包層級。每日或每週記錄儲存規範化後的 `HH:mm:ss.SSS` 時間、時區、適用的星期集合及已提交的下一 UTC 時點。解碼和重新啟動不會重新計算該時點。規範名稱變化後，有效時區別名仍可讀取；後續目標使用主機目前的時區資料。

模型 `schedule_list`、Remote `list` 和 Session 頂部右側的提醒時鐘僅顯示活動任務。獨立的自動化任務頁面從側邊欄開啟，透過只讀 Remote `catalog` 方法讀取活動和未執行 Host 任務，不啟用 Session 或讀取其歷史。該時鐘在該 Session 沒有活動提醒時不顯示；恰好有一個時直接開啟該任務詳情，否則列出提醒供選擇。兩條路徑都開啟同一個右側邊欄任務頁籤，該頁籤渲染自動化任務頁面所用的同一詳情元件，因此都不會切換主面板。頁籤透過導航參數指明任務及其原 Session，並把該繫結帶入每個修改操作，因此從頁籤開啟或刪除都不會啟用 Session。頁面提供一行“全部/已開啟/未執行”狀態篩選，保留未執行任務詳情、最近一次投遞中繼資料和固定在位於詳情頁籤條內、與任務操作並排的原 Session 入口。頁頭的“新建”操作會開啟一個新工作階段，提醒由模型在該工作階段中建立；頁面不提供建立表單。導航等待 Session 與歸檔中繼資料，解釋不可用目標，且不會隱式恢復已歸檔 Session。任務保留與原 Session 可用性相互獨立。Every、Daily、Weekly 和 Cron 均為重複規則；頁面只按狀態分組。Daily 與 Weekly 規則標籤保留儲存的本地時間、精確規則時區和所存星期集合，不替換為下一目標顯示所用的瀏覽器時區。顯式確認刪除複用 `delete`，傳入條目的原始 Session 繫結，要求傳入繫結與已存任務一致。這項參數驗證不是獨立的呼叫者授權驗證：模型工具捕捉目前 Agent 的 Session，全域使用者介面則選擇任務的原始繫結。跨工作階段模型修改政策仍是產品決策，不由儲存佈局直接決定。無載荷的變更通知使查詢失效，重新連線時重新查詢以恢復漏掉的通知。刪除阻止後續投遞，但不撤回已排隊訊息。

第二層詳情將“規則”與“傳送記錄”分開。開啟傳送記錄時，`history` 請求攜帶任務的原始 Session 繫結，以及 1–100 的顯式分頁數量。排他的訊息 id 遊標用於讀取更早回執，新投遞追加後不會改變其定位。目錄僅保留最近一次回執中繼資料，不在每次任務列表回應中複製完整歷史。任務不存在和遊標未知屬於獨立失敗，不是查詢成功的空歷史。記錄檢視按需載入，拒絕晚到的過期回應，並將原 Session 導航與檢視記錄分開。

名稱、指令和時間更新與投遞、刪除共用 FIFO。在該佇列內比較完整的已觀察記錄，可防止舊草稿覆蓋已儲存規則或投遞已推進的目標。這樣無須增加持久版本計數器，代價是正常投遞改變目標後也會拒絕舊草稿。一次任務 put 替換規則、名稱或指令，保留身份、原始 Session 繫結、狀態、最近一次回執和已儲存歷史。請求可以省略時間變更、名稱或指令；省略的欄位保留已儲存值，僅修改名稱或指令不會改變已提交目標。歸一化後等價的修改保留已提交目標與儲存位元組。修改後的一次性任務以 At 記錄保留身份；固定間隔改變後以接納儲存時刻重新起算；鐘錶規則改變後以同一接納儲存時刻重新解析首個未來目標，而歸一化後等價的規則不產生變更。時間變更可以選擇不同的重複型別，新規則按建立時相同的方式、以同一接納儲存時刻計算目標。刪除會移除該行及其已儲存記錄（[該反轉的後果](2026-09-22-schedule-hard-delete-and-bounded-history.zh.md)），因此執行時不會再排程該任務，`history` 也不再按其原始繫結解析。未執行任務不會被重新啟用。

頁面使用現有 Host 任務 domain 和排程器，不使用 mock 引擎或 Session projection。名稱、指令和執行時間行編輯目前任務的同一份本地草稿，一次儲存把該草稿作為攜帶完整預期記錄的單個更新提交；取消恢復已儲存值，儲存失敗保留草稿，未儲存的草稿會保留到權威重新整理之後，儲存已提交與目錄重新整理失敗仍是不同結果。暫停和執行歷史操作仍不受支援。生命週期狀態與最近一次投遞確認不描述模型結果。

用戶端的呈現從已有持久化資料派生，而不擴充功能持久化格式。`schedule_create` transcript（文字記錄）卡片從該呼叫對模型可見的結果 JSON 中讀出建立的任務——該 JSON 已經序列化規範任務值——而不是宣告 `presentationMeta`：持久化 metadata 通道會為一張僅憑結果即可在 Session 日誌回放中重建的卡片增加持久欄位，而早於該卡片錄製的 Session 無需格式變更即可渲染它。側欄 Session 行的時鐘標記佔用 root 作用域的 `sidebar.session.row.leading` slot，而不是請求逐 Session provider，因為 Session 作用域的 slot 會繫結列表中每個 Session，從而啟用並保留它；同一個 root 作用域屬主約定也供給 `sidebar.session.row.hover`，兩者都讀取共享的 Host 目錄快照 `schedule/catalog()`，不讀取 Session 日誌。

Session 收件箱持久化和任務 put 發生在兩個持久化系統中。收件箱持久化先於任務 put，以免訊息尚不存在時就標記已投遞。收件箱持久化後崩潰或任務寫入失敗可能重複傳送訊息；狀態、目標和回執一起儲存，並不使兩個儲存具有原子性。投遞失敗保留任務並輸出診斷；沒有獨立的重試 timer。此功能不建立或替換 Goal。

## Alternatives considered

**啟動時載入每個 Session。** 發現任務不需要啟用 Session，這會讓 timer 恢復依賴 Agent 初始化和對話大小。

**引入獨立的 rule、run、scheduler 和 delivery 包。** 持久 schedule 與已儲存的收件箱回執足以支援任務檢視，無須獨立執行記錄或模型完成跟蹤。

**將歷史與任務分開寫入。** domain 提供獨立的逐記錄寫入，不提供多記錄事務。將歷史儲存在任務行內，可使狀態、下一目標、最近一次回執和追加歷史一起提交。採用獨立歷史儲存之前，需要明確的事務或恢復設計。

**入隊前推進，或承諾恰好投遞一次。** 先推進可能在入隊失敗時丟失訊息。恰好投遞一次需要共享事務或持久冪等協定，這兩個儲存並不提供。

**自動匯入全部歷史 Session。** 啟動掃描會重新引入對 cold 歷史的依賴。顯式重建使持久化權威來源保持明確；歷史解碼保留了現有日誌的存取能力。

**以 86,400 秒間隔表示每日提醒。** 固定經過時長無法在偏移量變化時保留本地鐘錶規則。獨立的 Daily 記錄保留了解析每個後續日期所需的規則。Weekly 以顯式星期集合而非 604,800 秒間隔延續同一決策，因此偏移量變化後仍能解析每個所選本地日期。

**手動取樣偏移量或在解碼時重新計算已儲存目標。** Temporal 提供受維護的日曆與消歧行為，無須由 Schedule 實作偏移量搜尋。即使較新的時區資料對規則給出不同解析，已提交目標仍然到期；僅後續目標使用該資料。

## Consequences

**不把 mock 的「每小時整點」引入持久詞表。** 設計稿把它與每天、每週、僅一次並列。每小時整點與固定間隔在語義上是同一種按經過時間計量的規則，因此詳情裡的該項直接對映到既有的間隔型別，而不是新增一個持久種類。若真要新增，需要新的持久變體、解碼器、目標解析與工具 schema，而它表達的能力現有間隔已經覆蓋。

任務發現和 timer 不依賴已載入的 Session。延遲、絕對時間和固定速率選擇器在與 Daily、Weekly、Cron 並存時保留自身語義；讀取已有任務不會重寫它們。Host 必須提供普通 Session 持久化和恢復服務，Web bundle 在其主機行列表中掛載 Schedule。顯式刪除會阻止後續投遞，並將任務從 `list` 和 `catalog` 中移除，不刪除對話訊息；被移除的行會帶走其已儲存回執。歷史在追加確認時按設定的視窗與條數上限裁剪，隨後載入到 Host 記憶體，並在每次確認時隨任務一起重寫。分頁限制返回記錄數量，不限制儲存增長或指令位元組數。此前被覆蓋的回執，以及任務寫入失敗的投遞記錄，無法重建。暫停和執行歷史操作仍不受支援。

必要覆蓋範圍包括從已儲存任務啟動、缺失狀態規範化、冷 Session 恢復、僅補發最新發生時點、保留未執行任務且不重複投遞、真實訊息回執、重新啟動後的刪除結果、刪除會移除已儲存傳送記錄、排隊或持久化失敗，以及銷燬。鐘錶規則的驗證要求包括缺口和跳過的日期、僅選擇較早時點的重疊、小數秒、UTC 範圍邊緣、已提交目標和別名保留，以及恢復後的時鐘回呼。Weekly 另需覆蓋星期集合的規範化與驗證、跨缺口與重疊的下一目標選擇，以及已存集合的保留。歷史解碼器必須拒絕 Daily、Weekly 與 Cron，而主機儲存接受它們。用戶端覆蓋範圍包括每種重複規則、精確規則時間、時區和星期集合、全部/已開啟/未執行狀態篩選、保留未執行任務詳情和原 Session 導航、確認刪除和通知後的權威重新整理、空列表、重新連線和晚到回應。呈現覆蓋範圍包括頁面“新建”操作開啟新工作階段、transcript 卡片從不完整或回放的結果 JSON 中收窄任務、頁頭時鐘在恰好一個任務時直接開啟並給出數量標籤、僅空閒行標記及其懸浮卡片兩個任務上限與遺漏行。歷史覆蓋範圍包括舊檔案位元組保留、追加與重新啟動、不可變的傳送指令、最近回執一致性嚴格驗證、穩定遊標分頁、繫結驗證、持久化失敗，以及重新整理或切換任務期間晚到的分頁回應。跨儲存崩潰導致的重複投遞仍是明確限制，不能被表述為完成保證。

名稱、指令和時間編輯覆蓋範圍包括所有支援的規則型別、完整記錄衝突、投遞與儲存的順序、取消、規範化後的無變更、歷史持久化不變、等待期間的控制元件、草稿保留，以及無碰撞的任務標識。[已建置 CLI 程序測試](../../../../apps/cli/tests/profiles/web/tests/schedule-timing.expected.e2e.ts) 驅動公開 Remote 請求，並在新 Host 中重新載入實際任務檔案位元組。任務和回執種子只是已保留資料的輸入，不是真實建立、投遞或模型錄制證據；這些證據需要普通 Session 操作與捕捉的模型請求。
