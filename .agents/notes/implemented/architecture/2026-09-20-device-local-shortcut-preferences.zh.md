# Agent Note: 快捷鍵偏好按裝置儲存，提交後才啟用

Status: implemented

[English](2026-09-20-device-local-shortcut-preferences.md) | 中文

## 問題

快捷鍵取決於接收輸入裝置的作業系統和瀏覽器限制。一個 Host 可服務多個裝置，而使用者錄入新組合後，本地儲存仍可能失敗。啟用未持久化的繫結會使介面與下一次啟動不一致。重寫不可讀或未來版本的偏好可能破壞舊用戶端無法解釋的選擇。

## 決策

[快捷鍵服務](../../../../packages/client/shortcuts/README.zh.md) 只儲存按執行端／平臺區分的版本化覆蓋。Web 使用同 origin 的瀏覽器儲存；Electron main 管理 `userData/keybindings.json`，與 Harness home 獨立。兩端介面卡共享總和檢查碼事務邏輯。持久化成功後釋出一個已接受設定，命令匹配、鍵帽和原生攔截都由此派生。

未載入命令保留休眠覆蓋。顯式覆蓋優先於新增預設值，相互衝突的顯式覆蓋全部停用。不可讀設定阻止普通編輯，並保留上次接受的值。全部恢復只清除已接受的目前平臺覆蓋，不會覆蓋不可讀或未來版本的資料。

## 考慮過的替代方案

**Host 設定。** 伺服器端作業系統和設定範圍不能標識存取者裝置或瀏覽器限制，Host 儲存還會耦合遠端存取者的偏好。

**樂觀啟用。** 在持久化之前更新繫結會讓儲存失敗看起來像成功，並使重新啟動行為與可見控制元件不一致。

**跨標籤頁原子合併。** localStorage 沒有比較並交換事務。Web 每次操作前重新讀取並拒絕已知過期草稿，但同時寫入採用最後成功寫入生效。Electron main 序列處理編輯並拒絕舊 revision。

## 影響

不同裝置以及 Web／Desktop 不自動同步繫結。修復不可讀偏好需要更正儲存文件；應用內編輯保留這些原始內容。瀏覽器並行不承諾無損合併。Desktop 原子替換使用共享寫入器的 Windows 重試行為，不承諾 fsync 永續性。確定性的事務、瀏覽器儲存和桌面檔案測試覆蓋失敗保留、衝突、過期草稿以及拒絕替換不可讀資料；平臺鍵盤驗收與持久化正確性分別驗證。
