# Agent Note: 在變更前繫結 JSONL 工作階段身份

Status: implemented

[English](2026-07-20-jsonl-storage-identity.md) | 中文

## 問題

JSONL 查詢會根據請求的工作階段 id 在各個專案目錄中選出物理日誌，而解析得到的 `SessionHeader` 會提供後續修復和追加操作使用的中繼資料。如果這兩個事實沒有繫結，為工作階段 A 選中的日誌就能宣告工作階段 B 的 id 或 cwd，並將修復或後續追加重定向到 B 的路徑。當同一個編碼後 id 出現在多個專案目錄中時，專案掃描也必須給出確定的結果。透過單一權威鍵解析 record 的介質可能不存在這種歧義，但交付的 JSONL provider 必須顯式繫結選定路徑。

## 決策

`findLog(id)` 是 JSONL provider 唯一的物理解析器。它掃描所有專案目錄，並要求名稱與該 id 的編碼值匹配且其中包含 transcript（文字記錄）的工作階段目錄至多有一個。對於受支援的歷史快照，generation 操作會在記憶體中轉換其 header，然後驗證 `header.id === id`，並驗證選定路徑要麼等於 `logPath(root, header.cwd, header.id)`，要麼經檔案系統路徑規範化後，兩種寫法解析為同一份 transcript；任何寫入都必須在該檢查之後。融合的 `loadCurrentStored(id)` 會在不再次讀取檔案的情況下解碼所得目前字首；已經是目前格式的快照採用無寫入快速路徑，並在該次解碼中執行相同的身份檢查。普通目前格式 `loadStored(id)` 掛鉤為協調器 fallback 保留身份驗證。`list()` 執行相同的路徑驗證，並拒絕跨專案目錄重複的 id。

協調器會獨立斷言返回的 id，並在修復、釋出狀態或持久化字尾之前比較已存 cwd 和活動工作階段的 cwd。協調器保留一份已驗證中繼資料的獨立副本；JSONL 的追加和修復操作根據該副本派生路徑。因此，`PersistenceBackend<TornMarker>` 介面既不需要限定範圍的活動工作階段查詢，也不需要儲存定位器型別。

如果設定的 JSONL 根目錄已存在，外掛載入時該路徑必須是可讀目錄。根目錄不存在仍然是有效設定，首次物化時會建立該目錄。後端對每個工作階段只支援一個活動寫入方；在所有者完成 dispose（資源釋放）且所有寫入停止之前，另一個後端實例或程序不得變更該工作階段。

## 考慮過的替代方案

**按工作階段 id 扁平化儲存。** 扁平名稱空間會讓重複釋出在同一路徑上衝突，但路徑驗證和重複項拒絕無需讓檢查依賴扁平的全域名稱空間，也能消除身份缺陷。

**透過協調器傳遞不透明儲存定位器。** 定位器可以將 JSONL 變更直接繫結到選定路徑，但 JSONL 可以根據已經驗證的中繼資料重新得到該路徑。為協調器、測試後端、追加和修復操作增加一個泛型和參數，會讓每個實作都承擔只有檔案後端需要的概念；儲存庫外 provider 把自己的介質定位器保留在自身原語內。

**協調多個活動寫入方。** 專用協調服務、程序級全域註冊表或跨程序鎖會定義新的部署拓撲，而不是修復身份驗證。受支援的拓撲只有一個活動寫入方；禁止覆蓋的硬連結釋出仍會裁決初始的同 id 建立競態。

## 後果

JSONL 日誌的身份不匹配、位置錯誤和重複會在修復或協調器狀態變更前失敗。查詢開銷仍與專案目錄數量成正比，單一活動寫入方的所有權仍是明確限制。協調器和 JSONL 測試固定了修復前拒絕、兩個受影響日誌的位元組均保持不變、列出時的路徑驗證、重複 id 拒絕、專案路徑規範化衝突與大小寫別名，以及載入時的根目錄驗證。
