# Agent Note: DeepSeek 請求圖片按官方 token 網格投影

Status: implemented

[English](2026-09-10-deepseek-v41-request-image-projection.md) | 中文

## 問題

harness 此前把每張 DeepSeek 請求圖片投影到 640,000 總畫素預算內。這個值是為已下線的 V4 視覺模型選的，[token 預估器改用 `v41` 計算器](2026-09-10-deepseek-image-token-calculator-v41.zh.md)時沒有改動它。目前 Flash 模型保留的遠多於此：它把每條邊補齊到整數個 14 px patch，把 3×3 個 patch 歸為一個 token 格，再保留 token 數 `rows × (columns + 1) + 2` 不超過 1024 的最大等比網格。正方形圖片保留 1302×1302 畫素，16:9 圖片保留 1708×966 的網格，極端寬高比最多保留約 180 萬畫素。因此 640,000 畫素投影把一張 2000×2000 的截圖縮成 800×800 發出，只有模型本可使用畫素的約 38%，預估器為這個縮小版計 422 token，而模型對完整網格收 994 token。影象理解指南里的「約 1300×1300 總畫素」只描述正方形的情況，確切規則是 token 網格。

旁邊還有兩個較小的缺口。請求版本沒有單邊上限：請求包含 15 張及以上圖片時，提供者拒絕任何單邊超過 4096 畫素的圖片，而規範化允許 8192 畫素長邊，多圖工作階段可能因一張細長圖失敗。1 MiB 編碼位元組目標是按 640,000 畫素輸出定的，會把 1302×1302 的照片壓到 JPEG 品質階梯的低檔。

## 決策

請求圖片的尺寸由路由決定，附件提供者只負責縮放和編碼。`dsh-attachment` 裡的 `ImageRequestPolicy` 改為 `ImageRequestTarget`，即一張附件的目標寬、高和位元組目標。`readImageRequest` 只按源圖長邊縮放且不放大，編碼器按路由預測的方式推出短邊；快取按附件 id、目標尺寸、位元組目標、編碼參數和新的 `request-image-v6` 變換版本取鍵，因此之前的快取條目和上傳對映都不會被複用。`dsh-attachment` 保留兩個提供者無關的幾何匯出：按總畫素預算的 `requestImageDimensions`，以及長邊精確、短邊四捨五入的 `longEdgeDimensions`。

提供者規則歸 `llm-deepseek`。`image-tokens.ts` 保留逐字移植的 `v41` 求解器，並新增 `deepSeekRequestImageDimensions`：補齊 patch 後的網格在上限內就發源圖本身，否則按源圖寬高比取求解網格的長邊，於是 3840×2160 的源圖以 1708×961 傳送，提供者再把它補齊到 1708×966 的網格。`resolveRequestImageTarget` 在省略 `imagePixelBudget` 時用這個求解器，正整數或 512×512 的 `low` 預設用 `requestImageDimensions`，然後對每張請求圖片加 4096 畫素單邊上限，使圖片數量不會改變目標，最後帶上路由的 2 MiB 位元組目標。計價對同一個目標算 `deepSeekImageTokens`，預估器和發出的圖片來自同一個求解器。pi-ai 路由從它不變的 2048×2048 畫素預算推導目標。小圖不放大，因為提供者自己會放大 544×544 畫素以下的圖片。

## 備選方案

**把畫素預算提高到 1302×1302。** 總畫素預算只對正方形正確：16:9 的源圖會按 169 萬畫素髮送而網格只保留 165 萬，4:1 的源圖網格只保留 159 萬，極端比例又會丟掉網格本會保留的細節。一條復現提供者的規則消除了猜測。

**在附件策略上加 `token-grid` 投影種類，求解器放進 `dsh-attachment`。** 最初就是這樣做的：策略變成 `pixel-budget` 和 `token-grid` 的封閉聯合，求解器搬進 `request-projection.ts`，`deepSeekImageTokens` 再從那裡引回來。這把一家提供者的佈局公式和 patch 常數放進了提供者無關的包，還起了個看似通用的名字；儲存層需要一個 `unscaled` 標誌來區分「發源圖」和「發求解尺寸」；以後每多一家提供者規則，聯合就要多長一個分支。把算好的目標交給儲存層，提供者規則和它的計價放在一起，儲存層不需要任何投影詞彙。

**用填充縮放傳送求解器的精確網格尺寸。** 求解出的網格邊長是整數個 patch，與源圖寬高比相差不到一個 patch。填充到這個框會輕微變形，儘管提供者那側也會這樣做；保持源圖寬高比可能改變取整後短邊覆蓋的 token 格數。1224×1429 的源圖以 1187×1386 傳送，官方計算器對源圖計 959 token，對傳送尺寸計 992 token。請求生成和定價共享目標尺寸，定價按目標尺寸應用官方計算規則。

**保留 1 MiB 目標。** 目標不是上限：超過它的輸出仍會以階梯最小品質傳送。1302×1302 的 JPEG 照片在品質 85 時約 400 KB 到 1.2 MB，2 MiB 讓多數圖片停在最高品質，也讓更多 PNG 截圖無損直髮，而內聯 base64 退回在 20 MiB 上界內仍能容納約七張這樣的圖片。

## 後果

正方形源圖現在最多以 1302×1302 畫素、994 token 到達模型，而不是 800×800 和 422，因此圖片密集的工作階段更早觸及 compaction 壓力，預估器按傳送目標尺寸應用官方 token 計算規則。所有已有的請求圖片快取條目和 DeepSeek Files API 對映在下次請求時重新生成。細長圖在單邊上限生效前保留完整網格：8192×78 的源圖在網格下計 396 token，但以 4096×39 傳送。`llm-replay` 不投影圖片，keyless 快照記錄不到傳送尺寸；`llm-deepseek` 介面卡測試對著 mock 伺服器固定了解析出的目標和投影后的控制代碼文字，本地儲存測試把真實圖片縮放到目標尺寸。
