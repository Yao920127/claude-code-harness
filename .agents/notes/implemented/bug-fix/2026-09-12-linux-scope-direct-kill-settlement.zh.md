# Agent Note: 等待直接程序終止後再判定 Linux scope 清理失敗

Status: implemented

[English](2026-09-12-linux-scope-direct-kill-settlement.md) | 中文

## 問題

scope 訊號傳送失敗時，已接受 fallback `SIGKILL` 或已不存在的直接程序可能尚未送達退出通知。在此期間根據 active scope 狀態報告訊號失敗，會讓仍在終止過程中的清理被判為失敗。直接程序退出本身也不能證明其後代已停止。

## 決策

[Linux scope owner](../../../../packages/subprocess/subprocess-local/src/linux-scope.ts) 保留最終 scope 訊號的失敗。程序組 `SIGKILL` 傳送成功只證明至少一個成員收到了訊號，因此還必須單獨確認直接 PID 的訊號投遞或證明它已不存在。程序組 `SIGTERM` 成功後保持單次投遞，避免重複觸發可捕捉的 TERM handler；該確認不允許進入最終 kill 的停穩等待。直接 PID 的請求使用 `process.kill()`，讓投遞錯誤與子程序的 `error` 事件分開；該事件也承載啟動失敗，並會拒絕直接結果。`ChildProcess.kill()` 可能在訊號被拒絕時、真實退出發生前發出此事件。直接 `SIGKILL` 成功提交或直接程序被獨立確認已不存在後，owner 可以等待一次直接程序退出或啟動錯誤的完成事件，再取得新的 scope 狀態。該事件獨立於輸出排空、啟動錯誤解釋和受管範圍的完成。直接訊號傳送失敗後，訊號零探測必須報告 `ESRCH` 才能證明程序不存在；程序仍存活或探測報告其他錯誤時，不允許此等待。

在直接程序停穩前，既有的 scope 為空證明仍足以完成清理。如果 active scope 查詢開始時直接程序尚未退出，且該狀態不能證明範圍為空，owner 僅等待一次直接程序停穩，隨後重新查詢 scope。直接程序退出後才開始的查詢不需要額外等待或再次查詢。仍有程序存活或程序數未知時，保留原始訊號失敗。狀態查詢和解析錯誤仍然報錯。

[原生 containment 決策](../architecture/2026-08-28-subprocess-native-containment.zh.md) 繼續負責後代成員關係，以及直接結果與整個範圍完全停穩的區分。[託管映像 fixture 策略](../testing/2026-09-10-hosted-image-test-assumptions.zh.md) 保留既有測試預算，但這些預算不能證明訊號處理已經完成。

## 考慮過的替代方案

**首次觀察到 active 狀態就報錯。** 否決，因為直接訊號傳送成功只是請求終止，不會同步送達退出通知。

**增大寬限期或在沒有完成事件時重複查詢。** 否決，因為經過的時間不能證明收到訊號的程序已經退出。

**將直接程序退出視為清理成功。** 否決，因為後代可以在直接父程序退出後繼續存活於 scope 內。

## 影響

清理只在訊號成功傳送或已證明程序不存在後等待直接程序停穩，同時保留獨立的 scope 驗證。設定的寬限期和輪詢預算保持不變。此等待可能將訊號錯誤推遲到直接程序停穩後報告，但不能讓仍有存活程序或無法觀察的受管範圍被判為成功。
