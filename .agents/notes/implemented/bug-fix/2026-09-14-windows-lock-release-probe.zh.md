# Agent Note: Windows 鎖在競爭探測前釋放

Status: implemented

[English](2026-09-14-windows-lock-release-probe.md) | 中文

## 問題

Windows 獨佔建立檔案時，若另一寫入方持有鎖，可能報告 `EPERM`。持鎖方可能在競爭者執行 `lstat` 前刪除鎖，因此之後觀察到鎖不存在，並不能證明建立失敗源於持續的權限限制。profile 模組退回的競爭測試暴露了這一競態。

## 決策

`withFileLock` 在每次 Windows 取得鎖的過程中允許對無法確認鎖存在的 `EPERM` 重試一次，沿用現有退避與截止時間。確認存在的競爭仍正常等待。第二次無法確認鎖存在的權限失敗會重新丟擲，且只有獨佔建立成功後才會執行受保護操作。

## 考慮過的替代方案

對所有權限錯誤一直重試到超時會掩蓋持續的權限失敗。要求鎖在之後探測時仍存在會拒絕合法的釋放競態。延遲測試中持鎖方的釋放只改變時序，無法修復寫入協定。

## 後果

Windows 持續的權限失敗可能在一次退避後才報告。POSIX 行為不變。atomic-write 測試強制在探測前釋放鎖，並驗證成功取得鎖和持續權限失敗；profile 測試覆蓋真實的競爭寫入方。現有憑證註冊筆記仍負責寫入序列化決策，不會被此取得鎖規則取代。
