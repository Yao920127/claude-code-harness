# Agent Note: Session 列表快取的線性對帳

Status: implemented

[English](2026-09-15-linear-session-list-cache.md) | 中文

## 問題

Client Session 列表保留行物件，以維持 React 引用穩定性。為每個快取 ID 掃描整個新列表，會使快照重建成本按平方增長；首次載入也受影響，因為新行在清理之前就已進入快取。數千個 Session 可能在列表更新時佔用瀏覽器執行緒。

## 決策

SessionManager 從對帳後的行建置一個 ID 集合，用於快取淘汰和選中行的成員檢查。欄位比較、行物件標識、陣列複用、派生順序和保留的子智慧代理地址維持現有語義。

## 考慮過的替代方案

**每次重建都替換行快取。** 新 Map 同樣可以線上性時間內移除缺失條目，但需要修改行復用路徑。臨時成員集合把改動限定在成員檢查。

**在單元測試中限制實際耗時。** 共享 CI 負載會使嚴格時間預算不可靠。實例區域性的 ID 存取器統計重複重新整理時的成員讀取次數；原實作超過線性上限，無需依賴機器速度。

## 影響

對於 n 個目前行和 c 個快取行，對帳使用 O(n + c) 時間和 O(n) 臨時成員儲存。缺失行失去快取標識；未變化的行及其陣列保留標識，離開列表的候選選中項在行返回後可以再次成為目前項。

本地 macOS arm64 Node 26 測量將生產 manager 編譯為 JavaScript，並在存在訂閱時，從重新整理開始計時到結果列表快照可讀，Remote 回應使用新建的合成物件。預熱三次後採集九個樣本，1,000、2,600、5,000 和 10,000 行的重新整理耗時中位數分別為 0.67、1.40、2.78 和 5.46 ms。原實作對應中位數為 4.86、29.01、30.62 和 459.89 ms。測量包含列表重建，排除伺服器端掃描、傳輸、DOM 渲染、瀏覽器輸入和記憶體測量，因此不能證明端到端重連延遲。聚焦 manager 的測試覆蓋淘汰、空列表、選擇恢復、標識複用和線性讀取上限。
