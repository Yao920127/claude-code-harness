# Agent Note: 重新整理後任務標籤頁的恢復

Status: implemented

[English](2026-09-18-schedule-task-tab-restore.md) | 中文

## Problem

右 Sidebar 按 [標籤型別與導航決策](../architecture/2026-09-05-sidebar-tab-types-and-navigation.zh.md) 只把 Session 佈局持久化為標籤記錄，不持久化開啟方傳入的導航參數。因此重新整理恢復出的 `scheduleTask` 標籤沒有任務身份：正文只能顯示載入回饋，chip 只能顯示固定文案，直到使用者從 Session 入口重新開啟該任務。按 [佈局持久化決策](../architecture/2026-09-14-sidebar-layout-provider-recovery.zh.md) 為終端確立的劃分，恢復內容屬於標籤型別自身 provider 的職責，而 Sidebar 沒有可供頁面型別複用的參數儲存。

## Decision

任務標籤頁儲存到它最後顯示任務的持久關聯，並據此恢復重新整理出的記錄。

關聯鍵是 Sidebar Session 加布局記錄自身的 id。`dsh.sidebar-right.v1.<sessionId>` 持久化標籤記錄以及鑄造其 id 的計數器，因此記錄重新整理後保持 id，該佈局之後鑄造的記錄也不會複用它。記錄的 `contentId` 不能作為鍵：同一種頁面型別的所有標籤都記錄在同一個 `sidebar://<kind>` 地址下，而頁面去重按 pane 進行，兩個 pane 可以各有一個任務標籤。每條記錄還儲存寫入時該記錄的 `kind` 和 `contentId`；讀取時若這一對與讀取它的記錄不一致，就刪除該條並視為無關聯。

每個 Session 一個 localStorage 文件，鍵為 `dsh.schedule.task-tab.v1.<sessionId>`，按 tab id 儲存一條記錄，把該頁面對映到其最後任務的 Session 和 id。不儲存任何任務內容。寫入時只保留 Session 已提交佈局仍然持有的標籤對應的記錄，該佈局透過 `ctx.sidebarRight.tabsIn(sessionId)` 讀取；佈局未被採用的 Session 保持其記錄不變。標籤頁出現之後成功的一次讀取無法解析的記錄會被刪除，使該標籤顯示未關聯頁籤提示，與從未有關聯的標籤相同。

只要一次導航攜帶本型別的參數，正文就在 effect 中寫入該關聯；只有記錄完全沒有導航參數時才讀取它，其他型別的參數讓記錄停留在任務缺失狀態。恢復出的身份隨後遵循既有的渲染規則：保留的記錄包含該任務時即顯示詳情，判據之後請求的讀取仍未給出該任務時顯示目錄回饋，讀取失敗時顯示帶重試的查詢失敗狀態。這樣的讀取仍無法解析的關聯顯示未關聯頁籤提示，而不是載入回饋，也絕不產生任務缺失提示，因為該提示的含義是開啟方指名了一個任務。

正文以它為目前導航觀察到的目錄讀取請求序號作為判據，並在保留的記錄使標籤頁沒有任務、且該序號之後沒有讀取成功時補發一次讀取，該讀取未落實期間顯示目錄回饋。Sidebar 會在不重新掛載正文的情況下對同一標籤再次導航，因此以導航的 revision 移動判據；早於判據發出的讀取永遠不能斷言該標籤的任務已消失。

## Alternatives considered

**用 `contentId` 作為關聯鍵。** 否決：同一種頁面型別的所有標籤都記錄在同一地址下，且頁面去重按 pane 進行，兩個 pane 的任務標籤會共用一個關聯並恢復出同一個任務。

**把導航參數持久化進 Sidebar 佈局。** 否決：這會把內容參數放進 [導航決策](../architecture/2026-09-05-sidebar-tab-types-and-navigation.zh.md) 保持為臨時的佈局快照，且之後每種頁面型別都會繼承該格式。

**把 kind 宣告為 `multiple: true`，讓每次開啟都鑄造唯一 contentId。** 否決：為了取得一個鍵而改變開啟任務的行為——開啟第二個任務會新開一個標籤，而不是在已有標籤中顯示；而且它無法恢復改動之前已存在的記錄。

**從目錄解析任務。** 否決：目錄不儲存按標籤的關聯，而開啟該標籤的 Session 入口在重新整理後已不存在。

**複用 client store 的 localStorage 持久化。** 否決：`createSnapshotStore` 的 `persist` 選項把一個 store 的整體值儲存在一個鍵下，並在該 store 建立時回填，因此需要按 Session 各建一個 store；而該關聯還必須拒絕複用的 id 並在寫入時清理已關閉標籤，這些由一份按鍵文件在一處完成，也不需要正文為其訂閱重渲染。

**在關聯旁儲存任務標題以確認恢復。** 否決：標題屬於任務內容，會隨編輯變化，而已定論的目錄讀取本身就能判斷繫結的 id 是否可解析。

## Consequences

重新整理後的 Session 無需重新開啟任務即可恢復每個任務標籤的詳情和 chip。該關聯是視窗內的瀏覽器狀態：其他瀏覽器、被清除的站點資料，或被佈局工具包複製出的標籤都沒有它，這類記錄會說明該頁籤未關聯任務，而不會聲稱任務已不存在。被丟棄的佈局快照可能鑄造出關聯仍然指名的 tab id；kind 與 contentId 守衛會拒絕其他型別的記錄，而同型別記錄會因該標籤的下一次導航被覆蓋，或在任務不再可解析時被刪除。

佈局不再被採用的 Session 的記錄會保留到其下次寫入；寫入時的清理使每個已採用的 Session 有界，且任何記錄都不含內容。

## Testing

單元測試覆蓋：導航時寫入、僅在無參數時讀取、詳情與 chip 的恢復、無法解析關聯的降級、已提交標籤的清理、複用 id 的拒絕、損壞的儲存文件，以及儲存缺失或拒絕寫入的情況。
