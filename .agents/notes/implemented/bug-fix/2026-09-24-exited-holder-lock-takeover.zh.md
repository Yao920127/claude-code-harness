# Agent Note: 接管持有者已退出的寫鎖

Status: implemented

[English](2026-09-24-exited-holder-lock-takeover.md) | 中文

## 問題

[dsh-atomic-write](../../../../packages/util/atomic-write/README.zh.md) 的 `withFileLock` 以獨佔建立方式建立 `<file>.lock`，並在 `finally` 中移除它。程序若未執行該 `finally` 就結束，鎖會留在原地，該檔案後續的每個寫入方都會超時，直到有人手動刪除它。[原始決策](../../archived/architecture/2026-07-30-settings-write-path-integrity.md)接受了這一點，因為檔案存續時間無法區分已崩潰的持有者與暫停的持有者。

profile 包鎖（`<profile>/package.json.lock`）讓這個代價顯現出來。`dsh plugin` 不安裝訊號處理器，因此在 pnpm 執行期間按 Ctrl-C、傳送 SIGTERM 或關閉其終端都會結束程序，鎖隨之留下。`dsh` 與 `dsh web` 在應用銷燬完成後立即退出，而此時被取消的安裝仍在恢復檔案，尚未釋放鎖。崩潰、SIGKILL 或記憶體不足被殺也有同樣效果。發生上述任一情況後，該 profile 上的每個外掛操作都會在 `lockWaitMs`（預設兩分鐘）後失敗，且不說明持有者已不存在。

## 決策

- 鎖沿用早期版本寫入的 `<pid>\n` 記錄，因此本變更之前遺留的鎖也會被接管，新舊版本的程序可以互操作。
- 競爭者發現鎖時讀取其記錄。若對該 PID 的訊號探測以 `ESRCH` 失敗，則證明持有者已不存在，鎖會被接管。`EPERM` 表示該程序以其他使用者身份存在，鎖保留。指向競爭者自身程序的記錄同樣保留：該程序正在執行，而瀏覽器 Worker 的程序模擬層會把自身 PID 報告為不存在。
- 讀到同一條記錄的競爭者透過一個以 `wx` 建立的認領檔案 `<file>.lock.takeover-<記錄 SHA-256 的前 16 位十六進位制>` 序列化。認領者重新讀取鎖並再次探測其 PID，僅當鎖仍是該記錄且該 PID 仍不存在時才移除它，隨後移除認領檔案並立即重試取得。PID 不存在時記錄的持有者無法再釋放它，另一次接管需要同一個認領檔案，複用了該 PID 的新持有者無法透過第二次探測，因此認領者絕不會移除另一個競爭者在已退出持有者之後獲得的鎖。
- 記錄為空、不完整、不是十進位制 PID，或指向 PID 0 或超出探測所接受的 int32 範圍的 PID 時，競爭者繼續等待。這些情況都無法證明持有者已經停止。
- 接管只能證明記錄中的程序已退出，不能證明它啟動的程序已停止寫入。[Plugin Manager](../../../../packages/boot/plugin-manager/README.zh.md) 在每次 pnpm 執行期間把它記錄在 `.plugin-manager/run.json` 中；發現該記錄的操作最多等待五秒讓記錄中的執行停止，否則拒絕執行，並指明該程序與記錄檔案。
- 探測在競爭者所在主機上進行。不支援多臺主機透過網路檔案系統共享同一個 `DSH_HOME` 寫入；保護 Session 檔案的 `flock` 同樣無法可靠地排除它們。

## 考慮過的替代方案

**移除超過固定時長的鎖。** 時長無法區分已崩潰的持有者與正在執行十分鐘 pnpm 安裝的持有者，而外掛管理器會合理地持鎖這麼久。

**由核心釋放的鎖。** 持有者死亡時核心會釋放它們，從根源上消除問題而不是檢測它。[Session 寫租約](../../../../packages/session/session-persistence-jsonl/src/lease.ts)已在兩個平臺上持有這種鎖：POSIX 上透過 `@deepseek-ai/node-addon-system` 使用 `flock`，Windows 上透過 `koffi` 使用命名訊號量。把 `withFileLock` 遷移到它上面，會讓零依賴的 `dsh-atomic-write` 引入這兩個依賴；而早期版本的程序之間只透過 `<file>.lock` 互斥，因此過渡期必須同時持有兩種鎖。若 PID 複用或共享檔案系統部署變得重要，這仍是更強的修復。

**把陳舊鎖重新命名到別處，若重新命名後的記錄不同再恢復。** 恢復可能與在此間隙取得空路徑的第三個競爭者競態，導致出現兩個持有者。認領檔案無需任何恢復即可防止這一競態。

**記錄主機名和隨機數。** 主機名能讓其他主機上的寫入方不去探測不屬於自己的 PID，但沒有受支援的部署會跨主機共享這些檔案，而且 macOS 切換網路時會改變主機名，導致變更前留下的鎖無法接管。隨機數能讓每條記錄唯一，但認領後的第二次探測已經能排除複用了該 PID 的持有者。

**終止記錄中的 pnpm 執行而不是拒絕。** 其 PID 可能已被無關程序複用，傳送訊號會殺死該程序。拒絕則把這種情況交給操作者，診斷會指明該程序與記錄檔案。

**只在 `dsh plugin` 中安裝訊號處理器。** 這隻覆蓋留下鎖的其中一條路徑，崩潰、強制退出和其他鎖檔案仍會遺留。

## 後果

- 已退出程序留下的鎖（包括本變更之前留下的）不再需要操作者處理；下一個寫入方無需等到期限即可繼續。
- 重新啟動後被存活程序複用的 PID 會讓鎖保持原樣，直到操作者移除，與之前相同。
- 共享鎖檔案但不共享 PID 名稱空間的程序，例如共享同一卷的容器或透過網路檔案系統共享的多臺主機，可能把存活持有者視為已退出。不支援此類部署。
- 競爭者在持有認領檔案時崩潰會留下該認領檔案，對應的鎖隨後不會被自動接管。
- 已退出操作留下的 pnpm 執行會阻止後續操作，直到它停止或操作者刪除其記錄。
- 仍存活的持有者會保留其鎖，因此本變更不限制存活操作的持鎖時長。
