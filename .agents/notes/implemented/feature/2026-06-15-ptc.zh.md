# Agent Note: PTC mode——模型針對工具註冊表編寫 TypeScript

Status: implemented

[English](2026-06-15-ptc.md) | 中文

## 問題

在註冊表的原生呈現方式下，agent loop（智慧代理迴圈）將每個可見能力以 JSON Schema 函式定義的形式通告給模型。`ToolRuntime` 將其 schema 貢獻給系統提示片語裝，組裝結果中的 `tools` 落到協定格式（wire format）上（也記錄在請求頭日誌中），模型每步呼叫一個 `tool-call` 塊，而在本 note 寫作時，迴圈透過 `ctx.tools.execute()` **逐個**分發每次呼叫（並行工具執行當時還是 open TODO；此後有界的並行分發已經交付——見[並行工具呼叫 note](2026-07-10-parallel-tool-call-execution.zh.md)，以及 [docs/architecture.md](../../../../docs/architecture.zh.md) 中的 rolling pool）——且**每一個**中間 `tool-result` 都會在下一次請求時重新進入模型上下文。

對於多步工具操作，這種方式 token 開銷大且序列。模型無法組合工具——遍歷結果集、根據中間值分支、扇出、後處理——每次呼叫都需要一次完整的模型往返，而每次往返都會把完整的中間結果拖回上下文，不管模型是否需要。

Cloudflare 的 [Code Mode](https://blog.cloudflare.com/code-mode/) 提出了一種替代方案，基於一個簡單的觀察：LLM（大語言模型）編寫程式碼的能力優於發出工具呼叫，因為它們見過數百萬行真實程式碼，而人為建構的工具呼叫 trace 相對很少。模型不再每步發出一次工具呼叫，而是針對工具生成的 API 編寫一段 TypeScript 程式，程式在沙箱執行時中執行，模型只篩選返回的內容——僅限它 print 或 return 的部分——而非所有中間結果。

工具呈現屬於掌管工具可見性的註冊表：將另一種呈現實作為事後的 waterfall（瀑布式事件）變換會依賴監聽器順序，並與[可重建請求](../architecture/2026-07-05-reconstructable-requests.zh.md)衝突。執行必須獨立於呈現模式，保留全新程式狀態、Host 擁有的繫結和可取消結算。

## 決策

三項決策，各自在下方獨立小節中展開：

1. **PTC mode 是 `ToolRuntime`（`dsh-tools`）的一等呈現模式**，透過經驗證的 `mode` 設定選擇：`'native'`（預設，貢獻可見能力 schema）、`'ptc'`（註冊表僅貢獻其保留的 `run_code` 傳輸通道加一份生成的 SDK `.d.ts` 到系統提示詞中）或 `'both'`（原生 schema 加傳輸通道 + SDK）。註冊表在源頭建置其規範貢獻；協作式提示片語裝的結果仍具權威性，記錄在日誌中的請求頭精確反映該返回的呈現。
2. **程式碼執行是一個能力 seam**——`packages/ptc-runtime/` 包含 Service Definition 包 `@deepseek-ai/dsh-ptc-runtime`，擁有 `ctx.ptcRuntime`（[能力 seam](../architecture/2026-06-13-capability-seams.zh.md)；消費方 = `dsh-tools`，core 消費 seam 的先例見 `agent-loop` → `dsh-llm`）。執行時對工具一無所知：它接收一段程式和命名的非同步繫結，執行程式，報告 `{ value, logs, error? }`。語言和基底是後端屬性，因此未來的 Python 或容器後端只是另一個 Service Provider 包，而非重新設計。
3. **交付的實作是 `@deepseek-ai/dsh-ptc-runtime-node`**：每個程式在全新的受管 Node 程序中，按呼叫 Session 的已解析沙箱策略執行。直接 Node API 在該策略內仍可使用；具名 Host 繫結透過單獨驗證的控制通道呼叫。

本說明負責 PTC 呈現、組合與結算。[型別化工具返回決策](2026-07-20-ptc-typed-tool-returns.zh.md)負責生成輸出、規範繫結值、`ToolCallError` 與無損外層輸出。[沙箱 Node 決策](../architecture/2026-09-11-sandboxed-node-ptc-runtime.zh.md)取代 worker 執行、信任姿態與預算實作，同時保留本說明的消費方規則。

### 每段程式的執行控制

消費方根據執行時只讀 `timeout` 描述符通告 `timeoutMs`，並把顯式值交給其解析器。不支援的提供者不公開超時欄位，並拒絕顯式請求。沙箱提升在執行時解析和啟動前使用共享的嚴格擴大權限審批輔助函式；僅替換已解析策略的模式，使授權只作用於一段程式。巢狀分發保留原始 Agent 和 Session，因此其審批與檔案策略保持獨立。失敗程式不會隱式重放，因為先前效果可能已提交。

[Node 執行決策](../architecture/2026-09-11-sandboxed-node-ptc-runtime.zh.md#deferred-timeout-design) 負責經過時間預算核算與延期的生命週期問題。

### 註冊表擁有模式

`ToolRuntime` 獲得一個經 schemastery 驗證的設定（`static Config`），這是它的第一個設定：`mode: 'native' | 'ptc' | 'both'`，預設 `'native'`。部署透過 `cordis.yml` 翻轉模式（`tools: { mode: ptc }`），無需改程式碼，遵循 no-hardcoded-tunables 約定。

**協定工具列表。** 註冊表在 `'native'` 下貢獻可見能力，在 `'ptc'` 下僅貢獻 `run_code`，在 `'both'` 下兩者都貢獻。最終的 `PromptAssembly.tools` 列表記錄在請求頭中。`run_code` 是一個保留的呈現傳輸通道，位於註冊和限制層之外；直接提示詞提供者和組裝 waterfall 仍各自負責自己的貢獻。

**與 `toolOrder` 的互動：** 如果設定的 `systemPrompt.toolOrder` 引用了原生能力名稱，在 `mode: 'ptc'` 下會拒絕所有組裝，因為那些名稱不在該模式的協定驗證範圍內。這是正確行為而非 bug：使用 PTC mode 的部署需要更新其 order 設定或移除它。

**SDK 提示詞段。** 在 `'ptc'` 和 `'both'` 下，tool-guidance order band 中的惰性 `tools:sdk` 段為目前 scope 的可見能力渲染所載入執行時語言的宣告加固定的使用說明（預設 TypeScript；[語言分發 note](../../archived/feature/2026-07-31-ptc-language-dispatch.md) 加入了 Python 與按 `ctx.ptcRuntime.language` 選擇的渲染器表）。它共享查詢和執行可見性，排除 `run_code`，並按字典序排列工具以獲得位元組穩定的輸出。

**組裝所有權。** `run_code` 和 `tools:sdk` 作為正常的組裝輸入進入受信任的 `system-prompt/assemble` waterfall。一個 scoped 的 `tools:sdk` 段可以在分發前遮蔽全域預設值，監聽器也可以移除或替換任一貢獻。waterfall 返回的組裝結果是最終的，因此修改這些輸入的人有責任在部署期望 PTC mode 可用時保持協定面的完整性；沒有恢復 pass 會覆蓋有意的組合。

**程式碼生成。** `jsonSchemaToTs()` 將 `defineTool` 的 JSON Schema 子集對映為 TypeScript，將 schema 描述帶入 JSDoc，不支援的建構降級為 `unknown`。SDK 將工具暴露為帶引號的物件鍵，支援任意名稱而無需別名或衝突處理。型別是建議性的，因為執行時在執行前會剝離型別。

### run_code 工具與分發橋

在 `'ptc'` 和 `'both'` 下，註冊表擁有 `run_code` 作為保留的呈現傳輸通道，帶兩個必需參數 `{ code: string; description: string }`（description 為 UI 標註該呼叫，沿用 bash 的先例）。它由一個正常的 `ToolDefinition` 表示以供分發，但位於可過濾的能力層之外，因此限制規則不會意外移除 PTC mode 的唯一入口。呼叫遍歷完整的工具流水線——`tools/pre-execute` → 單調性守衛 → `tools/execute` 包裹分發 → `tools/post-execute` → 由定義擁有的可選 `finalizeContent` → 不可變的 `tools/result` 通知——與原生呼叫完全一致；權限外掛可以在程式執行前檢查程式文字，最終結果觀察者看到的是規範化的外層結果。其 `execute(args, exec)`：

1. **建置繫結。** 一個 run 級別的 signal 跟隨外層取消，並在 run 結算時被 abort。每個可見工具繫結都會對無損 JSON 參數建立快照，進入原生約定的分發池（排程設計由[即時並行 Agent Note](2026-07-26-ptc-live-parallel-dispatch.zh.md) 負責），以確定性的 call id 和外層 token 作為 `parent` 執行，透過外層 execution 延後返回的上下文，並記錄 `tool/ptc-dispatch-start`/`tool/ptc-dispatch` 事件對，其中結算側攜帶完整渲染後的結果內容。成功時返回工具最終的規範 JSON 值；失敗則變為程式可見的 `ToolCallError`。每個子呼叫保留自己不可變的執行標識，並遍歷完整的工具流水線。
2. **執行已解析輸入：** `ctx.ptcRuntime.run(ctx.ptcRuntime.resolve(request))`。請求攜帶程式、繫結、執行級訊號、呼叫 Session 的 cwd 與適用的已解析檔案策略。執行級訊號將外層結算與執行取消關聯。
3. **完全停穩後結算。** 執行時結算後，橋 abort 未完成的工作並排空分發佇列後再返回。成功時返回捕捉的日誌和完成值，將其作為規範輸出；註冊表再把該值渲染為持久化的 `tool/result.content`，供結果卡片直接讀取。執行時失敗變為 `CodeRunFailedError`；後端拒絕使用註冊表的正常錯誤邊界。兩者都產生結構化的錯誤結果，且 `run_code` 結算後不允許子呼叫追加。

**子呼叫上下文透過父呼叫延後。** 在 `run_code` 內部注入會破壞父呼叫/結果的相鄰性，因此 `ToolRunContext.deferContext()` 按分發順序收集每個子結果的 `additionalContexts` 條目。即使程式後來丟擲異常，註冊表仍攜帶該陣列；迴圈只在外層結果與步驟中所有兄弟結果之後追加每個條目。外層 post-execute 阻止會丟棄工具延後的條目，只暴露阻止 decision 顯式附加的上下文。

**並行是有界的，而非被序列化。** 每次 run 擁有一個分發佇列，嚴格按提交順序啟動呼叫，並透過 `registry.executionMode` 對每個呼叫分類——與原生迴圈所用的 fail-closed `isConcurrencySafe` 約定相同。連續的 parallel 類呼叫最多重疊 `maxParallelSubCalls` 個（預設 10；設為 `1` 恢復序列分發）；exclusive 類呼叫會排空池並單獨執行。結算時放棄尚未開始的排隊呼叫。本 note 交付的是被序列化的佔位實作；取代它的排程器由[即時並行 Agent Note](2026-07-26-ptc-live-parallel-dispatch.zh.md) 負責。

**呈現。** `run_code` 的 render intent 按[呈現意圖 Agent Note](../architecture/2026-07-02-tool-render-intent-union.zh.md)在此決定：`presentCall` 建立一個 `generic` 卡片，`kind: 'execute'`，以程式文字作為標題，並將同一程式文字作為 `rawInput`；`run_code` 有意不宣告 `presentResult`，因此 TUI 和主機/用戶端執行時（Web）會透過通用原始內容退回機制，使用最終持久化的 `tool/result.content` 補全該卡片，其中包括捕捉的日誌，以及回傳值、失敗資訊或 post-policy spill 預覽。這不是 `terminal` 卡片：該卡片的語義是「工作目錄中的 shell 命令」，程式不是。參見[結果卡片完整性說明](../../archived/bug-fix/2026-07-20-code-mode-result-card-completeness.md)。

### 可觀測性：`tool/ptc-dispatch`

每次子分發在進入分發池時追加一個僅日誌的 `tool/ptc-dispatch-start` 事件，並以一個 `tool/ptc-dispatch` 結算事件收尾，後者包含父子 call id、工具標識、規範化參數以及完整渲染後的 `content`/`isError` 結果。它不進入模型歷史，但可供持久化和 UI 使用。追加發生在開放的 `run_code` 輪次內。沒有 agent 的直接執行仍然執行，但無法記錄該事件。

新子呼叫使用 `<parent>:ptc:<n>` 標識，按提交順序編號。消費者將所有 call id 視為不透明值：遷移逐位元組保留每個歷史標識，包括 `:code:` 子串，因此分發事件對、spill 引用及其他關聯保持完整。橋接層將轉發圖片上下文的來源標記為 `{ kind: 'plugin', plugin: 'tools-ptc' }`。

[V2 到 V3 PTC 規範](../../../../packages/session/session-format-v2-to-v3/README.zh.md#ptc-vocabulary)負責精確的歷史標籤與歸屬轉換；[原生 V3 准入](../../../../packages/session/session-format-v2-to-v3/README.zh.md#native-v3-admission)負責前代標籤拒絕。這些不是執行時別名：不透明擴充功能不能僅因版本變化就獲得 PTC 生命週期含義。

### ptc-runtime seam

`dsh-ptc-runtime` 負責 `PtcRuntime` 與[請求、已解析 spec、繫結及結果型別](../../../../docs/subsystems/ptc-runtime.zh.md)。`resolve(request)` 驗證支援的 cwd、timeout 與策略選擇並補全部署預設值；`run(spec)` 執行完整輸入。具名非同步繫結和可選拒絕建構器使執行時不必瞭解註冊表特定的工具名稱。

`language` 選擇 SDK 渲染器與 `run_code` flavor；不支援的語言使組裝失敗。`isolation` 標識執行基底，不標識權限。`sandboxMode` 表示消費方能否傳入已解析 Session 檔案策略。缺少執行時使 PTC 組裝失敗，native 呈現則不需要執行時。

程式結果以欄位返回；呼叫方誤用可以拒絕。無損繫結值在提供者自己的傳輸限制下跨越。沙箱模式、拒絕與強制事實獨立於成功或失敗。

### Node 程序執行時

Node 提供者擦除可擦除 TypeScript，在設定的檔案系統／子程序世界中解析可執行檔案與 bootstrap，並透過共享沙箱與受管程序所有者啟動。每個子程序都有空模型環境和全新程式全域物件。型別化拒絕建構器與捕捉 console 仍對程式可見。

繫結通訊使用與 stdout/stderr 分開的專用控制通道。Host 在分派前驗證幀、呼叫身份與允許的繫結。輸出、待處理呼叫與通道緩衝有設定上限；完成、截止、取消和協定失敗會終止並等待受管範圍。提供者 README 與沙箱 Node 決策負責確切上限和平臺限制。

### 信任姿態

所選 OS 後端按照與 Bash 相同的策略約束直接 Node 副作用。巢狀工具保留註冊表策略與審批路徑。完整或部分強制能力獨立報告；所需後端不可用時以失敗關閉。清理繼承子程序提供者宣告的範圍；程序描述符不意味著更強的多租戶保證。

### 模型看到的內容

SDK 指示模型編寫一個所載入執行時語言的非同步函式體（預設可擦除 TypeScript；Python 執行時下為 Python `async` 函式體——見[語言分發 note](../../archived/feature/2026-07-31-ptc-language-dispatch.md)），透過 `await tools.name(args)` 呼叫工具，在需要時捕捉被拒絕的工具呼叫，並僅 return 或 log 應重新進入上下文的輸出。兩種 flavor 用各自的原語陳述同一約定：相互獨立的只讀呼叫可以（MAY）在 `Promise.all`（TypeScript）或 `asyncio.gather`（Python）下重疊，有副作用的呼叫按提交順序單獨執行，有依賴的工作用 `await` 排序。宣告字首可能與原生 schema 一樣大，尤其在 `'both'` 下，但對提供者快取保持穩定。

傳輸自身的 `description` 與兩種 flavor 的 SDK 說明都以點名 `code` 和 `description` 這兩個必填參數開頭。把該呼叫描述成「傳入一個程式」的散文會讓第二個參數只能從參數 schema 中發現，而只發出 `{code}` 的模型會因 `INVALID_ARGS` 被拒，連同已寫好的整個程式一起丟失。

## 後果

切換到 `'ptc'` 的部署必須更新任何僅限 native 的 `toolOrder`。組裝監聽器有責任維護任何被重寫的協定訊息的完整性。子分發在有界的重疊池下按提交順序啟動，而每次呼叫的上下文會透過外層結果保留其 source、信封與中繼資料。

## 測試

- **Node 執行時：** 提供者測試覆蓋直接 Node 執行、已解析 cwd／策略、空環境、型別化繫結、惡意控制幀、輸出上限、截止、取消與受管清理。Bootstrap 測試覆蓋原始碼與建置後執行。
- **註冊表整合：** 測試覆蓋程式碼生成、所有呈現模式、保留名稱和限制規則、scoped 可見性、權威組裝重寫、`toolOrder`、執行時相容性失敗、完整流水線子分發、parent-token 關聯、序列化、取消和佇列排空、JSON 規範化、錯誤傳播、日誌事件、成功與失敗程式中的有序上下文延後、外層阻止抑制以及 HMR（熱模組替換）清理。
- **帶金鑰 e2e：** 真實模型在一個程式中組合兩次 bash 呼叫；另一個模型透過 PTC mode fs 分發發現巢狀的工作區指令。測試驗證摺疊的請求頭、關聯的分發事件、結果檔案、延後上下文和模型行為。
- **快照：** `ptc-turn`、`both-mode-turn` 和 `ptc-workspace-context` fixture（測試前置資料）固定 SDK 文字、請求頭工具列表、分發事件、延後上下文和結果卡片。TypeScript SDK PTC 情境透過測試擁有的顯式 profile patch 掛載 Node 執行時，並固定 Session 事件與 JSON-RPC 通知；預期回覆和完成輪次檢查在 refresh 寫入前執行。

## 曾考慮的替代方案

**一個零核心改動的附加消費方外掛。** 否決，因為 `agent/request` 在[可重建請求](../architecture/2026-07-05-reconstructable-requests.zh.md)下僅限 call-config，而變換已組裝的工具列表需要在不擁有其設定的情況下撤銷 `toolOrder` 規範化，並依賴監聽器順序。向模型提供哪些工具、以何種表示形式提供，是註冊表的單一關注點：原生 schema 和 SDK 是同一個可見儲存的兩種投影。

**將 `node:vm` 作為執行時安全機制。** 語言 realm 不會對直接 Node API 強制 OS 檔案／程序策略。因此提供者使用共享沙箱與受管程序所有者；獨立 realm 不能代替這些保護。

**在原生工具呼叫上做結果省略/摘要。** 僅解決問題中上下文膨脹這一半：裁剪舊 `tool-result` 作為可重建請求下的日誌化表面替換成本低，但仍需每次呼叫一次模型往返，且無法表達迴圈、分支或匯合。互補而非競爭；它可以在 PTC mode 下為殘餘的原生呼叫分層。

**迴圈中的並行原生分發。** 決策當時對往返成本的另一個答案；它被並行安全中繼資料阻塞，且無論如何都不提供組合能力——它並行化的是模型在一步中已經決定的呼叫。PTC mode 的佇列決策保持了兩者相容，兩者後來都已交付：中繼資料即 `isConcurrencySafe`（見[並行工具呼叫 note](2026-07-10-parallel-tool-call-execution.zh.md)），原生 rolling-pool 分發加每工具繫結並行化則基於同一個分類器。

**始終排他（忠於 Cloudflare，無模式）。** 否決，因為本 SDK 的主要消費方是編碼 agent：其日常的單次呼叫（`bash`、`read`、`edit`）作為原生呼叫已經是最優的，強制每次編輯都透過程式會給常見情境增加負擔。mode 設定讓忠實形式（`'ptc'`）只需一行設定即可啟用，而不強加於人。

**每工具可見性分層（此工具 native，彼工具 ptc-only）。** 推遲：它需要每工具中繼資料和 `'native' | 'ptc' | 'both'` 不提供的呈現拆分，且其設計取決於模型在 `'both'` 下如何分配使用的證據。

**SDK 中的清潔化識別符號別名**（`my-tool` → `my_tool`，Cloudflare 的做法）。否決：`declare const` 上的帶引號鍵使每個名稱可達，零別名碰撞邏輯；模型能正常處理 `tools["my-tool"](…)`。

**REPL 風格的持久核心**（狀態跨 `run_code` 呼叫存活）。在 MVP 中否決：跨呼叫狀態對工作階段日誌不可見，破壞了「每個請求是日誌的純函式」這一可重建性保證；每次 run 均使用全新實例則維持了這一保證。核心風格的後端在未來仍可透過同一 seam 表達，配合自己的日誌方案。

## 風險

**平臺強制能力與清理能力不同。** 執行時報告所選沙箱後端的完整性，並繼承受管程序所有者的範圍。不支援或部分的平臺保證保持明確，不隱藏在 isolation 描述符之後。

**`stripTypeScriptTypes` 標記為 experimental。** 它與 Node 自身原生 `.ts` 執行背後的引擎（amaro/swc）相同，在本儲存庫的整個引擎範圍內作為 API 暴露。緩解措施：執行時的單元測試套件會檢查位置保持和可擦除限制拒絕訊息中的必需部分；呼叫位於一個私有函式之後，且 `amaro`/`sucrase` 可在 API 變化時直接替換它。僅可擦除子集是面向模型的輸入限制，錯誤訊息會告訴模型如何修正程式。

**SDK 的提示詞成本，尤其在 `'both'` 下。** `.d.ts` 可能與它補充的原生 schema 體量相當；`'both'` 攜帶兩種表示。字首穩定性 + 提供者快取攤銷了每工作階段成本；mode 按部署設定；本 Agent Note 不做無條件節省的宣告。何時優先使用哪種模式的量化指導明確屬於上線後學習。

**註冊表 scope 增長。** `dsh-tools` 吸收了程式碼生成、一個工具、一個橋和一個事件。包內模組把這些職責分開（`ts-types.ts`、`ptc.ts` 與 `schema.ts`、`json-schema.ts`、`presentation.ts` 並列），所有 ptc-runtime 專用實作都由 `ctx.ptcRuntime` 提供。

**大型繫結值仍可能耗盡記憶體。** Node 提供者限制控制幀、未完成參數和排隊寫入，而 Host 繫結可以在這些檢查前分配其結果。無損 JSON 傳輸與外層輸出帳本不構成程序級分配配額。

**子分發的重疊由工具自身的安全宣告限定，而非由呼叫方決定。** 程式裡的 `Promise.all` 或 `asyncio.gather` 只在工具自己分類為並行安全的呼叫之間換來掛鐘並行性；一串 exclusive 呼叫仍要按順序付出各自的往返開銷，模型可能過度期望。兩種 flavor 的 SDK 說明都陳述了真實約定。本 note 交付的是使該風險絕對化的序列化佔位實作；排程器及其重疊上限由[即時並行 Agent Note](2026-07-26-ptc-live-parallel-dispatch.zh.md) 負責。

**經過時間截止包括被等待的工作。** 巢狀工具和審批等待消耗程式的經過時間預算。Host 在截止到期時停止執行並等待受管清理；它不計量程序樹 CPU 消耗。沙箱 Node 決策記錄目前預設值與延後評估的 timeout 問題。
