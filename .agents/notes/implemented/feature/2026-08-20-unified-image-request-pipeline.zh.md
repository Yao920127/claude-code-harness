# Agent Note: 統一規範化附件、請求版本與提供者檔案

Status: implemented

[English](2026-08-20-unified-image-request-pipeline.md) | 中文

## Problem

持久圖片歷史、提供者解析度、內聯請求大小和遠端檔案複用有不同限制。過去把已接納圖片直接作為之後每次請求傳送的位元組，導致一個位元組上限和一份光柵同時承擔四種職責。普通大圖會被拒絕；乾淨的 16-bit PNG 可以進入歷史，之後才被 DeepSeek 拒絕；重複 base64 使長工作階段請求持續增長；提供者拒絕後，同一持久圖片還會進入每次後續請求。

## Decision

圖片路徑有兩個顯式版本。附件後端擁有提供者無關的持久規範化附件。每條支援圖片的模型路由擁有確定性請求策略，附件後端從該附件派生並快取確切請求版本。工作階段歷史只包含規範化附件引用；內聯位元組和提供者檔案 ID 都是瞬時請求投影。

### 提供者無關的規範化附件

每條訊息最多准入 20 張圖片，源圖編碼位元組總量不超過 200MiB。每張源圖會在可設定的 20MiB、64,000,000 畫素和單邊 8192px 限制內完整解碼。規範化過程會應用 EXIF 方向，刪除中繼資料和色彩設定檔，轉換為 8-bit sRGB/sRGBA，並保持寬高比縮放進 `normalizedImageMaxPixels` 總畫素預算（預設 2048×2048），隨後受 `normalizedImageMaxDimension` 長邊上限約束（預設 8192px）。縮放減小光柵時，`originalDimensions` 記錄規範化之前、應用方向之後的輸入寬高。

規範化附件有獨立的 `normalizedImageMaxBytes` 編碼位元組目標，預設 4MiB。透明通道絕不鋪平。編碼路由只看解碼出的 alpha 事實：透明輸入編碼為 WebP（effort 0），非透明輸入編碼為 JPEG，共用 85/75/60 品質階梯；全部檔位都超過目標時保留最小產物，見取代本節的[按 alpha 路由的品質階梯記錄](../bug-fix/2026-08-24-alpha-routed-image-quality-ladders.zh.md)。處於全部規範化限制內的乾淨、單幀、8-bit sRGB/sRGBA PNG、JPEG 或 WebP 按位元組原樣直通，並保留內容定址去重。GIF、動圖、中繼資料、方向、16-bit PNG 和不相容色彩空間都會觸發轉換。源圖和轉換輸出各完整解碼一次；輸出的格式、尺寸、位深、色彩空間和透明通道事實透過驗證後，其摘要才會進入引用。

批次准入在釋出任何成員前，為每張圖片各準備並驗證一次規範化附件。驗證失敗不會開始寫入。釋出直接使用這些已準備位元組，因此大批次不會在提交時重複完整解碼和編碼。之後發生的儲存失敗不會返回部分引用；按現有儲存規則，已經發布的不可變物件可能保持不可達。

### 確定性請求版本

`AttachmentStore.readImageRequest` 按路由擁有的總畫素和編碼位元組預算派生請求版本。縮放公式為 `min(1, sqrt(maxPixels / (width * height)))`，不會放大小圖，隨後向預算內取整，確保編碼光柵不超過總畫素上限。DeepSeek V4 Flash Vision Exp 預設使用總畫素 640,000 和原始編碼位元組目標 1MiB。其 catalog 只使用一個 `imagePixelBudget` 欄位：正整數選擇確切總畫素預算，`low` 選擇總畫素 512×512，省略時使用路由預設值。2048×1024 規範化附件在這個硬上限下會投影為 1130×565。請求編碼與規範化共用同一套 alpha 路由和 85/75/60 品質階梯，按需執行；沒有任何檔位達到目標時保留最小產物（見[按 alpha 路由的品質階梯記錄](../bug-fix/2026-08-24-alpha-routed-image-quality-ladders.zh.md)）。普通 agent 輪次、直接 `ctx.llm.stream` 呼叫、壓縮和其他輔助流都使用同一派生過程。

`variantId` 和快取路徑覆蓋規範化附件 ID、變換策略版本、路由畫素和位元組預算及固定編碼參數。新快取條目在釋出前會完整解碼。快取命中只探測檔案頭，驗證格式、8-bit sRGB/sRGBA、尺寸和透明通道，不會再次完整解碼光柵；不匹配時會重新生成。因此，同一策略下的 DeepSeek Files 和 pi-ai 內聯 base64 使用相同的確定性位元組。內聯計量使用派生位元組經過 base64 膨脹後的長度，不使用規範化附件位元組數。同一程序內相同 `variantId` 的呼叫共享一次變換和快取寫入。每個呼叫方可以取消自己的等待；只有全部等待方都取消時，共享變換才會中止。呼叫方對單數 `readImageRequest` 使用 `Promise.all` 保持結果順序。本地實作透過一個 FIFO 速率限制器執行規範化和請求變換，`imageCompressionConcurrency` 的可設定範圍為 1 至 8，預設值為 2。全部規範化附件準備完成後，批次仍按順序釋出。

請求大小 offload 遵循[持久圖片省略決策](../architecture/2026-09-10-image-offload-events.zh.md)。路由根據請求版本位元組和圖片數量預算檢查保留的位置，透過 `IMAGE_OFFLOAD_REQUIRED` 報告所需移除數量。Compaction 外掛在 `image/offload` 中記錄明確的最舊圖片出現位置，Session 派生時應用標記。介面卡只準備保留的附件，將每個帶標記的位置渲染為包含其身份和目前執行環境存取路徑的佔位文字，巢狀工具結果圖片也適用。原始訊息事件保留附件引用。

### 穩定控制代碼

每張保留請求圖片前都有顯示名稱或完整附件 ID，以及實際請求尺寸。附件提供者可以給出主機物件位置；LLM 消費方將其與目前檔案系統對映組合後，再加入絕對只讀路徑、規範化尺寸和媒體型別。描述會說明規範化或請求投影可能縮小或重新編碼上傳圖片，因此模型不能從任一版本推斷上傳圖片原本的屬性。使用者訊息、工具結果、agent loop 請求、壓縮和直接 `ctx.llm.stream` 呼叫共享這套投影。路徑獨立於確定性請求版本解析，不進入其 `variantId`、持久引用或工作階段日誌。

### DeepSeek Files 生命週期

直連 `deepseek-official` 介面卡透過 [Messages Files API](2026-09-07-deepseek-messages-adapter.zh.md) 上傳每個保留的請求版本，併傳送 file-id 引用。檔案解析失敗時，[有界內聯退回](../../archived/bug-fix/2026-08-21-deepseek-files-inline-fallback.md)傳送相同的確定性請求版本。上傳 id 按 Files 端點、API-key 作用域及 `variantId` 建立索引。上傳預設請求七天有效期。Messages 中繼資料不含過期時間，因此本地複用使用原始上傳時間加設定的有效期，不承諾遠端刪除。剩餘複用時間不超過一小時的對映會直接替換，不先呼叫 retrieve。索引從不儲存 API 金鑰。

只有上傳回應返回有效的原生檔案物件、位元組數匹配，且用戶端確定了該協定的複用期限時，上傳結果才會寫入索引。缺失或不一致的回應不會留下本地對映，後續請求會重新上傳。同一作用域和 `variantId` 的並行解析共享一次提供者上傳；單個等待方無法取消其他等待方，全部等待方取消時才會停止上傳。格式損壞的上傳索引按空快取處理，並在下一次成功上傳時替換；檔案系統 I/O 失敗仍是錯誤。如果模型端點報告 ID 已過期、刪除、缺失或無效，並指出本次請求使用的一個或多個 ID，介面卡只刪除這些對映。如果回應只說明檔案狀態失效而沒有指出具體 ID，介面卡會刪除該次模型請求使用的全部對映。受影響的請求位元組會重新上傳，模型請求只重試一次。第二次仍報告檔案失效時，介面卡會按回應清理對映並返回錯誤，不會發起第三次模型請求。一次上傳配額錯誤會先列出設定數量的最舊 `dsh-` 檔案，再刪除收集到的檔案並重試一次；分頁完成後才刪除，避免遊標失效。公開檔案操作提供列表、查詢、刪除、單個變體釋放和整個作用域釋放。每個 Files 請求都攜帶 Harness 的共享 `User-Agent`。用戶端執行 Files 單次上傳 128MiB、請求單圖 32MiB、10,000 個檔案、25GiB，以及一小時到 30 天有效期限制。

### 診斷

16-bit RGB 或 RGBA PNG 屬於普通可接納輸入，會轉換為 8-bit sRGB/sRGBA。本地轉換失敗時，`read_image` 會寫明路徑、檢測到的 16-bit PNG、所需規範形式和手工轉換方法。如果 DeepSeek 拒絕已規範化請求版本，主錯誤會寫明附件 ID 或顯示名稱、持久訊息和圖片位置、規範化媒體型別、8-bit sRGB/sRGBA 位深、尺寸和提供者訊息。多圖片錯誤無法確定物件時會列出全部候選圖片。原始提供者正文保留為錯誤 cause，不會成為唯一可見訊息。

持久附件物件之後缺失或無法透過完整性驗證時，系統仍會明確失敗。持久隔離和經驗證恢復需要新增工作階段事件，由[隔離不可讀歷史附件](../../proposed/bug-fix/2026-08-20-attachment-read-quarantine.zh.md)繼續跟蹤。

## Alternatives considered

**使用一份 1MiB 規範化附件同時負責儲存和請求。** 這種做法讓模型解析度決定持久圖片細節，並把本地儲存、內聯膨脹、Files 配額和模型畫素合併成一個設定。獨立的規範化和請求策略會明確區分這些職責。

**拒絕超過提供者尺寸或達到編碼品質下限的圖片。** 提供者限制屬於具體路由，未來請求可能改用另一個模型。按比例規範化和投影請求版本可以接納普通大圖，同時約束每種後續表示。

**把 PNG 當作截圖，並拒絕 16-bit PNG。** 檔案格式不能說明畫素複雜度，16-bit RGB/RGBA 是可轉換位深，不是不支援的圖片型別。畫素取樣和轉換後探測能提供所需事實。

**把 DeepSeek data URL 作為首選傳輸方式。** 內聯 base64 會在每次請求中重複位元組，並按請求正文大小限制可用圖片歷史。Files API 引用會複用上傳後的確定性請求位元組，並限制本地複用期限、提供顯式刪除操作；有界退回只在檔案解析失敗時傳送內聯 base64。

**永久信任本地索引中的檔案 ID。** 遠端過期、刪除和上傳回應丟失會使本地與提供者狀態不一致。按回應失效和一次重新上傳可以恢復，同時避免無界重試；回應沒有給出可安全使用的精確目標時，必須使該次請求使用的全部檔案失效。

**歷史中出現圖片後拒絕選擇純文字模型。** 持久歷史可能比最初讀取它的模型存活更久。按請求生成的佔位文字可以保持工作階段可用，無需改寫歷史。

**請求每次越過上限就移除一張圖片。** 這種做法會在幾乎每次新增圖片後改寫較早的請求訊息。按固定步長遞增的移除字首會降低快取失效頻率，同時遵守設定的上限。

## Verification

包測試會生成 16-bit RGB 和 RGBA PNG fixture，驗證 8-bit 轉換與乾淨 8-bit 位元組直通、位元組壓力下保留透明通道、首個候選合規後停止編碼、位元組目標不可達時保留最小階梯產物、正方形和寬屏 640,000 畫素投影、相同變體與上傳 singleflight 且不會共享取消、變換並行上限、快取與上傳身份、跳過已持久省略的歷史附件讀取、批次只準備一次、Files 回應不一致、進入重新整理餘量時不查詢遠端並更新 ID、單個 ID、多個 ID 和模糊失效回應只恢復一次、檔案解析失敗後退回到有界全內聯請求、刪除配額檔案前完成分頁、規範化提供者診斷、純文字投影，以及普通請求與壓縮共享請求位元組。無需金鑰的組裝快照覆蓋真實工具 schema 和圖片請求路徑。使用憑證的測試只使用內建 `deepseek-official` 路由及其已設定端點，不使用自定義提供者條目。

## Consequences

持久規範化附件最多佔用獨立的本地安全上限，請求快取和遠端 Files 還會佔用額外派生儲存。確定性身份和 singleflight 使這些成本可以被共享同一 DSH home 的輪次和工作階段複用。同時執行兩個變換會降低批次延遲，但峰值 RSS 高於序列執行；記憶體更緊張的部署可以把上限設為 1。編碼器或變換策略版本變化會為未來內容產生新身份，不會改寫已有歷史。DeepSeek 圖片請求優先複用 Files；有界的陳舊 ID 恢復會處理遠端狀態不一致，檔案解析失敗則使用較小的內聯預算。缺失或損壞的持久附件仍需要單獨的隔離設計。
