# Agent Note: 對稱訊息回饋提交

Status: implemented

[English](2026-09-10-symmetric-message-feedback-submission.md) | 中文

## 問題

助手訊息的兩個評分控制元件使用不同的提交時點。點贊會立即記錄正面評分，點踩則先開啟回饋彈出視窗，僅在使用者提交後記錄。這種不對稱會讓誤觸點贊在確認前就持久化，也讓正面回饋無法攜帶與負面回饋相同的可選分類和描述。

## 決策

[回饋彈出視窗與分類](2026-09-08-feedback-dialog-and-categories.zh.md)決策負責共用表單和持久化分類表。兩種未記錄的評分都開啟共用回饋彈出視窗，並且只在提交後記錄。訊息 `FeedbackDialogTarget` 攜帶所選的 `positive` 或 `negative` 評分，`FeedbackSurface` 將該評分與彈出視窗條目一起傳給 `MessageFeedbackController.rate`。動作行會在任一操作前讀取已提交條目：點選目前評分會呼叫注入的 `retract` 操作，點選未記錄或相反評分則開啟彈出視窗。`retract` 會在控制器的序列變更佇列內重新檢查已提交評分，並在並行變更後變為無操作，因此不會把陳舊的 UI 意圖轉成裸評分 put。彈出視窗的輸入仍可全部留空：不選分類也不填描述時提交會記錄所選評分並彈出確認 toast；關閉彈出視窗不會記錄任何內容。

## 考慮過的替代方案

**保留點贊立即提交。** 這能讓正面回饋少一次點選，但會讓並列的兩個評分繼續使用不同提交模式，也無法讓正面回饋攜帶上下文。

**撤回已記錄評分也必須經過彈出視窗。** 撤回沒有需要收集的分類或描述，多一次確認會讓現有撤銷操作變得不夠直接。

**分別建立正面和負面表單。** 兩者的欄位、驗證、失敗處理與確認完全相同；在現有目標中攜帶評分即可共用一套草稿與提交生命週期。

## 後果

使用者提交彈出視窗前，兩種評分都不會建立 `feedback/message-put` 事件。正面與負面記錄都可以包含分類和備註，而點選目前評分仍會直接建立 `feedback/message-delete`，無需開啟彈出視窗。單元測試固定共用動作路徑與目標路由，無金鑰 Web 情境則透過真實彈出視窗提交兩種評分，再檢查持久事件與遙測投遞。
