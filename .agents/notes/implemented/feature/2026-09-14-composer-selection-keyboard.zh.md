# Agent Note: composer 的選擇介面沿用 composer 的 Enter 與 Escape

Status: implemented

[English](2026-09-14-composer-selection-keyboard.md) | 中文

## 問題

composer 內有兩個選擇介面在開啟期間持有焦點，兩者都把 Tab 留給了瀏覽器。

`/model` 與 `/permission` 背後的 popupSelect 面板把焦點放在自己的搜尋框上，且只回應卡片之外的指標按壓。未被消費的 Tab 於是落到原生焦點遍歷上，把卡片留在開啟狀態、搜尋框已失焦——這是一個任何按鍵都清不掉的狀態。它的高亮還總是落在首行，而選項行標記的工作階段目前值可能位於按 provider 分組的列表中的任意位置，於是第一次接受選中的是使用者沒有選擇過的行，而不是確認正在使用的值。

模型位的下拉選單（`ModelSelect`，「推理等級」行開啟其面板）把卡片 portal 出去，並用方向鍵移動真實焦點。選單開啟期間焦點留在觸發器上，而走位把「焦點不在任何行上」當作第 0 行再步進，於是第一次向下移動落在第二行上。

## 決策

`PopupSelectView` 用回車或 Tab 接受，用 Escape 或 Shift+Tab 離開：回車與 Tab 都對篩選後的高亮行執行 `select`，Escape 與 Shift+Tab 都關閉並透過對話自己的 `focus()` 把焦點還給 composer，該路徑走 Lexical，因此游標回到草稿原來的位置，而不是開頭。該方法是本決策對 `SessionInput` 面的唯一新增：外殼需要的是 composer 自己的焦點，而不是對其 contenteditable 的 DOM focus，而游標的擁有者是唯一能恢復它的一方。從 composer 的 launcher 按鈕開啟觸發選單時也在開選單之前做同樣的事：該選單是掛在編輯器上的 combobox，按鈕不能握著鍵盤。`↑`／`↓` 在篩選後的高亮間移動（迴圈，滾動進視野），`←`／`→` 仍歸搜尋框的原生游標。上述按鍵全部被消費，因此尚未就緒的行列表會把 Tab 當作 no-op 吞掉，而不是把焦點放出卡片。

`PopupSelectController` 把高亮停在已載入列表標記為目前值的那一行；沒有行被標記，或重試時保留的搜尋把該行過濾掉時，退回首行。輸入搜尋會把高亮重定到篩選結果的首行，因為搜尋要找的正是目前值之外的東西。因此在剛開啟的面板上接受即確認正在使用的值。

`ModelSelect` 的 `↑`／`↓` 仍是在所顯示面板行間移動焦點（迴圈；焦點仍在觸發器上時從近端進入）。Tab 執行接受：它啟用鍵盤所在的那一行；焦點仍在觸發器上時，改為進入選單並把焦點放在正在使用的那一行。Escape 與 Shift+Tab 都先退出已下鑽的面板，否則關閉並回到觸發器。面板切換會替換持有焦點的那一行，因此每次切換都指明鍵盤的落點：下鑽落在正在使用的值那一行（其選中行；沒有標記行時為首行），返回根面板則落在開啟該面板的那個格子上。沒有這一步，已解除安裝的行留在頁面 body 上的焦點就位於卡片自身子樹之外，掛在那裡的按鍵處理永遠收不到鍵盤事件。

在 `ModelSelect` 觸發按鈕或 portal 選單按鈕上按下滑鼠時，阻止瀏覽器的預設焦點轉移：否則 WebKit 可能先讓聚焦行失焦，並在 `click` 前關閉選單。選擇和取消仍由原生 `click` 決定。開啟選單或透過觸發按鈕關閉選單時，焦點落在觸發按鈕上。選擇請求在停用選項行前將焦點交回該按鈕，因此請求被拒絕後仍可使用鍵盤導航。

`Menu`——權限檔位、預設晶片、檔案卡與設定行背後的共享錨定下拉——沿用同一組配對：列表開啟期間，Tab 選定聚焦行（鍵盤在錨點按鈕上時，Tab 改為進入列表），Escape 或 Shift+Tab 關閉並把焦點還給錨點的第一個按鈕。只攔截已經位於錨點或列表內的鍵盤，因此頁面其它位置按下的 Tab 即使在選單開啟時也仍歸瀏覽器。行的焦點填充就是行自己的焦點提示：瀏覽器預設輪廓會與之疊加，而這一填充與指標懸停時用的是同一個，視覺語言因此一態一義。選定一行會把鍵盤還給錨點——除非擁有者自己移動了焦點（例如檔案卡把自己的預覽按鈕設為焦點）。`↑`／`↓` 與 Home／End 無論是否設定 `autoFocus` 都在列表中走位——該選項如今只決定開啟時是否聚焦首行——鍵盤所在的那一行使用與懸停行相同的填充（否則鍵盤走位看不出目前行），而 Escape 或 Shift+Tab 關閉時，只要鍵盤原本在選單裡就把焦點歸還錨點。

被關閉的選單保持關閉：`InputTriggerController` 記下使用者關閉的那個命中（Escape／Shift+Tab、指標關閉或一次落定選定）的身份，同一 token 以同一查詢重新 track 時選單保持關閉，因此關閉後恢復游標、或已選定命令關閉它開啟的介面，都無法把它召回來；新的查詢或另一個 token 才會重新武裝。

行契約不變。產出方本就標記自己的目前行 `active`，兩個介面也都沒有新增下鑽動詞。

## 備選方案

**Tab 負責走位。** 讓 Tab 成為第二個 `↓`，會讓這兩個介面在 composer 已經用來接受的按鍵上沒有接受動作，並把 Shift+Tab 變成「反向走位」，而不是它相鄰按鍵所映像的 Escape。最終選擇的是 composer 自己的配對：回車／Tab 接受，Escape／Shift+Tab 離開。

**讓面板的 Tab 落到原生遍歷。** 卡片的關閉只回應指標按壓，殘留狀態——卡片開啟、搜尋框失焦——會一直留到下一次點選。

**面板高亮繼續停在首行。** 這正是本決策要消除的缺陷：剛開啟的面板上接受會作用於沒有人選擇的行。

**搜尋之後也把面板高亮重定到目前值。** 搜尋表達的是對目前值之外內容的興趣；把高亮留在查詢可能排到末尾的行上與查詢相悖。

**被下鑽的面板落在首行。** 它把鍵盤停在最上面的一檔而不是正在使用的那一檔——正是「高亮停在目前值」要消除的缺陷——於是沒看就按下的接受動作會切換推理等級，而不是確認它。

**模型位的 Tab 保持原生。** 焦點離開觸發器與卡片時模型位會因失焦關閉，所以那裡的 Tab 並不是死狀態。它被否決是因為：一個沿用 composer 按鍵含義的介面不應把 Tab 單獨排除——那裡的 Tab 與回車一樣接受，Shift+Tab 則離開。

## 驗證

[模型位瀏覽器證據](../../../../apps/web/tests/declared-reasoning.e2e.ts) 用真實 Chromium 與 WebKit 驅動已釋出的 bundle：兩者都驗證原生滑鼠選擇、取消、請求被拒絕後的焦點以及鍵盤導航。每種引擎都會開啟已下鑽的等級面板，用 `↑` 走位，用 Tab 選定一檔並斷言儲存下來的推理等級，隨後重新開啟該面板、斷言鍵盤落在那一檔而不是列表頂部，再用 Shift+Tab 退回被下鑽的格子並關閉。[模型位鍵盤測試](../../../../packages/client/ui-model-selection/tests/model-select.client.spec.tsx) 覆蓋下鑽交接落在正在使用的值上（沒有標記行時落在首行）、交回給該格子、`↑`／`↓` 的雙向迴圈走位、Tab 選定聚焦行以及從觸發器進入選單、Shift+Tab 先退層再關閉，以及選單關閉時 Tab 保持原生。[彈出視窗檢視測試](../../../../packages/client/ui-commands/tests/popup-view.client.spec.tsx) 覆蓋 Tab 接受停放的高亮並完成消費與焦點歸還、Shift+Tab 關閉且不接受、行仍在載入時 Tab 被消費且焦點不離開卡片、方向鍵與原生左右游標互不干擾，以及 `↑`／`↓` 的迴圈。[觸發流水線測試](../../../../packages/client/ui-input-trigger/tests/service.client.spec.ts) 覆蓋關閉粘在它自己的命中上（Escape、指標關閉、落定選定三種）、同一命中重新 track 時保持關閉，以及查詢改變後選單重新武裝。[Menu 測試](../../../../packages/client/ui-primitives/tests/atoms.client.spec.tsx) 覆蓋不帶 `autoFocus` 的方向鍵走位（從近端進入、兩端迴圈、跳過停用行）、Escape 把焦點還給錨點、Tab 選定聚焦行、Shift+Tab 關閉並把焦點還給錨點、Tab 從錨點進入列表，以及列表開啟期間無關位置的 Tab 保持原生。[彈出視窗控制器測試](../../../../packages/client/ui-commands/tests/popup.client.spec.ts) 覆蓋高亮的停放、沒有標記行時退回首行、重試時在保留的搜尋內重新停放，以及輸入時重定到首行。彈出視窗面板的 Tab 只有單元覆蓋：目前還沒有 Web 情境驅動 `/model` 或 `/permission`。

## 影響

在剛開啟的彈出視窗上接受確認的是工作階段正在使用的值，而不是切換它，因此 Tab 不會帶來意外的結果；對已經走過位的高亮按 Tab 會選定那一行，與回車一致。離開這兩個介面用 Escape 或 Shift+Tab，且介面開啟期間它們都被消費，鍵盤使用者因此是靠 Escape 或 Shift+Tab 退出，而不是 Tab 走開。composer 的觸發選單保留自己的 Tab：它確認或下鑽高亮候選——該選單的下鑽動詞沒有其他鍵盤入口——而 Escape 與 Shift+Tab 則離開該選單且不選定，退出動作因此永不消耗草稿。同一組配對一次性覆蓋所有 `Menu` 使用方：composer 的權限檔位、預設晶片、檔案卡與設定裡的下拉都以 Tab 選定、以 Shift+Tab 離開。按鍵記在各歸屬模組的說明與 README 中，觸發選單的按鍵則留在 `ui-input-trigger` 的 README。
