# Agent Note: Background job completion wakes are unbounded by default

Status: implemented

[English](2026-09-22-unbounded-completion-wakes-by-default.md) | 中文

## 問題

[空閒所有者喚醒決策](2026-08-11-background-job-completion-wakes-an-idle-owner.zh.md)釋出時 `maxConsecutiveWakes` 預設為 3：空閒所有者最多被任務完成喚醒三次，此後的通知降級為注入，只有被領取的使用者訊息才補充預算。計數器按所有者記錄，並由所有任務型別共用——後臺 `bash`/`pwsh`/PTY 命令與一次性 `subagent_*` 子級。

一個工作階段在沒有使用者訊息的情況下串起超過三個這樣的任務就會觸頂（issue #4944，來源為 [dsh-external/issues#641](https://github.com/dsh-external/issues/issues/641)）。第四條通知被注入到一個無人會喚醒的所有者的 next-step inbox；用戶端不渲染待領的 `context` 訊息，工作階段就帶著一條自己看不見的通知停在那裡。`tool-jobs` 的提示詞向模型承諾「任務完成會在工作階段內通知你，不要輪詢」，恰恰鼓勵了會耗盡上限的「啟動後結束本輪」模式。停擺發生在使用者離開時，看起來像掛死，直到使用者輸入點什麼。

## 決策

`maxConsecutiveWakes` 沒有預設值。未設定時，`wakeup` 投遞下抵達空閒所有者的每次完成都會開啟一輪。`agent/inbox/claimed` 補充監聽與按所有者的臺帳只在設定了上限時存在；設定的值仍必須是整數輪數，`Infinity` 被拒絕，因為省略該欄位已經表示無上限。

上限所針對的自激鏈——被喚醒的一輪啟動某個任務，其完成又喚醒它——依然真實存在，想要該界的部署自行設定欄位。取捨在於：這條鏈花掉的是使用者看得見、能停下的模型請求，而停在上限之外的通知是不可見的：用戶端不顯示，沒有機制重新充能預算，模型得到的承諾也成了假話。可觀察的代價勝過不可觀察的停擺。

`dsh run` 不受影響：headless 在任務輪次空閒後即退出，沒有可喚醒的空閒所有者。

## 被否決的替代方案

**保留預設上限，讓停駐的通知可見**——工作階段級的待處理指示或任務列表上的未讀標記。這保住了失控約束，但仍然違背提示詞的承諾：模型結束本輪等著通知，卻要等到使用者動手才收到。可見性值得為已設定的上限補上；它不能為預設上限辯護。

**只統計自激的喚醒**——只有被喚醒的一輪又啟動了新的後臺任務時才計入預算。這約束了失控鏈而不切斷一串獨立任務，但這種區分需要外掛把任務啟動與喚醒所開啟的輪次關聯起來，是目前沒有消費者需要的狀態。若設定的上限被證明過粗，它仍是自然的細化方向。

**用冷卻或速率限制代替計數器。** 時間無法區分想要的鏈與失控的鏈；想要的情形往往正是慢的那種，而速率限制觸發時同樣會把通知不可見地停駐。

**在每條輪次結束路徑上覆查 next-step inbox**（abort、LLM 錯誤、被拒絕的 pre-step）。這關閉了 issue 列出的其他停駐點，但它們只會被一條已停駐的通知觸及；沒有預設上限時，報告的情境根本不會停駐通知。它仍是獨立的 `agent-loop` 改動。

## 影響

- 串起後臺任務的無人值守工作階段會為每次完成被喚醒；每次喚醒一次模型請求是其代價，使用者可以停止工作階段。
- 上限是可選設定。其 README、config-catalog 與 JSDoc 說明了設定它帶來的靜默停擺代價。
- 單元覆蓋釘住預設設定下連續四次無人值守完成各開啟一輪；上限、補充與 quiet 投遞的測試保留顯式的 `maxConsecutiveWakes` 值。
- 錄製工作階段快照無變化：沒有任何內建 profile 設定該欄位，也沒有既有情境串起超過三次空閒完成。
