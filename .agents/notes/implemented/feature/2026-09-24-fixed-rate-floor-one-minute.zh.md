# Agent Note: 固定速率下限改為 1 分鐘

Status: implemented

[English](2026-09-24-fixed-rate-floor-one-minute.md) | 中文

## Problem

`every_seconds` 會拒絕所有低於 300 秒的間隔，Web 用戶端也把該下限複述為自己按單位計算的下限：1 小時、5 分鐘或 300 秒。同一產品已經提供粒度為 1 分鐘的 `cron` 選擇器，於是兩個都在描述重複節奏的選擇器對「最短能填多少」給出了不同答案：每分鐘重複一次的提醒用 `cron` 可以表達，用 `every_seconds` 會被拒絕。該下限也讓預設釋出 Schedule 的 Web 介面難以試用——任何人建立的第一條重複提醒都不可能在五分鐘內回到。

## Decision

`packages/schedule/schedule/src/domain.ts` 的 `MIN_EVERY_INTERVAL_SECONDS` 為 60。主機解碼器、建立與更新驗證、`every_seconds` 工具參數描述及其拒絕訊息都讀取該常數，因此一處改動即可移動主機陳述該下限的所有位置。

用戶端保留自己的 `MIN_INTERVAL_SECONDS = 60`，「執行時間」卡片用它驗證秒數行，並據此推導各單位的數量下限：1 小時、1 分鐘或 60 秒。對應行的在地化提示與拒絕文案改為 1 分鐘與 60 秒。

1 分鐘是無需新增協定決策的最短節奏：它與 cron 選擇器的粒度一致，且每個被接受的值仍是以整秒錶示的間隔，持久記錄本來就以整秒儲存。已儲存的記錄保留主機當初接受的值：按舊下限（300 秒及以上）寫入的記錄仍然有效、仍可回放；由於舊下限拒絕了低於它的值，因此不存在需要遷移的資料。

## Alternatives considered

**保留下限 300 秒。** 兩個選擇器會繼續對最短重複節奏給出不同答案，而每分鐘一次的節奏仍只能透過 `cron` 達到。

**把下限降到 1 秒。** 低於分鐘級的間隔會讓每條提醒產生更多持久 follow-up 訊息與 timer 重新對齊，而背後沒有這樣的需求；分鐘粒度已經覆蓋產品在別處命名的最短節奏。

## Consequences

- 固定速率提醒現在可以每分鐘重複一次；最小可接受值對模型可見，出現在 `every_seconds` 的描述與用戶端的提示文案中。
- 投遞行為、批處理、補跑與間隔運演算法則不變：被接受的間隔仍以建立時刻或接受儲存的時刻為起算點，每條逾期記錄仍只貢獻最新一次發生時點。
- 部署無法透過設定提高該下限；它是協定常數，需要更長最小間隔的部署應在建立任務的介面上自行約束。
