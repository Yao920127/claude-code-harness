# Agent Note: 瀏覽器 GIF 保留單一證據鏈

Status: implemented

[English](2026-08-08-browser-gif-evidence-chain.md) | 中文

## 問題

瀏覽器演示的分鏡可以由每張都真實的截圖組成，卻無法證明這些截圖來自同一次真實執行。複用應用全域狀態可能引入舊設定或舊工作階段；錄製自動化可能誤將不同模型執行的畫面合併；聊天 transcript（文字記錄）可能顯示降級處理成功，卻沒有揭示觸發降級的工具拒絕。按無障礙名稱進行模糊匹配，還可能誤把提示詞回顯或後代文字當成預期結果。

無頭模式下的生產環境錄製還有兩道邊界。產品預設設定可能開啟自動化無法操控的原生作業系統介面，而用 mock 或測試掛鉤替換該介面，就意味著 GIF 不再展示生產路徑。釋出之後，上傳或推送成功也不能證明上傳的資產在評審路徑上可達且完好，或 GitHub 能將 PR（Pull Request）的 Markdown 識別為圖片。

## 決策

[`record-browser-gif`](../../../skills/record-browser-gif/SKILL.md) 工作流將一套分鏡作為同一次執行的完整證據，並固定到精確的 PR head。建置之前，工作流要求 worktree 乾淨並記錄其 commit SHA。每次執行都使用全新的 `DSH_HOME`、`DSH_AGENTS_HOME`、工作區、工作階段和隔離瀏覽器狀態，所有釋出幀均來自同一個伺服器及同一次由模型驅動的情境執行。無法建立全新瀏覽器上下文時，應在導航之前清除該 origin 的 cookie 和站點儲存。只有使用者提出要求或確有必要時才能使用使用者已有的瀏覽器狀態；必須在 GIF 旁說明使用了該狀態，並不得以此證明用戶端狀態全新。錄製失敗時，丟棄該次執行並從全新的狀態根目錄重新執行，不與另一次執行合併。

瀏覽器自動化會等待唯一且精確的語義狀態。如果需要證明工具呼叫、拒絕或恢復，分鏡就必須包含詳情幀或軌跡幀：標明工具、顯示其狀態或穩定錯誤碼，並展示後續結果。最終編碼出的 GIF 始終是驗證物件；如果檢視器無法播放動畫，應從該 GIF 中解碼出代表性幀，而不能將源截圖視為等效證據。

仍應優先使用已有的瀏覽器控制工作流。如果該工作流不可用，錄製程式應在隔離的無頭瀏覽器中使用儲存庫已宣告的 Playwright 依賴，而不是安裝其他驅動或開啟使用者的瀏覽器。只有透過正常應用設定選用官方且可由瀏覽器操作的生產後端，才能替換原生生產介面，並且必須在 GIF 旁註明這一覆蓋。fixture（測試前置資料）、mock 傳輸層、合成事件和測試專用掛鉤均不能支撐真實生產實作的主張。

釋出環節會再次驗證邊界。首選路徑使用 `gh --attach` 上傳（v2.99.0 或更高版本；僅限 github.com；不超過 10 MB）：正文件案引用本地 GIF 路徑，命令上傳已驗證的產物並把該引用就地改寫，之後線上正文必須顯示改寫後的上傳 URL，且該 URL 必須返回 `200` 與 `image/gif`。當 attach 無法使用時——GIF 超過 10 MB、`gh` 版本過舊或儲存庫位於 GitHub Enterprise Server——仍保留資產分支路徑：該分支只包含媒體檔案，暫存和釋出的位元組必須與已驗證產物一致，私有儲存庫中的資產須透過經身份驗證的 API 或原始內容請求檢查其路徑、位元組大小、總和檢查碼、回應狀態和媒體型別，這隻能證明儲存庫成員的評審存取路徑（[文件站點圖片決策](../../archived/process/2026-08-06-doc-site-carries-its-images.md)解釋了公共站點為何不能依賴私有的原始內容 URL）。修改 PR 正文之前，必須再次確認線上 head 仍與錄製時的 head 相同。編輯後還要再次檢查線上 head，且它必須保持為該記錄值；GitHub 的 Markdown 渲染器則須單獨生成預期圖片。

## 曾考慮的替代方案

**只要可見狀態看起來等價，就允許使用不同執行的畫面。**視覺相似不能證明各畫面共享同一狀態、具有因果順序或來自同一次情境執行。重新錄製需要再執行一次真實模型輪次，但能維持整套分鏡所表達的主張。

**將聊天 transcript 視為工具恢復的充分證據。**最終答案能證明任務已經完成，卻可能隱藏呼叫了哪個工具、失敗是否為結構化失敗，以及模型是否從該失敗中恢復。軌跡幀或詳情幀可以直接承載這些事實。

**使用 fixture 或測試掛鉤替換無法存取的原生 UI。**這種做法透過改變被觀察的產品路徑來簡化自動化。透過正常設定選用官方生產後端，既能保持受測實作真實，也能明確表述所採用的較窄執行模式。

**相信上傳成功，或相信推送成功。**上傳或推送只能證明 GitHub 接受了相應位元組，不能證明正文引用指向已上傳的資產，或 Markdown 能把圖片渲染出來。重新讀取線上正文並經 GitHub 的 Markdown API 渲染，覆蓋了評審者實際使用的兩道釋出邊界。

## 後果

GUI 證據現在能證明一次具有因果關係的執行，而不會把不同執行中的可信畫面當作同一次執行的證據；評審者既可以檢查結構化的工具失敗，也可以檢查最終完成的結果。在 PR 正文被視為完成之前，釋出驗證可以發現陳舊的 PR head、損壞或位置錯誤的媒體檔案，以及無效的圖片 Markdown。

該工作流會佔用額外的臨時狀態；錄製失敗後，可能需要再執行一次由真實模型驅動的情境；通常還會增加一張詳情幀以及釋出檢查——線上 head 與正文的復讀、Markdown 渲染和上傳 URL 請求；資產分支路徑還會增加其經身份驗證的資產檢查。相比互動式桌面，無頭錄製可使用的生產後端更少；每個所選後端都會在 GIF 旁說明。
