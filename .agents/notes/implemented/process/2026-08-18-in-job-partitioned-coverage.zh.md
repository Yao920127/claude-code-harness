# Agent Note: 單 job 分割槽覆蓋率

Status: implemented

[English](2026-08-18-in-job-partitioned-coverage.md) | 中文

## 問題

原生 Windows 覆蓋率是拉取請求完整清單中回饋最慢的路徑。把插樁套件保留在單個 Vitest 程序內並只使用 1 個 worker，可以避開較大程序內 worker 池曾出現的 worker 丟失和 Node 24 CJS lexer 故障，但一次失敗可能超過 14 分鐘才會顯現，而且門禁排程器會在子程序結束前扣住輸出。

這項最佳化必須保留全部測試以及合併後的逐檔案 100% 閾值，也必須留在既有覆蓋率 job 內：若把同一套件拆到多個工作流 job，就會向必需拓撲增加 checkout、安裝、產物傳輸和合並 job。

## 決策

普通的 `pnpm run test:coverage` 命令仍只啟動一次 Vitest。Linux 覆蓋率 CI 將 `DSH_COVERAGE_PARTITIONS` 固定為 4；原生 Windows 現在也固定為 4，以降低自託管高並行下的程序建立壓力。執行期間不會由任何耗時觸發器改變這兩個數量。[覆蓋率豁免重型套件](../../archived/process/2026-07-31-coverage-exempt-heavy-suites.md)仍作為獨立的無插樁門禁與插樁工作並排執行。

整個 `packages/typert/` 組豁免原始碼覆蓋率，並在無插樁門禁中執行。其編譯器 fixture（測試前置資料）、目錄復現、loader、協定及註冊表斷言仍為必需檢查。共享的[豁免清單](../../../../scripts/coverage-exempt.ts)選擇每個 Typert 包及其巢狀測試；project 排除規則與分割槽清單都使用該清單。豁免只移除覆蓋率採集，不忽略測試或掛鉤失敗。

啟用分割槽後，`scripts/run-gates.ts` 為插樁門禁選擇 `pnpm run test:coverage:partitioned`。`scripts/coverage-partitions.ts` 按設定數量並行啟動 Vitest 子程序，每個程序只用 1 個 worker。協調器透過 `vitest list --filesOnly` 收集插樁清單（呼叫方過濾器會先收窄清單；exempt 重型套件需在此剔除，因為 list 不應用其排除），從協調器持久化的 gitignore 檔案讀取逐檔案耗時（windows-coverage job 透過 GitHub cache 恢復並儲存該檔案，因為 checkout 會刪除它且 Vitest 自身快取無法在 CI 存活），並借最小堆按最長處理時間把檔案分配到各分割槽，使重量級子程序密集型套件分散到不同子程序，而不是全部落入路徑 hash 恰好命中的那一個分片。每個分割槽獲得一個臨時 Vitest 設定，其 include 按 project 拆分（命令列傳檔案會超過 Windows CreateProcess 上限；互斥的 thread-safe 與 process-bound project 只保留各自的檔案，避免任何檔案跑兩次）；空分割槽會在任何子程序啟動前被拒絕，最重的分割槽最先啟動使其結論最早落實（fail-fast），耗時歷史透過 GitHub cache 以每 run 唯一鍵恢復與儲存（cache 條目不可變）。分割槽模式會在各子程序中關閉閾值與覆蓋率報告器，為每個子程序分配獨立報告目錄，讓每個程序寫出 1 份 blob 報告，並額外掛載[分割槽位置規範化器](../bug-fix/2026-09-13-partitioned-coverage-location-canonicalization.zh.md)這一 Vitest 報告器，使每份 blob 的位置保持可合併。

協調器等待全部子程序結束，驗證 blob 目錄只包含預期檔案，然後執行一次 `vitest --merge-reports ... --coverage`。只有這條合併命令應用儲存庫的逐檔案語句、分支、函式與行閾值，因此係統不會拿有意不完整的測試清單單獨判定任一分割槽。

`DSH_COVERAGE_MAX_WORKERS` 繼續控制無插樁豁免門禁和普通非分割槽路徑的規模，不會調整分割槽子程序。原生 Windows 為豁免門禁分配 2 個 worker，並允許 4 道外層門禁並行。在完整參考流程中，工作區建置與生產網站驗證會立即啟動，兩道覆蓋率門禁都等待完整建置；這次等待也能避免豁免門禁的臨時 Oxlint 探針與原始碼編譯競態。拉取請求覆蓋率 job 與 Linux 一樣以零建置方式執行：工作區匯入透過 tsconfig paths 對映解析到 `src`，而消費建置產物的套件——豁免門禁的打包器映像斷言與全語料匯入 sweep，以及插樁語料的 client-bundle 產物驗證——在未建置的檢出上會自跳。觀測性清單隻等待兩道覆蓋率門禁結算，因此在覆蓋率失敗後仍會執行；各門禁自身的 `needs` 依賴仍要求前置門禁透過。Linux 讓 4 個插樁分割槽程序與 2 個豁免 worker 重疊執行，在保持每個插樁程序只有 1 個 worker 的同時，恢復普通路徑原有的 4 路插樁並行。

## 失敗與輸出語義

分割槽子程序透過協調器流式傳遞 stdout 與 stderr。覆蓋率門禁選擇 `run-gates` 流式輸出，因此測試進度與失敗會在發生時進入 CI 日誌，排程器不會緩衝完整日誌。協調器還會為每個子程序保留一份有界的 64 KiB 混合輸出尾部；子程序以失敗狀態結算時，它會列印 spawn 錯誤、結束代碼或訊號，並在驗證完整 blob 集合前重印這份尾部，使具體 Vitest 失敗與最終分割槽診斷相鄰。

普通測試失敗仍透過 `--coverage.reportOnFailure` 產出 blob，使合併步驟可以先報告完整覆蓋率狀態，再由協調器返回失敗。spawn 失敗、訊號終止、非零退出、blob 缺失或多餘，以及合併失敗都會讓門禁失敗。協調器只刪除自己擁有的覆蓋率目錄樹；若該路徑是連結，則只 unlink，不遞迴跟隨。

## 驗證

`scripts/coverage-partitions.spec.ts` 固定了參數建構、包腳本分隔符移除、單 worker 分割槽、加權最長處理時間分配（含一個在分配忽略記錄權重時必然失敗的案例）、唯一一次合併閾值命令、失敗測試合併、完整 blob 驗證前的失敗診斷、spawn 失敗後等待兄弟分割槽，以及連結安全清理。`scripts/run-gates.spec.ts` 固定了顯式啟用、非法數量拒絕、兩道原生 Windows 覆蓋率門禁對完整建置的依賴、完整 Windows 清單及其阻斷性劃分，以及不緩衝的流式輸出。可能在分割槽間移動的 React fake-timer 案例會在 `act()` 內推進計時器；依賴幾何位置的 portal 測試會固定元素矩形，使不同分片排程不會把延遲更新或 jsdom 座標變成只在覆蓋率執行中出現的失敗。

已完成的原生 Windows 對比中，雙分割槽耗時約 405 秒，16 分割槽耗時 112.66–122.01 秒；這些資料來自先前的門禁順序，只用於比較分割槽延遲，不代表目前峰值。目前的覆蓋率階段會讓 4 個插樁分割槽程式與 2 個豁免 worker 並行，共形成 6 個覆蓋率執行單元。若改為 16 個分割槽，則在尚未結束的生產網站工作或系統開銷計入之前，該階段就會達到 18 個執行單元。4 個分割槽保留獨立程式隔離並與 Linux 對齊，代價是單 job 覆蓋率牆鍾更長；這是為了降低自託管高並行下 vitest worker 啟動失敗而接受的取捨。兩個 Linux 樣本中，保守的雙分割槽設定耗時 276.68 秒和 282.27 秒；該設定執行穩定，卻把普通路徑原有的 4 個插樁 worker 減半。4 個分割槽恢復這份並行，使 16 核託管 runner 上的覆蓋率執行單元總數為 6，故障切換虛擬機器的 32 個 runner 實例最多合計 192 個執行單元。這些數值來自完整執行或固定容量上限；執行尚未結束時跨過任意耗時刻度，不構成增加並行的證據。

## 曾考慮的替代方案

**使用工作流級分片。** 不予採用，因為多個 job 會重複設定工作，並需要上傳、下載產物以及合併依賴。所選分割槽方案只在同一個 job 和工作區內使用多個程序。

**提高單個插樁程序內的 Vitest worker 數。** 不予採用，因為已完成的 Windows 高扇出試驗暴露了 worker 退出、fixture 不穩定和 Node 24 CJS lexer 故障。相互獨立的單 worker 程序既保留隔離，也能讓所選分割槽並行執行。

**在每種主機上使用相同的分割槽數量。** 先前不予採用，因為 Linux 的 4 程序執行與 Windows 的 8 程序執行具有不同的啟動成本與資源上限。本次變更在 Windows 高並行執行暴露 8 分片 worker 啟動失敗後，將兩者統一為 4 分割槽。

**在每個分割槽內獨立應用閾值。** 不予採用，因為每個分割槽有意只看到套件的一部分，會誤報未覆蓋檔案。閾值歸合併報告所有。

## 後果

每個分割槽都要支付 1 次 Vitest 啟動與設定開銷，最後還要執行 1 次報告合併，但它不引入另一套工作流拓撲，並保留唯一的最終閾值判定。分割槽輸出可能交錯，但分割槽啟動標籤和 Vitest 檔案標識仍可用於歸因。

Linux 與 Windows 使用相同的協調器，並各自設定分割槽數量與外圍 worker 預算。兩條拉取請求覆蓋率通道都以零建置方式執行；完整參考流程（serial-windows standby）仍在建置門禁之後啟動其覆蓋率門禁，使消費建置產物的套件對真實產物執行。本地覆蓋率預設保持簡單；只有呼叫方顯式選擇分割槽包腳本並提供大於 1 的合法數量時，才啟用分割槽。

未來調優從一個固定設定的完整執行開始。進度緩慢本身絕不會提高分割槽數量或外層並行，因為反覆重新啟動會抹掉選擇穩定設定所需的唯一證據。
