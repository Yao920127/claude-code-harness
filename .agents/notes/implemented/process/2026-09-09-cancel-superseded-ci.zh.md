# Agent Note: 取消被取代的 CI 驗證

Status: implemented

[English](2026-09-09-cancel-superseded-ci.md) | 中文

## 問題

驗證已被取代的 PR（Pull Request）修訂或 master 提交會消耗執行器容量，卻不能確定最新修訂的狀態。無條件執行的聚合判定和覆蓋率耗時歷史上傳，還可能讓已取消的執行繼續處理記帳任務。保留舊的合併後執行，意味著優先完成歷史驗證而非目前驗證，在共享自託管池上尤其如此。

## 決策

驗證優先保留各工作流/引用組內最新的執行。[CI](../../../../.github/workflows/ci.yml)、[CI master](../../../../.github/workflows/ci-master.yml)、[真實 API e2e](../../../../.github/workflows/e2e.yml)，以及無憑證的 [dsh](../../../../.github/workflows/release.yml) 和 [vendor](../../../../.github/workflows/release-vendor.yml) 打包驗證，均在 `${{ github.workflow }}-${{ github.ref }}` 組中使用 `cancel-in-progress: true`。不同 PR 引用和不同工作流不會相互取消。事件型別不參與分組：CI master 中的 master 推送與手動基準測試可以相互取代，e2e 的推送、定時執行和手動執行也可以在同一引用上相互取代。

[可複用 Python 執行時建置器](../../../../.github/workflows/build-exe-for-python-sdk.yml)使用 `${{ !inputs.release }}`。其 `build-single-exe-${{ github.workflow }}-${{ github.ref }}` 組與呼叫方的組保持區分，呼叫方工作流名稱將普通 CI 與釋出所屬的建置隔離。釋出所屬的建置獲得豁免，因為它們屬於一次有意發起的釋出事務。釋出、部署和中繼資料工作流保留各自的策略；本決策不會不加區分地對所有工作流應用取消。

PR 聚合使用 `${{ !cancelled() && github.event_name == 'pull_request' }}`。顯式狀態函式使其在依賴失敗或跳過後仍然求值，而非採用 GitHub 預設的僅成功條件。當工作流本身未被取消時，聚合仍會因任意依賴失敗、取消或跳過而失敗；整個工作流被取消時則抑制其已失去用途的判定。覆蓋率耗時歷史也使用 `!cancelled()`：覆蓋率失敗時仍可儲存有用的測量資料，但被取消的覆蓋率執行不上傳。Wine 的 `always()` 清理仍是必要的資源清理，而非可選記帳任務。

本決策推翻[故障切換手冊](2026-07-26-ci-failover-runbook.zh.md)、[僅 master 執行的平臺 CI](2026-09-06-master-only-platform-ci.zh.md) 和[真實 API e2e 決策](../testing/2026-06-19-real-api-e2e-ci.zh.md)中的取消豁免。這些記錄對執行器池信任與切換、平臺覆蓋和金鑰暴露仍有獨立價值。[釋出演練決策](2026-09-06-release-rehearsal-selfhosted.zh.md)仍負責執行器選擇與隔離。沒有記錄被完全取代或歸檔。

## 曾考慮的替代方案

**保留正在執行的 master 推送演練。** 原有 `${{ github.event_name != 'push' }}` 豁免優先保證週期性就緒證據：每條熱備以單門禁工作程序執行完整的未分片聚合流程，耗時可能長於 master 合併間隔。即便該策略也不保證每次演練完成。GitHub 每個組僅保留一個待執行條目，會替換中間的待執行推送；取消條件針對新觸發的執行求值，因此共享 master 組的手動基準測試仍可取消演練。當時接受了這種罕見的手動中斷，期望後續推送提供證據。豁免成本被限定為僅 master 執行的執行時檢查、Wine 和兩條演練；PR 作業仍在獨立工作流中，按精確條件匹配的迴歸檢查固定推送可達作業集合。為釋放容量給目前驗證而否決該策略，明確接受熱備因反覆被取消而無法完成。

**用作業級並行保護演練，或僅取消 PR 事件。** 作業級分組不能讓作業免於整個工作流的取消。僅針對 PR 的取消條件還會豁免手動觸發：重複派發的執行器基準測試可能佔用十二臺大型執行器長達十五分鐘，而非替換陳舊的測量。工作流級取消同時覆蓋推送和手動執行。

**保留每次合併後、每夜和打包執行。** 完成歷史執行能提供更多按提交和觸發劃分的證據，但已被取代的驗證會與最新執行競爭。這些驗證不釋出包，因此保留每次執行與保護有意發起的釋出事務並不是同一項要求。

**替換每個 `always()` 條件。** 失敗聚合與資源清理承擔不同義務。僅成功時執行的聚合可能把依賴失敗隱藏為跳過的必需檢查；移除無條件 Wine 清理則可能留下仍在執行的資源。只有已取消執行的記帳任務被抑制。

## 後果

master 快速更新可能反覆取消耗時更長的熱備演練，使其無法產出結論。運維人員使用最近一次已完成的熱備結論，並在依賴它判斷故障切換就緒狀態前核對其時間和提交；已排程、正在執行或已取消的演練都不構成就緒證據。該策略不保證每個中間提交、每夜觸發或基準測試都能完成。不同引用仍會競爭共享主機容量。

取消是由 GitHub Actions 及其執行器處理的請求，不保證立即終止或限定排隊時長。清理仍可能耗時。該策略讓已被取代的驗證可以被取消，但不承諾固定執行時長或取消延遲。

## 驗證

[工作流回歸測試](../../../../scripts/ci-workflow.spec.ts)固定工作流/引用隔離、釋出所屬建置豁免、聚合狀態條件、覆蓋率歷史取消及保留的 Wine 清理。[平臺路由迴歸測試](../../../../scripts/tests/ci-master-platforms.spec.ts)保留 master/PR 目標劃分與釋出矩陣；[釋出演練迴歸測試](../../../../scripts/tests/ci-release-selfhosted.spec.ts)在驗證取消策略的同時保留執行器准入與釋出隔離。這些設定檢查不重現 GitHub 排程或執行器停止過程。真實執行取代行為與已完成熱備證據仍由 CI 負責驗證。
