# Agent Note: 按變更生產程式碼行的歸屬調整審批權重

Status: implemented

[English](2026-09-11-production-blame-approval-weight.md) | 中文

## Problem

固定的一分評審權重無法反映評審者對拉取請求所修改程式碼的作者貢獻。目錄級歸屬可能獎勵同一資料夾中的無關程式碼，扭曲與本次評審有關的貢獻。

## Decision

[審批策略](../../../../.github/review-ownership/README.md) 按變更舊生產程式碼行的歸屬比例，以 `min(2, 1 + 4 × ownedLines / totalLines)` 調整一分批准的權重。歸屬比例為 0% 時計一分，12.5% 時計 1.5 分，25% 及以上時計兩分。分數在與兩分透過線比較前不做舍入。合併基點同時提供程式碼分類和 blame 依據，GitHub 將歸屬提交關聯到評審者帳號。無法關聯帳號的作者仍計入分母。新增行沒有原作者，不計入行數；分母為空時不提升權重。

釋出器在依賴安裝和評估前將頭提交標記為待定，避免歷史拉取中斷後保留此前的成功狀態。它使用即時 base 分支和被評審的精確 head，讀取完整 Git 歷史，不檢出 PR 程式碼；基礎分數或阻塞評審已決定結果時跳過歸屬計算。維護中的詞法分析器區分儲存庫各原始碼語言中的註解與程式碼。作者查詢按提交批次執行，所有評審者共用一次統計。現有的[待定狀態語義](2026-09-09-blocked-weighted-approvals-remain-pending.zh.md)和[評審事件驗證](2026-09-10-approval-review-workflow-identity.zh.md)仍是獨立要求。

## Alternatives considered

**硬閾值。** 線性權重區分 25% 以下的部分歸屬。25% 封頂讓負責四分之一變更舊程式碼的評審者滿足兩分要求；更多歸屬不會使其票數超過該要求。

**目錄加權歸屬。** 變更目錄中其他程式碼的歸屬不能證明待評審程式碼行的歸屬。

**將新增行計入分母。** 這些行沒有合併基點上的作者，會稀釋既有程式碼的作者貢獻訊號。

**將作者姓名或電子郵件字串與評審者登入名匹配。** 顯示名稱不是帳號標識，一個帳號也可能使用多個電子郵件提交程式碼。GitHub 的提交作者帳號關聯提供該對映。

## Consequences

冷啟動的主要開銷是拉取歷史。選擇合併基點前必須具備完整歷史：淺歷史中看似共同祖先的提交可能使部分變更被排除出分母，因此不能據此安全判定無需 blame。2026-09-11，在本機測量 PR #3969 和 #3977，得到 4 和 14 個檔案中的 73 和 535 行舊生產程式碼。三次本地執行分別耗時 0.31–0.32 秒和 0.87–0.93 秒；每個 PR 的一次批次作者查詢額外耗時約一秒。同一主機上，全新單分支裸克隆 master 耗時 47 秒。這些是本機觀測值，不是 CI 耗時保證。

Blame 衡量最後修改者歸屬，不代表評審品質或語義上的專業能力。生產程式碼分類器排除未支援的原始碼位置和副檔名；在其清單之外新增交付原始碼時，必須擴充功能分類器。詞法分類不判斷程式碼是否在語義上可執行。評估錯誤保留錯誤狀態，不靜默授予或取消加權。
