# Agent Note: PR 範圍內的批准委託

Status: implemented

[English](2026-09-15-pr-approval-delegation.md) | 中文

## Problem

評審人可能信任另一位評審人來決定某個 PR（Pull Request），同時保留自己的儲存庫角色和程式碼歸屬對應的分數。如果同時計入原始批准和轉交的分數，就會放大該評審人的貢獻。

## Decision

[批准策略](../../../../.github/review-ownership/README.md#delegating-points) 接受 PR 普通評論中的 `/delegate @username`。每位符合資格的委託人，其分數跟隨指定受託人的有效批准，按委託人的權重計入一次。委託僅適用於目前 PR，且雙方都必須具有寫權限，不能是 PR 作者。收到的分數不能繼續轉交。命令會透過 GitHub 撤銷委託人原有的批准和變更請求。其他有效阻塞評審仍遵循[阻塞評審策略](2026-09-09-blocked-weighted-approvals-remain-pending.zh.md)。

按評論建立順序，最新、仍存在且符合資格的命令決定受託人。編輯過的命令要求最近編輯者與作者的不可變帳戶 ID 一致；其他有寫權限的人不能透過編輯評論轉交或取消作者的分數。委託給自己或隨後提交評審會恢復使用委託人本人的評審決定。僅評論的評審也會收回分數；尚未提交的評審不會。時間戳相同時以評審為準，隨後撤銷評審也不會重新啟用委託。評審之後的新命令可以再次委託。編輯和刪除會根據目前評論重算，包括恢復較早的命令。可信釋出器按 `/delegate` 篩選普通評論變更，解析即時且未關閉的 PR 頭提交，並將評論及編輯者身份作為 API 資料讀取。每次評估都會處理所有有效且符合資格的命令，撤銷舊的決定性評審，並請求尚未批准、尚未收到請求的受託人進行評審。這覆蓋了排隊事件被替換以及草稿轉為 ready 的情況；其他 requested reviewers 保持不變。撤銷後重新整理分數；撤銷保留舊提交時間戳，不會取消委託。移除受託人的批准只會移除計入的分數，委託仍然保留，供其下次批准使用。草稿 PR 不撤銷或請求評審。撤銷失敗會使評估失敗；請求失敗單獨記錄日誌，並在後續評估中重試。已關閉或合併的 PR 會在寫入狀態和安裝依賴之前跳過。獨立的[評審工作流驗證](2026-09-10-approval-review-workflow-identity.zh.md) 保持不變。

## Alternatives considered

**把委託直接視為批准。** 這會在選定的評審人作出決定前批准 PR。

**增加委託人的分數，同時保留其直接貢獻。** 這會將同一帳戶計算兩次，削弱批准閾值。

**沿委託鏈繼續轉交收到的分數。** 這會允許受託人將他人的分數轉給未經原委託人指定的帳戶。

**只在分數中忽略委託人的舊決定。** GitHub 會保留原有批准或阻塞評審。撤銷舊評審使原生評審狀態與委託一致。

**委託人提交評審後仍保留委託。** 已提交的評審表達了委託人本人的決定，繼續使用他人的批准會忽略該決定。

**在評論之外單獨持久化命令。** 這需要額外儲存，並協調編輯與刪除；目前評論已經提供可檢查的記錄。

## Consequences

委託保留委託人的[生產程式碼歸屬權重](2026-09-11-production-blame-approval-weight.zh.md)和獨立的作者信用規則。每次評估都需要完整評論與編輯者歷史和參與者的目前權限；歷史缺失會使評估失敗。編輯較早命令不會改變其優先順序，刪除較新命令可能重新啟用較早命令。策略測試覆蓋分數守恆、評審觸發的收回、舊評審撤銷、權限過濾、評審請求、阻塞評審、分頁和失敗狀態釋出；工作流測試約束可信執行及每個 PR 共享的並行分組。過期評審和最新推送要求仍由 GitHub 原生規則負責。
