# Agent Note：Desktop 釋出版本改為命令參數，不再改寫清單

Status: implemented

[English](2026-09-21-desktop-build-version-as-input.md) | 中文

## 問題

[從完整 dsh 版本派生 Desktop 測試版本](2026-09-16-desktop-release-version-derivation.zh.md)確定了測試建置叫什麼，但沒有確定這個名字存在哪裡。釋出一次測試建置要先執行 `release:dsh`，把版本寫進所有釋出家族清單和鎖檔案——295 個檔案——因為打包、更新 feed 和上傳驗證都各自從工作區讀取版本。這些改動從不提交，所以每次測試建置都會留下髒工作區直到有人還原，而還原後的工作區又不再描述已經發布出去的產物。`<base>.YYYYMMDD.index` 裡的序號同樣靠人對著釋出記錄和 bucket 挑選，而這是腳本可以完成的查詢。

另有兩件事在建置之後無法還原。交給同事或推到測試 feed 的建置沒有任何標籤可查，它來自的建置樹也不是工作區，因此沒有任何東西把安裝檔和原始碼連起來。production 釋出同樣只在 bucket 裡留下痕跡。

## 決策

建置釋出的版本是一個參數。`--build-version` 指定它，`--build-version auto` 給出當天的下一個序號，該值經 `extraMetadata` 進入 electron-builder，並作為同一個輸入貫穿更新 feed 與上傳驗證。清單保留產品版本，因此任何打包執行都不修改被跟蹤的檔案。

[Desktop 釋出規則](../../../../apps/desktop/README.zh.md#release-versions)中的版本規則不變：production 釋出 dsh 基礎版本，預釋出基礎版本追加 `.YYYYMMDD.index`，穩定基礎版本追加 `-test.YYYYMMDD.index`。驗證直接使用 `semver`，因為 `electron-updater` 就是用 `semver.gt` 把 feed 版本與已安裝的 `app.getVersion()` 比較。

本決策取代上述 Note 的兩條要求。釋出家族清單不再被改寫；外殼版本也不再等於內建執行時版本：內建執行時就是產品版本的 dsh 包，`verifyDesktopRuntime` 接收準備該執行時樹的一方寫入的版本，而安裝升級驗證會為自己的材料改寫這個版本。應用本來就把兩者分別上報給強制更新策略。

所有產物的清單都記錄 `dshBuildCommit` 與 `dshBuildDirty`。production 上傳在產物公開後把打包所用 commit 打成 `desktop-v<版本>` 標籤，失敗時只列印需要手工執行的命令，而不讓已完成的上傳變成失敗；來自有改動工作區的建置不打標籤。test 與本地建置有意不留標籤，因為為每個測試建置打標籤會淹沒真正的釋出。

上傳從打包寫下的完成記錄中讀取釋出版本，而不是從變數讀取，因此[釋出欄位仍然只來自目標檔案](../../../../apps/desktop/README.zh.md#release-versions)。

## 考慮過的替代方案

**繼續改寫清單，事後還原。** 髒工作區本身就是缺陷，而還原會與任何同時讀取工作區的操作競爭，也會讓已釋出產物所描述的狀態在儲存庫中不復存在。

**只在臨時副本里改寫打包執行時的清單。** 內建 dsh 會因此宣稱一個 npm 上不存在的版本，副本還得與鎖檔案保持一致，沒有任何收益。

**不要參數，全部自動編號。** 操作者需要在打包前與使用者確認版本。自動編號以 `auto` 提供並列印所選版本，而不是作為預設行為。

**為每個建置打標籤。** 測試 feed 持續接收建置，逐個打標籤會讓 `desktop-v*` 無法再用於查詢釋出。改由產物自身攜帶 commit。

## 影響

打包執行不再改動儲存庫，因此建置產物的程式碼樹就是標籤或記錄的 commit 所指的那棵樹。`auto` 會存取目標 bucket，`--check` 下同樣如此；未設定 bucket 或列舉未能在期限內完成時退回到本地輸出目錄，不完整的列舉結果會被丟棄，以免複用序號覆蓋已釋出的安裝檔。production 上傳現在會寫入儲存庫，而早先的釋出自動化刻意避免這一點；這次寫入只是一個標籤，由操作者自己的命令在上傳成功後執行。
