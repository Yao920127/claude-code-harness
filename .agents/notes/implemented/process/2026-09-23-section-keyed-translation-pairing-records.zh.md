# Agent Note: 按分節記錄翻譯配對

Status: implemented

[English](2026-09-23-section-keyed-translation-pairing-records.md) | 中文

## Problem

一致性記錄過去儲存每個語言檔案完整的 blob hash。對配對的任何修改都會改動這兩行，因此兩個分支即使修改同一配對的不同部分、Git 也能幹淨合併兩個 Markdown 檔案，記錄仍然必然衝突。受影響最大的是 `docs/config-catalog.md`、`docs/module-graph.md` 和 `docs/event-producer-consumer.md` 等生成參考文件：大多數涉及包、設定或事件的 PR 都會重新生成其中之一，而每次重新生成還要求手工複製中文更新並寫入新記錄。worktree 本地的合併驅動可以組合這類記錄，但 GitHub 的可合併性檢查從不執行它，因此在有人於本地合併基線分支並推送之前，PR 仍顯示衝突。

## Decision

`foo.i18n.yaml` 為每個含有計入 hash 內容的標題分節儲存一個條目。`verify-translation-pairing` 計算這些條目；`scripts/translation-pairing-record.ts` 負責該格式。

- 兩側都在每個標題處切分。英文件案的第 `i` 個分節對應中文件案的第 `i` 個分節；標題數量不同屬於結構錯誤，無法記錄。
- 鍵是英文標題 slug 組成的路徑，例如 `/plugin-config-catalog/loadable-plugins-with-no-config`。第一個標題之前的文字為 `/`，重複路徑依次加 `~2`、`~3` 等字尾。鍵的計數覆蓋每個分節（包括沒有條目的分節），因此鍵只取決於標題。
- 每側的 hash 覆蓋該分節在配對文件連結在地化後的頂層塊，只排除圍欄程式碼塊和生成區域。這兩類內容正是配對門禁已要求兩側一致的內容；其他內容即使碰巧相同也計入 hash。條目儲存每側計入 hash 的塊的 SHA-256 前 16 位十六進位制值。沒有計入 hash 的塊的分節沒有條目。
- 每個條目佔三行：一行不變的鍵，後跟 `en:` 與 `zh:` 兩行 hash。鍵行把相鄰條目隔開，因此 Git 文字合併把對相鄰條目的修改視為不同的 hunk。

因此，只有兩個分支都修改了同一分節中計入 hash 的內容時，記錄才會衝突。

生成器把生成資料放在生成區域中，並把每個區域寫入兩種語言的頁面，因此重新生成既不改變記錄，也不改變中文說明文字。`gen-config-catalog` 寫出兩種語言和記錄，每個包一個區域，每個包表格一個區域；區域內的標籤是程式碼識別符號 `inject`、`refs`、`source` 和 `class`，由已翻譯的介紹段落解釋。`gen-module-graph` 把表格放在區域中，列頭使用識別符號。`gen-doc-graphs` 把事件矩陣的表格寫入人工撰寫的中文頁面，`gen-cordis-catalog` 已經以同樣方式處理子系統區域。

`gen-translation-brief` 從配對的提交中找到內容能生成已提交記錄的最新提交，並從中還原上次確認的文字。記錄不再指向 Git blob，`--write` 也不再儲存快照物件或 ref。

已歸檔的 Agent Note 保留其已封存的整檔案記錄；該格式由 `verify-archived-agent-notes` 負責。

## Alternatives considered

**保留整檔案 hash 和合並驅動。** 驅動只在已安裝它的本地 worktree 中解決衝突。GitHub 仍把 PR 報告為衝突，未安裝執行時的原始合併會停止，而驅動、解決命令、安裝腳本整合及其測試共約 1,400 行需要維護的程式碼。

**按頂層塊而非按標題分節記錄條目。** 長分節內的誤報衝突更少，但記錄會增長到約等於文件的塊數。按位置編號的塊鍵還會在每次插入時重新編號，自身又製造衝突。

**按位置編號的分節鍵（`h2[3]`）。** 插入一個分節會讓之後的每個鍵重新編號，並改動之後的每一行記錄，重新造成這種格式要消除的衝突。標題 slug 鍵只在該標題的英文文字改變時才改變。

**透過 Actions 或 GitHub App 在 GitHub 上解決。** 託管自動化需要憑證、並行控制以及改寫 PR 分支的權限。Git 預設文字合併即可組合的記錄不需要這些。

**對整個分節（包括程式碼塊和區域）取 hash。** 每次重新生成的行或程式碼塊仍會改動一行記錄，因此生成參考文件最大的分節仍會衝突。

**排除兩側逐位元組相同的任何塊。** 這同樣能讓生成的行不進入記錄，但它隱式地判定哪些內容不需要翻譯：原樣複製到中文件案而未翻譯的英文段落也會被排除，之後對它的修改也不再改變記錄。程式碼塊和生成區域是現有門禁已檢查的、明確宣告的共享內容。

## Consequences

對不同分節的修改，以及重新生成的區域和程式碼塊，無需本地工具即可合併，在 GitHub 上也是如此。重放 2026-08-20 至 2026-09-23 期間可從 `master` 到達的合併提交可以看到它在真實歷史上的效果：見[實測效果](#measured-effect)。

同一分節的衝突需要先解決 Markdown 衝突，再重新執行 `verify-translation-pairing --write <pair>`；沒有命令會自動完成。生成區域的中文讀者看到的是程式碼識別符號和英文表頭，而不是譯文標籤。為 brief 還原上次確認的文字，要求已確認的配對已經提交。

## Measured effect

重放覆蓋了 2026-08-20 至 2026-09-23 期間可從 `master` 到達的 2016 個雙父合併提交，其中大多數是 PR 分支向前合併基線分支。對兩個父提交都修改了其記錄的每個活躍配對，它分別對舊記錄、根據同一提交內容計算出的按分節記錄，以及兩個 Markdown 檔案執行 Git 預設文字合併。某個提交中標題未對齊而無法計算的記錄計為衝突。舊格式在 850 個合併提交中的 2950 次配對合並裡衝突；按分節格式在 595 個合併提交中的 1586 次配對合並裡衝突，按配對計減少 46%。Markdown 檔案本身在 338 個合併提交中的 926 次配對合並裡衝突，這部分任何記錄格式都無法避免。只有記錄衝突的合併提交從 512 個降到 257 個（減少 50%）。

重放使用各提交當時的內容，那時生成器還未把資料放進區域，因此 `docs/module-graph.md`（277 次）、`docs/event-producer-consumer.md`（220 次）和 `docs/config-catalog.md`（110 次）仍因其中的生成資料衝突。資料放進區域後，它們的記錄只在說明文字改變時才變；在同一重放中排除其生成行後，前兩者分別剩 0 次和 14 次衝突。用這一結果替換這三個頁面後，預計約 990 次配對沖突，比舊格式少約 66%；這是估算，不是重放實測。
