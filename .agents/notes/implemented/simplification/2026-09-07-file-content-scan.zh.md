# Agent Note: 檔案內容掃描不為每個陣列建立回呼

Status: implemented

[English](2026-09-07-file-content-scan.md) | 中文

## Problem

每次模型分發都檢查完整訊息內容中的檔案，包括 tool-role 結果內容。請求歷史 CPU profile 將 23.540 ms 自身時間歸於 `contentHasFile`，將 5.584 ms 歸於其回呼。即使[迴圈自有凍結證據](2026-09-06-agent-request-freeze-evidence.zh.md)消除了重複請求凍結，這次遍歷仍然必需。兩次抽樣的 master 修訂與實測的 V3 整合修訂 的 LLM 熱點原始碼完全相同；這些觀察不能證明 PR 因果關係。

## Decision

[`contentHasFile`](../../../../packages/llm/llm/src/content.ts) 使用直接迭代，替代遞迴的 `Array.some` 回呼。它保留提前退出、tool-role 結果遍歷，以及其他塊型別返回 false 的行為。它不儲存身份、驗證結果或凍結證明。圖片檢測、檔案投影和請求建置保持既有行為。[請求凍結證據](2026-09-06-agent-request-freeze-evidence.zh.md)擁有請求歷史預算。

## Measurement evidence

Apple M4 Pro、Node 24.19.0：九組交替原始/候選配對在全新的普通 Node 程序中執行不變的[請求歷史 worker](../../../../benchmarks/agent-continuation/agent-continuation.worker.ts)。每個程序接收同一個原生 V3 種子的副本。只有建置後的 LLM 入口變化；每個樣本均完成 40 次請求、零次即時工具呼叫與 13,925 個事件。以下全部總耗時單位為毫秒，按配對順序排列。

| 變體 | 原始總耗時 | 中位數 |
|---|---|---:|
| 原始 | 61.772167, 66.480917, 63.590042, 62.250333, 63.804875, 62.504208, 61.887958, 61.062959, 67.120125 | 62.504208 |
| 直接迭代 | 53.655375, 56.223416, 57.078125, 54.559250, 54.271459, 55.288917, 55.400416, 56.191916, 54.877041 | 55.288917 |

中位數改善 11.54%；全部九組均改善，幅度為 4.871–12.243 ms。使用者 CPU 中位數為 82.019/76.150 ms。獨立的五組配對掃描探針使用相同的合成歷史：5,601 條凍結訊息、13,600 個塊和 8,801 個內容陣列，掃描 40 次。原始總耗時為 17.188584, 17.944000, 16.869458, 17.437750, 17.459708；直接迭代總耗時為 8.726333, 8.373000, 8.851750, 8.479167, 9.074083。這些本地測量證明實作改善，不代表託管 CI 透過或新的校準。

## Alternatives considered

弱引用的否定結果快取需要證明每個相關後代均不可變；淺凍結根物件並不足夠。直接迭代提供實測收益，無需引入此類所有權或失效問題。本實驗沒有提供最佳化圖片遍歷或系統提示詞投影的證據，因此它們不在此次變更範圍內。

## Consequences

掃描仍與存取塊數呈線性關係，每次呼叫都重新讀取可變的巢狀內容。[內容測試](../../../../packages/llm/llm/tests/content.spec.ts)覆蓋空陣列、凍結陣列、巢狀陣列與後續變更的陣列；服務測試保留檔案 handle 投影，請求凍結、重建與恢復測試保留原生歷史語義。模型可見文字與 Session 格式均不改變。凍結證據與[後端基線](../testing/2026-09-06-backend-continuation-performance.zh.md)記錄仍各自擁有獨立決策；兩者均未被取代。
