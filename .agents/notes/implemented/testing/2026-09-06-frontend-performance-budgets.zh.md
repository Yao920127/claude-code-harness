# Agent Note: 前端長 Session 效能預算

Status: implemented

[English](2026-09-06-frontend-performance-budgets.md) | 中文

## 問題

Node 對話摺疊很快，並不能證明瀏覽器能繪製長對話或在流式回覆期間保持回應。活躍重連還會重建與已結算曆史不同的表示：緊湊字首變成公開的逐 chunk Client 條目。[Session 效能策略](2026-09-04-session-open-performance-gate.zh.md)提供隔離的 CI job，但不測量這些使用者路徑。

## 決策

現有序列基準清單包含兩個前端所有者：[活躍重連](../../../../benchmarks/active-stream-reconnect/README.zh.md)和[瀏覽器工作流](../../../../benchmarks/long-session-browser/README.zh.md)。瀏覽器工作流在一個順序情境中組合冷開啟、更早分頁導航、首次啟用 Trajectory、返回 Chat，以及伴隨真實鍵盤輸入的有節奏回覆。這些是同一工作流的測量終點，而不是相互獨立的冷情境。已結算對話摺疊基準保持不變。

`build:bench` 保留僅 Node 的 library 與 worker 建置。`test:bench` 額外建置 Web shell 後再執行所有案例；必需的基準 CI job 遵循[標準託管執行器決策](2026-09-06-standard-hosted-benchmark-runner.zh.md)，在該託管執行器上無條件安裝 Chromium 及其 Linux 依賴，並啟用現有門禁詳細輸出，使成功案例的原始樣本可用於校準。瀏覽器案例複用產品組合的 Web scaffold，使用私有臨時目錄和原子分配的迴環埠。只有不確定的模型被合成重放替代。scaffold Host 透過現有 Vitest 原始碼解析器執行；被測 Client 渲染在全新 Chromium 程序中執行建置後的 bundle。因此瀏覽器壁鐘時間包含測試 Host、傳輸、Playwright 可互動性等待及渲染，不代表釋出版 Host 程序。

瀏覽器輸入包含 240 個已關閉輪次、40 個工具結果和 20 個程式碼塊，以及混合語言正文和推理。歷史 Assistant 記錄攜帶匹配的緊湊 stream，透過生產 accumulator 按 12 字元推理/文字 delta 和 8 字元工具參數 delta 建置；空 stream 會遺漏儲存與傳輸負載成本。從觀察到的初始 25 輪視窗開始，九次更早分頁操作讀完該輸入；就緒探針跟蹤已掛載輪次增長，不複製分頁演算法。每個樣本使用全新 scaffold 和瀏覽器。環境準備、資料播種、瀏覽器啟動、初始 shell 載入及側欄展開不計入開啟時間。開啟測量在對話可用且輸入框可編輯時結束；分頁與導航測量在目標 DOM 狀態出現時結束。兩次動畫幀包含一次渲染機會，不代表硬體顯示或保證每個螢幕外節點都已繪製。

續接以 16 ms 重放間隔傳送 120 個文字 delta。輸入觀察器在從已聚焦輸入框按 Enter 提交前安裝；鍵入保留焦點，不執行滑鼠重新聚焦，也不單獨等待輸入前動畫幀。首段/最終標記查詢在動畫幀上取樣最新 Assistant step 內的可見文字，避免選擇器重試退避。隱藏文字和較早步驟中的標記均不能滿足觀察條件。首次觀察在瀏覽器內記錄回覆標記與焦點；診斷在鍵入後取回，避免增加輸入前的通訊往返。診斷還記錄首個實際輸入事件的瀏覽器時鐘時間戳與焦點。重放從不等待輸入；回應阻塞仍可能導致重疊失敗。同步輸入證據讀取同一個受限回覆。全歷史文字與無障礙查詢會向測量區間加入觀察器 CPU 和垃圾回收成本，因此減少此類觀察工作屬於基準修正，而非產品最佳化。它記錄 Enter 提交到首段可見回覆的時間、首個實際輸入事件觀察到首段回覆且完成標記尚未出現時的真實草稿鍵入、直到持久化結算並渲染新 turn-tail 的完整回覆壁鐘時間，以及 Chromium 主執行緒任務時間。完整壁鐘預算在縮放後的額外開銷額度上加固定的 1984 ms 腳本節奏；輸入和完成均有獨立執行的預算。強制 GC 後的瀏覽器 heap 和 DOM 數量仍僅供診斷，因為單個終點不能證明洩漏。

重連使用三個全新編譯後的純 Node 子程序。各程序在計時 `ClientAssistantStream.replace()` 前建立包含不同時間戳、兩條緊湊記錄和 100,000 個 delta 的推理字首。在基線前執行 GC，並在結果仍可達時於替換後再次 GC；替換時間不含兩次回收。報告在回收後消費結果，並檢查下一個稠密序號的即時 frame 仍被接受。這測量重建，不測量傳輸、渲染或完整重連工作流。

## 校準

在 arm64 參考機器、Node 24.19、Chromium 149.0.7827.55 和PR #3537 合併結果 上，三個樣本的中位數建立下表基線。完整工作流 smoke 後執行一次隔離重複測量。每個瀏覽器樣本報告原始終點資料和每一頁；分頁判定使用各樣本最大值的中位數。重連報告全部子程序測量。下列歷史參考表使用 8 ms 重放節奏，首段回覆計時包含兩幀等待。標準託管開啟、分頁、Trajectory 和重連預期在下文單獨記錄；其他原始碼參考常數保留這些額度。受限觀察器的分頁中位數 261.60 ms 超過 260 ms 參考額度，但仍低於 650 ms CI 限制；共享的 2× 時間倍率和 1.25× 方差餘量產生 CI 限制。記憶體僅使用方差餘量。共享倍率源自 Node CI 校準。下述兩次實際 x64 瀏覽器執行在基準程式碼不變的情況下均透過固定預算；這提供這些 runner 的重複執行證據，而非普遍適用的瀏覽器速度比。

| 終點 | 實測中位數 | 參考額度 | 歷史 CI 限制 |
|---|---:|---:|---:|
| 瀏覽器開啟 | 184.62 ms | 200 ms | 500 ms |
| 最慢更早分頁 | 261.60 ms | 260 ms | 650 ms |
| 首次 Trajectory | 136.46 ms | 160 ms | 400 ms |
| 首段回覆 | 373.72 ms | 1100 ms | 2750 ms |
| 流式主執行緒任務 | 1053.87 ms | 1800 ms | 4500 ms |
| 草稿鍵入 | 487.35 ms | 500 ms | 1250 ms |
| 完整回覆 | 1366.36 ms | 1000 ms 額外開銷 + 992 ms 節奏 | 3492 ms |

| 重連保留 heap | 23.03 MiB | 24 MiB | 30 MiB |

三個隔離樣本中的草稿鍵入時間為 124.97–504.96 ms；參考額度保持 500 ms，縮放後的 CI 限制覆蓋觀察到的波動；中位數不是單次按鍵上限。預算不能透過環境變數覆蓋。臨時零額度覆蓋每條拒絕路徑；這些負向對照證明預算執行，而非最佳化或歷史迴歸。另一項對照在鍵入前等待最終回覆標記，實際輸入重疊斷言因此失敗。緊湊合成 JSONL 為 3,262,577 位元組；三個修正樣本均報告重疊的真實輸入事件，並在第 241 個 turn-tail 渲染後結束。

### 標準託管預期與輸入排程

執行 34033336246，job 101487216170 在雙 CPU 標準託管 Ubuntu 上記錄重連替換時間 46.574411、46.067910 和 44.193704 ms，保留 heap 為 23.028 MiB。該終點的預期為 50 ms；現有 1.25× 餘量產生向上取整後的 63 ms 上限。30 MiB 記憶體預算及共享機器倍率不變。瀏覽器開啟記錄 681.276514 和 541.051233 ms，第三個樣本因輸入重疊失敗而中止；兩個值均超過歷史 500 ms 上限。下文的託管開啟重複測量決定其預期與上限。確定性對照透過這些記錄值，並使用與測量判定相同的斷言拒絕超過新上限的值。仍需完整的託管重複執行判定；這兩個開啟值不是三樣本中位數。

臨時使用 3× Chromium CPU 降速的本地診斷復現重疊失敗：首個標記在 1321 ms 可見，兩次動畫幀在 1370 ms 結束，輸入框點選在 1660 ms 完成；實際輸入是真實事件，但已看到 DONE。移除幀等待並在傳送前安裝觀察器後，一次執行仍在 1415 ms 才看到首個標記，點選在 1726 ms 完成，晚於原先 992 ms 的腳本流。固定 16 ms 節奏保留相同的 120 個 delta 和負載，為該工作負載提供 1984 ms 腳本節奏。完整壁鐘額度僅改變該節奏項（4484 ms）；輸入、首段回覆及主執行緒額外開銷額度不變。在相同診斷降速下，三個 16 ms 樣本在 1307/1479/1599 ms 達到首段可見狀態，並接受 DONE 之前的真實輸入；其 DONE 之後的對照拒絕該輸入。該診斷不是 CPU 比率校準。每個測量樣本仍要求真實輸入發生時 FIRST 存在且 DONE 不存在；測量後在 DONE 之後傳送的真實按鍵必須無法透過同一個斷言。Host 結算和第 241 個已渲染 turn-tail 仍是完成證據。

執行 34034524861，job 101490135303 記錄三個完整瀏覽器樣本，均具有真實輸入重疊，並透過 DONE 之後的拒絕對照。最慢分頁樣本為 843.941625/672.834329/684.461818 ms（中位數 684.461818）；首次 Trajectory 樣本為 605.788061/367.754027/485.931656 ms（中位數 485.931656）。兩者的終點專屬託管預期分別為 700 和 500 ms，相同的 1.25× 餘量產生 875 和 625 ms 上限。記錄中位數對照拒絕歷史 650/400 ms 上限，接受這些託管上限，並透過測量判定所用斷言拒絕超過各上限一毫秒的值。開啟、首段回覆、主執行緒任務、輸入及完整壁鐘的中位數為 713.910/1486.206/2806.415/947.398/2986.983 ms；僅開啟上限根據下文的重複測量重新校準。該執行提供校準資料，不代表基準判定透過；仍需完整的託管重複執行。

執行 34036109842，job 101494445658 記錄開啟樣本 875.306861/1083.683529/814.700998 ms，中位數為 875.306861 ms，前一次託管執行的中位數為 713.909727 ms。該終點的預期為 900 ms，向上取整較大的重複測量中位數，而非向 875 ms 上限增加微量餘量；不變的 1.25× 餘量產生 1125 ms 上限。同一個強制斷言接受記錄中位數，在歷史 500 和 875 ms 上限下均拒絕它，並在目前上限下拒絕合成的 1126 ms 值。三個樣本均保留真實輸入重疊與 DONE 之後的拒絕；其他所有前端中位數均在不變的上限內。此校準不代表 CI 執行透過。

受控的滑鼠重新聚焦延遲等待真實 DONE 標記，不暫停重放：滑鼠路徑拒絕 DONE 之後的真實輸入，而 Enter 提交與純鍵盤草稿輸入在相同對照下透過全部三個樣本。該延遲僅用於診斷。在 arm64 Node 24.19.0 / Chromium 149.0.7827.55 上，不含延遲的三個樣本報告首段回覆/輸入/完整壁鐘中位數 288.823/418.868/2567.328 ms，每個樣本均滿足實際重疊並拒絕 DONE 之後的輸入。這證明移除了滑鼠操作排程依賴，並不證明某次託管停頓的原因；全部工作負載常數和預算保持固定。

目前 Trajectory 驗收上限為 650 ms，由 520 ms 目標與共享的 1.25× 餘量表示。執行 35095609422 的首次執行與重試分別記錄中位數 666.651723 ms 和 630.843184 ms。相較於原先的 625 ms 上限，這次明確的 4% 放寬接受重試中位數，但仍拒絕首次中位數；這是預算決策，不代表測得產品提速。記錄的重試樣本覆蓋新增的接受區間，同一個判定斷言拒絕 651 ms。其他終點預算與工作負載參數保持不變。

## 考慮過的替代方案

**用 Node 摺疊作為繪製證據。** 拒絕，因為它不執行 DOM 修改、佈局或瀏覽器排程。聚焦重連案例同樣不聲稱 GUI 提速。

**把整個手動瀏覽器診斷提升到 CI。** 拒絕，因為其 1,000 Session 側欄和 100 輪 soak 覆蓋更廣的工作負載。受限的必需案例複用其產品 scaffold 和測量方式，不匯入測試模組，也不改變手動清單。

**合併活躍重連 chunk。** 不能作為基準捷徑：Client 條目向對話定義公開每個成員的順序和時間戳。基準保留該生產行為；減少保留條目需要獨立的語義設計，而非複製產品演算法或使用合成近似。

**每次流式標記查詢都搜尋全部已載入歷史。** 拒絕，因為 Playwright 把文字與無障礙掃描注入同一個被測 CPU 的渲染程序。將查詢限定在輸入框和最新 Assistant 中，可保留可見完成檢查，同時避免觀察器成本隨已載入歷史增長。

**只測量流式 CPU。** 拒絕，因為傳輸停頓和最終結算延遲可能不增加主執行緒 CPU。獨立的輸入、首段回覆和完整壁鐘預算覆蓋這些等待。

## 影響

基準層不改變產品實作或使用者可見行為。它在現有隔離 CI lane 中增加約十五秒的本地瀏覽器與重連執行，以及 Web 建置和瀏覽器安裝成本。全新瀏覽器丟棄此前的快取，但每個工作流刻意在續接期間保留自身已載入歷史和曾啟用的 Trajectory。

基線可獨立合併並保護現有效能；最佳化層只有在重複測量與聚焦語義測試支援下才收緊預算。它不覆蓋側欄數量級、數小時 soak、GPU 顯示、真實模型延遲、釋出版 Host 啟動或重連渲染。[Web 瀏覽器車道](2026-07-24-web-gui-browser-e2e-lane.zh.md)保留獨立的無閾值手動診斷與功能瀏覽器測試；經校準的必需測量由本基準車道負責。現有 Session 效能記錄保持活躍，因為它擁有 Node 校準和持久化理由；本記錄擴充功能而不替代它。
