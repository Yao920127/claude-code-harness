# Agent Note: 必需 benchmark 使用標準託管執行器

Status: implemented

[English](2026-09-06-standard-hosted-benchmark-runner.md) | 中文

## 問題

壁鐘效能檢查需要獨立執行的 lane 和一致的執行器類別。透過企業 Linux 故障轉移開關路由這些檢查，會讓測量取決於大型託管執行器或共享自託管虛擬機器，同時佔用並行正確性檢查所需的容量。

## 決定

[ci.yml](../../../../.github/workflows/ci.yml) 中的必需 benchmark job 使用標準 GitHub 託管 `ubuntu-24.04` 執行器，不受 Linux 故障轉移影響。它始終嘗試恢復 pnpm 儲存快取，並保留獨立的 benchmark lane。整個 job 的超時為 15 分鐘，覆蓋準備、安裝、建置和測量。這限制的是基礎設施執行時間，而非單項效能斷言。

[Session 效能決策](2026-09-04-session-open-performance-gate.zh.md) 繼續擁有工作負載、時間和記憶體預算、worker 隔離及校準。僅目前 generation `open` 使用端點專屬的 50 ms 標準執行器預期值，乘以既有 1.25 倍餘量後得到 63 ms 上限。其他效能預算以及 worker、測試和掛鉤的截止時間均保持不變。步驟級 `DSH_GATE_VERBOSE=1` 使成功執行的原始測量保留在 Actions 日誌中。硬體比較工作流保留有意設定的不同執行器規格。

## 考慮過的替代方案

- 企業或共享自託管路由保留更多建置容量，但使測量環境受無關故障轉移操作影響。
- 沒有端點測量就提高效能閾值，會混淆有界 CI 執行與退化容許量。閾值調整需要實測校準及正反例。

## 後果

標準執行器以並行建置容量換取固定測量類別，不移除必需判定。快取未命中和執行器波動仍會影響總耗時。每次更換執行器都需要實際託管 benchmark 執行，才能認定 job 超時經過驗證；本地工作流斷言無法單獨證明執行耗時。

所屬[工作流測試](../../../../scripts/ci-workflow.spec.ts) 固定執行器路由、無條件快取恢復、必需狀態及 job 超時。反例驗證拒絕故障轉移路由、快取條件和原來的 30 分鐘 job 上限。
