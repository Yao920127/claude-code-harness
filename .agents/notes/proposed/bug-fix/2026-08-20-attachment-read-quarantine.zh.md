# Agent Note: 隔離無法讀取的歷史附件

Status: proposed

[English](2026-08-20-attachment-read-quarantine.md) | 中文

## 問題

已接納的 `ImageAttachmentRef` 會留在持久歷史中，因此在被壓縮替換前都會參與之後的每次請求。引用物件丟失、完整性驗證失敗或無法讀取時，`AttachmentStore.readImage()` 會返回 `ATTACHMENT_NOT_FOUND`、`ATTACHMENT_CORRUPT` 或 `ATTACHMENT_READ_FAILED`。未變化的歷史隨後會讓之後每次模型請求在同一物件上失敗，使工作階段無法繼續，即使其餘訊息仍可使用。這是[可重建請求](../../implemented/architecture/2026-07-05-reconstructable-requests.zh.md)保留為明確失敗的物件不可用情況。

## 提案

由工作階段支撐的圖片請求投影在分派給提供者之前記錄無法讀取的引用。`ATTACHMENT_NOT_FOUND` 和 `ATTACHMENT_CORRUPT` 立即追加 `attachment/quarantine`；`ATTACHMENT_READ_FAILED` 先執行一次服從取消訊號的讀取重試，重試仍失敗時追加同一事件並標記為可重試原因。取消和未分類失敗不會隔離資料。

隔離事件標識附件和失敗類別。投影把每張已隔離圖片替換為確定性文字，包含可用時的顯示名稱、附件 ID 字首和失敗類別。之後的請求從日誌派生相同替換結果，並跳過該引用的 `readImage()`，原始圖片塊仍留在僅追加歷史中。請求發現並記錄隔離後，會在呼叫提供者前重新投影，因此讀取失敗不會成為終止性的模型請求嘗試。

顯式恢復會呼叫 `readImage()`，且僅在內容摘要和中繼資料驗證成功後追加 `attachment/recovered`。投影隨後恢復原始圖片引用。系統絕不會自動覆蓋丟失或損壞的位元組，也不允許未經驗證就清除隔離。

共享請求投影消費方擁有這項策略。附件儲存繼續報告準確的讀取失敗，提供者介面卡不會各自生成佔位或恢復狀態。

## 考慮過的替代方案

- **讓每次請求繼續失敗。** 這保留了嚴格錯誤報告，但一次儲存故障會讓其他部分仍可使用的持久工作階段永久不可用。
- **刪除或重寫歷史圖片塊。** 這會丟失證據、違反僅追加歷史，並使修復後的內容定址物件無法恢復原始請求。
- **由每個介面卡分別捕捉錯誤。** 未記錄的佔位會讓回放取決於當時存在的介面卡和儲存狀態，重複策略也會發生偏差。
- **自動替換丟失或損壞的位元組。** 引用標識經過驗證的不可變內容；在該身份下替換成其他位元組會破壞完整性驗證。

## 接受標準

- 缺失或損壞的歷史圖片產生一次持久隔離轉換和穩定佔位；之後的模型請求不再讀取該物件，也不會因它失敗。
- 一般讀取失敗會在服從取消訊號的前提下重試一次，隨後進入可重試隔離路徑。
- 重新啟動和 fork 後會從工作階段日誌重建相同的隔離請求。
- 僅在原始引用透過完整讀取驗證後，恢復操作才恢復圖片投影。
- 包測試覆蓋錯誤分類、冪等隔離、取消、重試、恢復和巢狀工具結果圖片；一個無需金鑰的可執行快照釘住模型可見佔位和持久事件。

## 風險

隔離和恢復各會改變一次提供者字首。實作必須在記錄狀態前識別準確的失敗引用，並協調並行請求，使重複失敗只產生一次有效轉換。沒有活躍工作階段的輔助呼叫無法記錄恢復狀態；它們的失敗策略屬於明確的實作範圍，不能退回到介面卡自行處理。
