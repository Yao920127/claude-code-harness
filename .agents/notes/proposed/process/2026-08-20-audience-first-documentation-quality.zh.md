# Agent Note: 以受眾為先的文件品質標準

Status: proposed

[English](2026-08-20-audience-first-documentation-quality.md) | 中文

## 問題

文件系統擁有健全的放置、新鮮度、連結、雙語和源等價性檢查，卻沒有把「簡短、直觀、友好」定義成可供使用者、新人、開發者和 agent（智慧代理）評審的結果。全部 `doc-sync`（文件同步門禁）檢查和全部翻譯配對均透過，但仍存在以下設計問題。前三項發現是設計重點；容量問題則解釋了為什麼增加更多常駐規則無法解決它們。

### 語義正確性可以在沒有現行歸屬者的情況下透過檢查

這些門禁證明結構和生成內容的新鮮度，卻不能證明維護中的正文仍指向實際機制。以前的 `dsh-doc-site-sync` 技能曾要求作者複用並不存在的 `en-docs` 側邊欄，還要求把章節加入已經移除的 `sectionOrder`；[website/docs.ts](../../../../website/docs.ts)實際擁有 `en-guide`、`en-develop`、`en-reference` 和 `sections`。已實作的[產品優先 README 決策](../../archived/process/2026-07-22-product-first-root-readme.md)描述了內部測試說明，以及 ACP、Python 與 JSON-RPC 介面章節，但[根 README](../../../../README.zh.md)並無這些內容；與此同時，已實作 Agent Note 必須跟隨已交付事實。

預算策略也存在相同的分裂。[docs/AGENTS.md](../../../../docs/AGENTS.md#wordcount-budgets)為 `architecture.md` 規定 1,800 詞目標和 5% 餘量，但[預算 manifest（中繼資料清單）](../../../../scripts/doc-budgets.manifest.json)允許 2,400 詞，而該檔案實際包含 1,313 詞。預算門禁之所以透過，是因為它只檢查 manifest 上限，不檢查目標或棘輪規則。因此，高影響正文需要一個具名真源或消費真源的聚焦檢查；第二份手寫副本不是新鮮度機制。

### 讀者成功與否是隱含判斷，而不是可測試結果

標準把頁面分成教學和參考，並要求作者私下判斷教學讀者的起始水平。標準沒有要求留下可供評審的讀者起始狀態、預期結果、最短成功路徑、常見失敗或下一篇有用頁面。因此，一份文件可以滿足層級放置、連結、詞數限制和 Markdown 結構，卻沒有證明目標讀者能完成任務。

公共站點直觀呈現了這種壓力。每種語言釋出 84 個頁面：3 個指南頁面、17 個開發頁面和 63 個參考頁面。`docs/user/` 下的 13 個英文件案共有 7,540 詞，而 47 個子系統頁面共有 100,759 詞。簡短的 Web 快速開始是良好的產品入口，但全語料沒有標準來驗證首次使用者、外掛新人和維護者是否都能沿一條明確路徑從入口走到結果與故障恢復。

### 生成內容的準確性與檢索品質混為一談

儲存庫包含 19 個完全生成的英文 Markdown 檔案，共 49,611 詞。47 個子系統頁面中有 44 個也包含生成的 Cordis 區域；這些區域佔子系統層級 100,759 詞中的 34,622 詞。`config-catalog.md` 有 14,807 詞，`tool-catalog.md` 有 10,599 詞，最大的混合子系統頁面則有 5,600–7,781 詞。

這些內容是正當的窮盡式參考，因此統一詞數限制反而會刪除價值。生成器證明完整性和新鮮度，但標準沒有為上下文視窗有限的 agent，或只尋找一個答案的人類讀者另設檢索標準。生成參考需要緊湊的入口層、穩定分組、直接錨點，以及根據查詢成本觸發的拆分規則；窮盡式細節可以在該入口層之後繼續保持窮盡。

### 標準沒有容納下一條規則的空間

常駐文件標準有 1,320 詞，等於 1,320 詞上限，並超過宣告的 1,250 詞目標。根 `AGENTS.md` 有 1,936 詞，目標為 1,600；`packages/AGENTS.md` 有 672 詞，目標為 650；`packages/README.md` 有 969 詞，目標為 600。凍結的上限能阻止進一步增長，卻沒有為受眾和結果標準創造位置。繼續增加常駐正文會加深該標準本應防止的問題。

### 基線

本次審計排除 `vendor/`、凍結的 `.agents/notes/archived/`、錄製快照和 fixture（測試前置資料）。受維護語料包含 1,042 個英文 Markdown 檔案和 986 箇中文對側檔案，共 1,106,138 個英文詞。活躍 Agent Note 佔 580 個檔案和 637,850 詞；`packages/` 下的 Markdown 佔 276 個檔案和 225,630 詞；`docs/` 佔 112 個檔案和 193,456 詞。這些數量描述維護和檢索壓力，本身並不構成缺陷。

系統最強的性質應予保留：按層級為每項事實指定一個歸屬者；把規範 Markdown 投影到站點而不建立副本；完整雙語配對；源變更時快速失敗的生成目錄；源等價宣告；可編譯的 TypeScript 範例；受檢查的連結與錨點；以及包區域性的模型體驗與限制約定。提案改變的是品質標準和入口結構，而不是這些保證。

## 提案

採用一套以受眾為先的品質約定，並給出五項定義：

- **簡短**表示常用路徑只包含達成結果所需的事實。窮盡式約定仍可透過直接連結或生成細節存取；簡短絕不意味著刪除必要行為、失敗、所有權或限制。
- **直觀**表示頁面會確定讀者的起始狀態，在依賴概念之前介紹前置知識，提供一個明確的下一步操作，並使用讀者會搜尋的產品或領域術語。
- **友好**表示讀者能識別成功，在操作前理解實質風險，從常見失敗中恢復，並在無需先學習無關架構的情況下進入下一層相關細節。
- **準確**表示每項持久事實都有一個歸屬者和與風險相稱的驗證路徑。生成事實來自源；手寫工作流值連結或消費其歸屬者，而不是複製列舉和路徑。
- **便於 agent 閱讀**表示標題、錨點、術語、所有權以及目前與提議狀態足夠明確，無需載入整個語料或重建評審歷史即可檢索所需章節。

### 原型規則

[dsh-doc skill](../../../skills/dsh-doc/SKILL.md) 負責這些規則的首個可執行版本。`session-persistence-jsonl` README 對以已交付的追加、恢復與編碼行為為證據，而不把其舊版正文當作權威。

- 每個撰寫型包 README 都以可搜尋 YAML 開頭。Skill 風格的 `description` 與按機制推導的 `kind` 為必填欄位。四種 kind 與四個技能範本一一對應：`package-group`（組地圖）、`package-reference`（外掛或服務包）、`package-library`（純模組入口）與 `package-bundle`（`dsh.bundle.patch`）。對照檔案路徑、雜湊與物理行對齊由支援自動合併的 sidecar 及其門禁負責，因此 README frontmatter 不包含 `i18n` 塊。名稱已由標題或包 manifest 歸屬，受眾已由文件職責表達；在受治理的標籤分類與搜尋消費方證明其價值超過全文檢索之前，不加入標籤。
- 撰寫型頁面先寫三至五句的 `Summary`，再寫帶連結的 `Table of Contents`。英文包 README 的 Summary 不超過 100 個按 `wc -w` 語義統計的詞。它描述讀者可見能力，而不是 Cordis 角色、註冊項或內部元件；除非讀者會在設定、命令或公開 API 中直接使用某個原始碼識別符號，否則不得寫入該識別符號。由格式約束的 Agent Note、事故檢討、生成片段和機器檔案保留其必需骨架。
- 每個實質章節在子章節、表格或程式碼之前先給出簡短引導，頁面則從基礎使用者用法逐步進入高階開發者與維護者細節。
- 英文技術正文采用受 ASD-STE100 啟發但不宣稱認證的清晰度評審：明確行動者與動作，穩定使用術語，使用直接動詞，拆分指令與條件，並完整保留情態、例外、時序與數值。指令 20 詞和描述 25 詞的限制僅作評審提示。準確性高於句長。
- 包約定留在程式碼旁。跨包材料有計劃地向 `docs/learn/overview/`、`docs/learn/cordis/`、`docs/learn/practices/`、`docs/user/`、`docs/developer/`、`docs/developer/discussion/`、`docs/scratch/` 和平行的 `docs/subsystems/` 層級遷移。
- 英文和中文頁面保持同等權威，並在結構、連結、程式碼、frontmatter 佈局和精確物理行數上一一對應。
- 內聯配對中繼資料是伴隨檔案的目標替代方案。在驗證器、合併驅動、恢復流程、生成區域記錄器和歸檔檢查消費非自引用配對摘要之前，原型可以同時保留兩者。
- 儲存庫根級內部連結是目標撰寫模型。原型保留渲染器可用的相對連結，因為前導 `/` 目前會在 GitHub 上離開儲存庫、繞過 `verify-md-links`，並且不會由站點投影。
- `Further Exploration` 是可選的新人路徑，連結三至七個相鄰頁面。
- 每個撰寫型頁面都以 `Dev Note` 結尾，作為活躍粗略上下文的唯一位置。它保持非權威狀態，只連結而不複製任務狀態，並在工作結束時完成提升或清理。
- 可獨立搜尋的規則、實踐、範例和決策在擁有不同歸屬者或變更節奏時，使用描述性目錄下的小檔案；緊密耦合的義務保留在一起。

### 按文件職責劃分的標準

| 職責 | 主要結果 | 必需入口資訊 | 驗證 |
|---|---|---|---|
| 產品快速開始 | 完成一項有代表性的任務 | 前置條件、一個啟動路徑、首次成功、安全邊界、下一步 | 文件路徑的建置或打包冒煙測試，加連結和站點檢查 |
| 使用者任務指南 | 完成一項使用者任務或從中恢復 | 起始 UI／API 狀態、有序操作、可觀察結果、常見失敗及恢復 | 行為測試；涉及視覺狀態時評審截圖；或指定人工歸屬者 |
| 貢獻者教學 | 進入透過檢查的開發狀態 | 支援的執行時、設定命令、預期結果、聚焦的後續命令 | 在受支援環境中對乾淨檢出執行命令冒煙測試 |
| 架構概覽 | 從一個頁面重建系統 | 產品組合、歸屬者、依賴方向、擴充功能點、細節連結 | 由源支援的包或圖檢查，加聚焦人工評審 |
| 包或子系統參考 | 無需閱讀實作即可查到一項約定 | 範圍、歸屬的型別或行為、失敗、生命週期、限制、相關歸屬者 | 既有 JSDoc、型別等價、生成區域、README 和連結檢查 |
| 生成參考 | 找到一個精確條目並信任其完整性 | 範圍、生成歸屬者、分組或索引、穩定錨點、相關概念指南 | 確定性 `--check`、完整性 fixture、站點建置和檢索規模報告 |
| Agent 指令或 skill（技能） | 在沒有陳舊複製值的情況下執行一項工作流 | 範圍、權威連結、必需決策、僅在此處歸屬時寫入精確命令 | 中繼資料或連結檢查，以及針對複製機器值的聚焦測試 |
| 提議或已實作 Agent Note | 理解決策、取捨與狀態 | 問題、提案或決策、備選方案、驗收或後果 | 既有生命週期、格式、配對和取代檢查；語義時效性由評審負責 |

該表應歸屬一份規範品質參考。`docs/AGENTS.md` 只保留每次編輯文件都需要的簡短常駐規則，並連結到該參考。這樣可以創造預算餘量，而不是把另一份完整標準放進 agent 上下文。

### 生成參考的入口層與細節層

每份生成參考都應在窮盡式輸出之前提供緊湊入口層：範圍、預期查詢、分組或索引、概念指南的直接連結，以及生成器或檢查命令。生成器應報告頁面詞數、條目數、標題數和最大章節。當一次查詢需要掃描無關分組，或單頁主導 agent 上下文時，該頁面便跨過評審閾值；隨後，歸屬者按照源中繼資料中已有的穩定領域拆分頁面，而不是按任意詞數切片。

首個原型應選擇一個大型目錄和一個混合子系統頁面。在進行全語料拆分前，它應比較查詢步驟、生成 diff 大小、建置時間、路由穩定性，以及代表性問題所需的 agent 上下文。路由移動時，既有錨點需要保留別名。

### 執行切片

1. 建立並驗證 `dsh-doc`，再把一組 package README 對改寫為行對齊、帶中繼資料的原型，同時不改變執行時事實。
2. 用新人、使用者、開發者和 agent 任務評審渲染後的原型；先修訂 skill，再在其他位置強制執行該格式。
3. 新增聚焦的中繼資料、Summary 長度、章節順序、行對齊、連結解析和配對 fixture。遷移所有違反已接受入口上限的既有包 Summary；在每個合併與恢復消費方都有替代支援前，保留伴隨檔案。
4. 把已接受的常駐規則提取到一份規範品質參考，將 `docs/AGENTS.md` 精簡到目標以下，並且一次只組織一個內聚的 `docs/` 主題，同時原子地修復連結與導航。
5. 在 `config-catalog.md` 和 `docs/subsystems/core.md` 上製作生成參考入口層與細節層分離的原型；只有實測查詢成本下降且沒有丟失事實或造成路由擾動，才把確認後的模式應用到其他位置。

該順序使每項變更都能獨立評審。前三個切片改進標準與包入口，而不改變更廣的資訊架構；生成文件原型則在更廣的結構變更前提供證據。

切片 1–3 已按此形式交付：`dsh-doc` 成為合併後的標準（`dsh-doc-standards` 與 `dsh-doc-site-sync` 已併入其中，站點工作流攜帶修正後的側邊欄值），`session-persistence-jsonl` README 對是參考範例，`pnpm run test:docs` 強制執行中繼資料、配對與快速文件檢查。切片 4–5 仍待完成。

### 非目標

本提案不縮減窮盡式事實，不合並受眾層級，不釋出內部決策記錄，不恢復 Agent Note 索引，不為了檔案數對稱而拆分緊密耦合的規則，也不把此次審計當作使用者研究。在替代方案透過等價的恢復與渲染檢查前，本提案不刪除現有配對或連結基礎設施。

## 考慮過的備選方案

**為每份文件設定統一詞數上限。**不予採納，因為窮盡式參考條目、公開約定和決策理由可以既長又正確。對這些文件職責而言，入口路徑長度與查詢成本才是相關約束。

**強制使用統一頁面範本或受眾前置中繼資料。**不予採納，因為這會給生成頁面、包參考和簡短指令增加形式，卻不能證明讀者成功。標準按文件職責定義結果，僅在 `kind` 能選擇具體包文件標準時使用它，並且只新增聚焦檢查或評審會消費的欄位。

**把可讀性分數作為品質門禁。**不予採納，因為公式會懲罰精確技術術語，卻無法發現錯誤所有權、遺漏失敗行為、陳舊命令或破損的讀者路徑。

**立即重寫或拆分全部文件語料。**不予採納，因為現有系統在機制上健康，許多長參考也確實應保持窮盡。範圍受限的包 Summary 遷移不會改變路由或窮盡式參考內容；更大的結構變更仍需實測證據。

**保留現有門禁，讓評審負責友好程度。**不予採納，因為陳舊工作流值和預算策略不一致說明，僅憑評審無法保留複製的語義事實，而現有門禁也不詢問讀者是否能完成任務。

## 驗收標準

- 一份規範品質參考按文件職責定義簡短、直觀、友好、準確和便於 agent 閱讀的文件。
- `.agents/skills/dsh-doc` 透過驗證，並直接連結其中繼資料、結構或層級及評審或原型參考，而不在 `SKILL.md` 中複製這些參考的詳細規則。
- `session-persistence-jsonl` README 對展示可搜尋 YAML、Summary、Table of Contents、從使用者到開發者的漸進結構、Further Exploration、結尾 Dev Note、結構一致性和精確行數相等，同時保留已驗證的包約定。
- 每個英文包 README Summary 都不超過 100 個按 `wc -w` 語義統計的詞；聚焦門禁報告實測詞數，並引導失敗項閱讀 `dsh-doc` 與所選 kind 範本。
- `docs/AGENTS.md` 連結該參考，仍足以充當常駐指令，並低於其目標且至少保留 5% 餘量。
- 根級使用者路徑、Web 快速開始、第一個外掛教學、貢獻者設定和架構概覽各自給出一個可觀察結果與驗證歸屬者，同時不複製實作細節。
- 預算 manifest 同時記錄目標與臨時上限，其檢查會報告或拒絕違反餘量或棘輪規則的狀態。
- 文件站工作流不再包含複製的無效側邊欄名稱或章節歸屬宣告，並有聚焦測試防止復發。
- sidecar 繼續作為唯一一致性記錄，因為它能保留同等權威、上次確認文字恢復、自動合併安全、生成區域記錄和歸檔封存，同時不會在正文件案中製造衝突。
- 一個已接受的儲存庫根級連結格式在遷移相對連結前能在 GitHub 與文件站正確渲染，並繼續接受本地目標或錨點檢查。
- 一個大型獨立生成目錄頁和一個混合子系統頁面展示緊湊入口層與更低的實測查詢成本，同時保留窮盡式生成事實、穩定連結、雙語配對和確定性新鮮度。
- `pnpm run doc-sync`、`pnpm run lint`、聚焦的新檢查和 `git diff --check` 均透過。

## 風險

- 中繼資料可能淪為樣板；因此包 README 檢查只允許具有現行檢索、範本選擇或雙語一致性消費方的欄位。
- 硬性句長限制可能割裂說明，或把條件與後果分開。受控英語的句長僅作評審提示；單獨的 100 詞包 Summary 上限只約束入口段落，精確約定仍保留在其歸屬章節。
- 精確行對齊可能迫使譯者寫出不自然的正文；評審必須保護含義，並可同時修訂兩側，而不是削弱其中一側。
- 拆分生成參考可能增加路由與連結維護；原型必須保留別名並衡量取捨。
- 語義檢查可能膨脹成阻塞正當變更的儲存庫拓撲掃描器；檢查應覆蓋高風險複製值和代表性路徑，而正文含義仍由評審負責。
- 包 README 的快速參考表會手工重複部分設定預設值；在源驅動檢查接管之前，評審者必須對照原始碼和生成設定目錄驗證變更值，並讓這些表保持精選而非窮盡。
- 為縮短 agent 上下文而最佳化可能使人類參考變得碎片化；每次拆分都需要一個穩定概念歸屬者和一條明確導航路徑。
- 永久的 Dev Note 可能變成第二份佇列或陳舊歷史堆積；完成工作時必須提升持久事實並刪除已解決的過程內容。
- 本次審計使用儲存庫結構、門禁和代表性頁面，而不是使用者研究。在廣泛推廣之前，維護者應透過真實的新人、使用者、開發者和 agent 任務驗證提議的讀者結果。
