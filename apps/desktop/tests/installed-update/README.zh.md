# Windows 已安裝應用更新演練

[English](README.md) | 中文

## 摘要

準備獨立測試應用和全新的 test 分發名稱空間，再由操作者親手安裝、注入故障、重試並確認重新啟動。本地清單或完整日誌序列不能證明安裝器合格或資料保留。下述已安裝應用步驟在操作者使用已驗證安裝檔執行之前仍未驗證。

## 準備物料

在已安裝依賴的儲存庫根目錄中，用兩個遞增的派生測試版本建立批次。這隻寫入已忽略的本地清單，不建置、簽名、上傳、安裝或讀取憑證。

範例以 `0.1.6-alpha.1` 為基礎版本。建立新物料前，按[釋出版本規則](../../README.zh.md#release-versions)替換為實際基礎版本、北京時間日期和未使用的序號。

```powershell
node --import tsx apps/desktop/scripts/prepare-installed-update.ts init 0.1.6-alpha.1.20260916.1 0.1.6-alpha.1.20260916.2
```

保留返回的 `run.json`，兩個安裝檔複用其中的隨機身份與 `qualification/<id>` 路徑。源提交與髒檔案列表標識起始工作區，不代表後續安裝檔內容。最終建置來源和產物雜湊另行記錄；不要在更新中途重新生成清單。

透過儲存庫的僅準備流程生成新原始碼資源，再生成共享啟動入口、兩份獨立的版本繫結執行時和凍結的應用檔案。將 `<run.json>` 替換為批次清單路徑。僅準備流程建置並檢查原始執行時，但在簽名前停止；其餘命令絕不呼叫簽名器或安裝器。這些命令拒絕覆蓋已有批次產物；出錯後保留不完整物料，不在其上重試。

```powershell
node apps/desktop/node_modules/pnpm/bin/pnpm.mjs --dir apps/desktop run prepare:package win-x64
node --import tsx apps/desktop/scripts/prepare-installed-update.ts bootstrap "<run.json>"
node --import tsx apps/desktop/scripts/prepare-installed-update.ts runtime "<run.json>"
node --import tsx apps/desktop/scripts/prepare-installed-update.ts application "<run.json>"
```

將生成的 `bootstrap` 目錄中的兩個檔案放在包內 `lib/` 同級，將包主入口設為 `qualification-bootstrap.mjs`。該入口在載入生產主程式前驗證已安裝應用的 ID 與版本。它將 Electron 使用者/工作階段資料、Harness home 和日誌放在作業系統應用資料目錄下的 `dsh-update-qualification/<id>/`；兩個版本使用相同路徑。執行時複製器僅修改釋出家族包版本和對應依賴引用，保留第三方版本，並重新驗證兩個副本清單和未修改的原始資源。其 `runtime-preparation/result.json` 記錄雜湊，並明確不宣稱簽名或副本版本的啟動驗收透過。這些合成版本屬於測試物料，不是 npm 釋出版本。

`application` 命令將已建置的主程式/預載入模組、介面檔案和準備好的啟動入口複製到 `application/files`，並在 `application/result.json` 中記錄 SHA-256。它不複製應用根目錄的 `.env.windows`，也不凍結 `node_modules` 與建置工具。[驗收打包設定](../../scripts/installed-update-builder.ts)驗證該清單與選定的獨立執行時，選用共享凍結檔案和隔離包中繼資料，並保留常規安裝器與簽名掛鉤。其測試替換籤名器，並透過固定版本建置器的設定驗證；測試不生成安裝器。另行授權的受監督建置仍須記錄依賴/工具輸入，並驗證最終包內容及簽名。

[打包入口](../../scripts/package-installed-update.ts)預設只檢查。保留的簽名保護鎖會在讀取憑證前使其拒絕；入口絕不清除此鎖。沒有保護鎖時，檢查會載入 `.env.windows`、驗證準備輸入，不啟動子程序。共享建置器要求[測試釋出設定](../../README.zh.md#upload-updates)中有效的 `DOWNLOAD_TEST_RELEASE_ID`；資格驗收仍使用清單中獨立的 `qualification/<id>` 路徑釋出。在儲存庫根目錄使用一個準確版本執行：

```powershell
node --import tsx apps/desktop/scripts/package-installed-update.ts "<run.json>" 0.1.6-alpha.1.20260916.1 --check
```

實際打包仍未驗證，必須另行獲得硬體恢復授權並有操作者在場。`--execute` 模式要求終端和包含版本、批次 ID 的準確確認，沒有管道批准選項。它再次檢查保護鎖，並獨佔建立該版本的 `packaging` 目錄。受監督子程序只建置該版本、停用釋出、移除無關憑證，失敗或達到 15 分鐘整體期限時停止。該期限不限制單次 CSP 內部認證嘗試。記錄保留原始碼/工具雜湊、脫敏輸出、事件和產物檔案雜湊；已有嘗試或輸出拒絕複用。`builderCompleted` 與監督程式成功結果不證明包驗證、驗籤或安裝成功；獨立完成這些檢查前，`packageVerification` 保持 `pending`。

操作者開始前，提供兩個已驗證安裝檔、生成的中繼資料與 blockmap、打包和簽名記錄、準確的安裝後可執行檔案路徑與固定 test feed URL。兩個安裝檔必須使用相同的測試身份、隔離資料目錄，並在每次啟動時設定同一個安裝目錄外的絕對路徑 `DSH_DESKTOP_UPDATE_JOURNAL_DIR`，包括安裝器觸發的重新啟動。僅在首次啟動終端中設定變數是不夠的。[Windows 簽名規則](../../README.zh.md#windows-ev-signing)仍適用；清單絕不解除簽名保護鎖。

Windows [只讀簽名檢查器](../../scripts/installed-update-signature.mjs)使用真實 updater 驗籤，釋出者來自可信公鑰憑證，隨後要求 Authenticode 與時間戳屬性有效且 SHA-512 未變。驗籤子程式不繼承簽名/上傳秘密或 PowerShell 模組路徑覆蓋。檢查器絕不載入 `.env.windows`、簽名檔案或執行被檢查的可執行檔案。本地已觀察到簽名探針透過、未簽名安裝檔被拒絕；這些結果不能證明任一準備版本、包身份或安裝行為已驗收。

[安裝檔檢查器](../../scripts/verify-installed-update-package.ts)先驗證最終安裝檔，再使用經過審查的本地 7-Zip 可執行檔案解包。清單、可信公鑰憑證和工具均須提供絕對路徑；絕不選擇從待驗安裝檔中解出的工具。此命令建立全新的 `verification/check-*` 目錄，保留部分記錄，安裝檔缺失時立即失敗：

```powershell
node --import tsx apps/desktop/scripts/verify-installed-update-package.ts "<run.json>" 0.1.6-alpha.1.20260916.1 "<public.cer>" "<reviewed-7za.exe>"
```

檢查器核對實際歸檔內的應用身份、入口、凍結應用位元組、updater 依賴版本、feed/快取/釋出者設定，並將內建 Harness 執行時與準備輸入比較；測試強更策略也必須有效。它從 `app.asar` 提取執行時，並在 `app.asar.unpacked` 路徑核對可執行檔案簽名。發生變化的執行時可執行檔案須單獨驗籤；其他執行時位元組在經過 electron-builder 的依賴 manifest 轉換後必須與準備輸入一致。它在解包前拒絕不安全歸檔路徑，記錄安裝器、應用及執行時可執行檔案的簽名。成功前再次核對安裝檔、feed/blockmap、清單、憑證和工具雜湊。`passed` 僅覆蓋這些檢查：依賴位元組未凍結，安裝器註冊、啟動、升級和資料保留仍是明確的人工檢查項。保留的舊包已完成真實歸檔讀取；本批次準備版本的完整簽名包檢查仍待執行。

遵循獨立的[上傳與釋出步驟](publication/README.zh.md)。先保持固定 feed 不存在以測試 404，再發布版本 1 以測試同版本。兩個情境在已安裝的版本 1 應用內完成之前，版本 2 中繼資料保留在本地。保留髮布記錄及遠端物件用於診斷，不刪除已釋出的 feed 來重建較早情境。

本地 `files` 命令接受 `<run.json>` 與本批次的一個準確版本。它讀取該版本的 `installer/nightly.yml`，驗證預期安裝檔檔名、大小、SHA-512 和非空外部 blockmap，輸出分開的二進位制目標與固定 feed 內容。安裝檔缺失會導致驗證失敗。它不寫檔案，也不讀取憑證。其 `file-integrity-only` 結果不能授權上傳，也不能替代簽名包內容和應用身份驗證；這些仍是釋出前的必要條件。

## 人工操作順序

僅在準備透過後親手操作。使用可丟棄的測試工作階段和設定，不使用生產工作區或未儲存的工作。

1. 安裝版本 1。記錄安裝檔路徑、雜湊、簽名結果和時間。透過安裝後的快捷方式啟動，核對可執行檔案路徑與介面版本；不要啟動解包目錄中的應用或開發伺服器。
2. 確認新日誌包含版本 1 的 `started` 和 `workspace-ready`。建立可辨認的測試工作階段並修改一項無害設定，在本地記錄預期值。完成下面兩項 feed 檢查，並保持版本 1 執行。
   - **清單缺失：**保留對設定的固定 URL 執行 GET 返回 404 的帶時間戳記錄。觀察啟動自動檢查不彈出打擾性彈出視窗，再手動檢查：預期先檢查、後提示失敗，而非“暫無更新”，且不下載、不安裝。釋出任何清單前先儲存截圖和日誌。
   - **同版本清單：**另行授權後將版本 1 釋出到相同 URL，保留完整的 200 回應、版本與 SHA-512。在仍執行的版本 1 內手動檢查：預期顯示暫無可用更新及目前版本，不下載、不安裝，且不殘留此前 404 的錯誤圖示。自動檢查無更新時應靜默。授權版本 2 前先保留證據。
3. 授權將版本 2 中繼資料釋出到已有的固定 feed URL。回讀該 URL，驗證版本 2 及其二進位制雜湊。保留晚於版本 1 啟動證據的釋出證據。
4. 在版本 1 中手動檢查，確認提示可用版本但不自動下載。準備經過審查的[僅針對測試應用的故障與恢復](network/README.zh.md)。絕不停用網路卡、VPN、共享代理、遠控連線或整個域名的存取。
5. 點選下載，在進度開始後僅中斷測試應用的傳輸。擷取一次失敗與持續重試提示，確認不安裝或靜默重試。進度開始前的連線失敗是另一種觀測，不能滿足傳輸中斷測試。
6. 移除本批次的準確故障設定並驗證恢復。親手點選重試。記錄進度、總和檢查碼就緒。預期出現獨立安裝確認；下載完成本身不得授權重新啟動。
7. 確認安裝。有任務時檢查警告並顯式授權停止；沒有任務時，確認內容不得聲稱存在任務。記錄版本 1 最後的視窗，讓安裝和重新啟動自然結束，不手動啟動另一實例。
8. 驗證安裝後的版本 2 可執行檔案與介面版本。檢查第 2 步的工作階段和設定並截圖。在同一外部證據目錄中找到版本 2 的 `started` 和 `workspace-ready`。自動重新啟動缺失與手動啟動成功分開報告，二者不能互相替代。

## 證據與恢復

故意保留的 404 屬於檢查失敗，不是後續的下載中斷情境。僅有瀏覽器回應不能證明應用行為。每次觀測的 URL、UTC 時間、HTTP 狀態、存在時的 feed 原文及雜湊、截圖和日誌快照應一同儲存。日誌檢查器不認證這兩個 feed 情境，也不記錄原始 HTTP 診斷；這些觀察結果由操作者提供。後續手動檢查成功應無需重新啟動應用即可恢復。

保留清單、建置記錄、原始 feed、二進位制雜湊、釋出回執與回讀、故障設定和移除證據、截圖及全部程序日誌。安裝器日誌與測試資料可能包含私有路徑或內容，分享前須審查。檢查器只讀，僅複製里程碑引用，不複製原始診斷。替換目錄預留位置並使用清單中的準確版本：

```powershell
node --import tsx apps/desktop/scripts/prepare-installed-update.ts inspect 0.1.6-alpha.1.20260916.1 0.1.6-alpha.1.20260916.2 "<journal-directory>"
```

結束代碼 0 表示按序日誌標記齊全；結束代碼 2 表示缺少標記；結束代碼 1 表示輸入或命令驗證失敗。失敗重試序列不能拼接不同版本 1 程序。早於原程序退出就啟動的後繼程序不計入；系統時間變化可能導致證據不完整，需要調查。`recordedFlow: complete` 不等於整體驗收透過。報告始終要求獨立人工檢查釋出時間、網路失敗與恢復、安裝器完成與路徑、資料保留以及截圖和確認。

使用 `collect` 及匹配安裝應用的 `dsh-update-qualification/<run-id>/journals` 目錄儲存本地日誌快照與報告。它先驗證所有選中記錄，再在物料批次下建立新的 `evidence/collection-*`。複製的日誌與 `report.json` 描述同一份記憶體快照，包含 SHA-256 和 `operatorAcceptance: pending`；原檔案保持不變。不收集其他檔案、設定、工作階段、建置輸出或憑證。將這些另外審查過的證據與報告一同保留，不放進日誌目錄。

```powershell
node --import tsx apps/desktop/scripts/prepare-installed-update.ts collect "<run.json>" "<journal-directory>"
```

收集結束代碼 0 表示檔案已儲存，即使記錄流程不完整；下結論前檢查 `report.json`。寫入失敗時保留部分輸出，並在儲存允許時留下失敗標記。重複收集建立新目錄，不替換舊證據。檢查和收集拒絕不完整結尾、未知欄位或診斷值、超過 10 MiB 的檔案及超過 50 MiB 的快照。相關操作穩定後再收集；執行中的應用可能在快照之後追加記錄，競爭中的不完整追加要求稍後再收集，不能截斷原日誌。真實安裝應用的收集仍需人工執行；測試使用真實日誌寫入器和合成生命週期操作。

使用下表記錄結果，未觀測項保留待驗證：

| 專案 | 證據位置 | 結果 |
|---|---|---|
| 兩個安裝檔及簽名已驗證 | | 待驗證 |
| feed 404：自動靜默失敗、手動可見失敗且不下載 | | 待驗證 |
| 版本 1 feed：執行中的版本 1 無可用更新，舊錯誤已清除 | | 待驗證 |
| 版本 1 執行早於版本 2 釋出 | | 待驗證 |
| 僅測試應用故障且觀察到下載失敗 | | 待驗證 |
| 故障移除後顯式重試達到就緒 | | 待驗證 |

首個前置條件失敗時即停止。簽名失敗終止打包並保留記錄，不自動重試 PIN 認證。feed 不符則在下載前停止測試。故障影響遠控時停止，並透過準備好的恢復動作僅還原其擁有的改動。不要解除安裝、清快取、刪除證據或覆蓋失敗批次，讓後續嘗試看起來成功。需要全新嘗試時新建批次，並保留失敗批次。

<a id="dev-note"></a>

## 開發備註

本地批次建立與日誌檢查已有自動化測試。簽名產物生成、隔離網路故障工具、延後 feed 釋出、安裝器觸發重新啟動和完整人工流程仍需單獨驗收；本頁不將其報告為已完成。
