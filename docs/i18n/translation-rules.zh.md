# 翻譯規則

[English](translation-rules.md) | 中文

本文規定：如何在本儲存庫文件配對的中英文兩種語言之間進行翻譯。兩種語言同權（見 [README.md](README.zh.md)）：每次變更可以用任一語言撰寫，被編輯的一側即為本次更新的源；本文的規則約束如何產出或更新對側檔案。這些規則對人類和 agent（智慧代理）同等生效。日常工作中，agent 會在術語指導下直接一次完成有改動內容的翻譯；擴充功能版 [.agents/skills/dsh-translate-docs](../../.agents/skills/dsh-translate-docs/SKILL.md) 工作流僅在使用者顯式呼叫時執行。規則級別沿用 RFC 2119 的用法：**必須（MUST）** ／ **禁止（MUST NOT）** 會卡門禁或評審；**應當（SHOULD）** 偏離時要說明理由；**可以（MAY）** 自行裁量。

## 忠實性

- 對側檔案*必須*傳達與撰寫側相同的內容：不新增行為、前置條件、警告、版本宣告或範例，也不漏掉任何一項。如果兩側在實質內容上不一致，沒有哪種語言預設獲勝；請修正錯誤的一側，並在同一個變更裡同步更新另一側。
- 對側檔案讀起來*應當*是其語言自然的技術文字，而非逐詞對照的譯文。請根據語義翻譯，在目標語言語法需要時重組句子，並保持原作者的語域（比如：簡練的保持簡練）。
- 不要翻譯不可譯的內容：如果一句話依賴源語言的習語、無法自然轉換，請翻譯它的意思，而非習語本身。

## 行文

- 語體以 [style-samples.md](style-samples.md) 為校準錨點。人工定稿的金標樣例按文體各一組，譯文必須參照文體最接近的樣例，採用其中目標語言一側的語體；如果樣例與本文的行文規則衝突，以樣例為準。譯成中文時，採用規範的技術制度文；譯成英文時，採用簡潔、專業的開發者文件語體。
- 以母語技術作者的身份重述內容，而不是以譯者身份逐句轉寫，同時保留原文的每個語義成分：不新增、不遺漏——流暢永遠不是丟掉語義成分的理由。
- 如果直譯會讓執行主體含糊，請明確寫出實際執行者；譯成中文時，應由「系統、門禁、評審人」等實際執行者作主語，避免含糊的被動句或抽象主語。
- 優先採用目標語言中通行的工程表達，避免生硬直譯（false positive/negative→誤報／漏檢、enforcement frontier→執行紅線）；隱喻應自然改寫，名詞鏈則按目標語言的習慣拆開。
- 長段按語義單元拆分，一段一件事。段落邊界可以與原文不同；結構簽名不比對段落數。
- 翻譯為中文時，類別名詞使用中文並在首現括注英文（實操手冊（cookbook））；翻譯為英文時，使用通行的英文類別名。指目錄或檔案本身時保留程式碼體英文。

## 結構保持

配對門禁會檢查標題深度、圍欄程式碼塊、表格行列數、列表型別、有序列表起始編號、列表項數量、連結 locale 與語義目標；門禁未覆蓋的結構仍需人工核對。兩個配對檔案必須在以下方面一一對應：

- 標題層級（相同級別、相同順序；標題的**文字**要翻譯）；
- 列表形態與編號；
- 表格（相同的列、相同的行序；表頭單元格按術語表翻譯）；
- 圍欄程式碼塊：**逐位元組一致，包括註解**。配對簽名比對資訊字串與內容，` ```ts ` 塊還要透過 `doc-typecheck` 編譯；
- 行內程式碼（命令、flag、設定鍵、檔案路徑、事件名、API 名、版本號）：原樣保留，從不翻譯或重排；
- 連結與錨點：每個相對文件連結必須保持相同的語義目標和完全相同的 query/fragment 字尾。目標屬於活躍雙語語料時，英文側使用其 `.md` 路徑，中文側使用其 `.zh.md` 路徑；該範圍內缺少對側屬於錯誤，範圍外的目標保留原路徑。外部 URL、圖片與純頁內 fragment 保持不變。語言切換行仍是顯式跨 locale 例外；在 GitHub 以外位置渲染的 README 可以按 [README.md](README.zh.md) 的規定，使用指向確切對側檔案的規範公開儲存庫 URL。連結**文字**翻譯。

本儲存庫的 Markdown 約定對 `.zh.md` 檔案原樣生效：一個段落一個物理行（`verify-md-wrap`）、相對連結必須可解析（`verify-md-links`）、檔案末尾恰好一個換行。

## 術語

- [terminology.md](terminology.md) 是雙向的術語真源。翻譯前請先載入它；表內術語必須遵守對應行與「不要譯作」禁項。譯成中文時，採用「中文」列，並按「首次出現」列括注；譯成英文時，採用「English」列，不加中文括注。
- 譯成中文時，術語表未收錄的技術術語只有在主流中文 OSS 文件或廠商資料中已有通行譯法時才可以翻譯（K8s／Vue／MDN 中文文件、微軟簡中風格指南、大廠專案文件），並須在 PR 中註明出處；否則必須保留英文，並在 PR 描述的「待定術語」中給出建議譯法。
- 譯成英文時，採用通行的英文技術術語。如果源術語沒有明確的通行對應詞，則保留原詞、附上簡短說明，並列入「待定術語」。兩個方向都不得自行創造譯法；確定後的術語須在同一個 PR 或後續 PR 中加入 [terminology.md](terminology.md)。

## 排版

本節規則約束中文一側；英文一側遵循儲存庫常規的 Markdown 約定（根 `AGENTS.md`）。以下中西文混排規則遵循 [MDN 簡體中文翻譯指南](https://github.com/mdn/translated-content/blob/main/docs/zh-cn/translation-guide.md)、[Kubernetes 中文在地化指南](https://kubernetes.io/zh-cn/docs/contribute/localization_zh/)、[Vue.js 中文翻譯須知](https://github.com/vuejs-translations/docs-zh-cn/wiki/%E7%BF%BB%E8%AF%91%E9%A1%BB%E7%9F%A5) 與[中文文案排版指北](https://github.com/sparanoid/chinese-copywriting-guidelines)的跨專案共識，其根據是 [W3C clreq](https://www.w3.org/TR/clreq/) 與 GB/T 15834—2011：

- 必須在中文與拉丁詞之間、中文與數字之間各留一個半形空格：`每個 plugin 註冊 3 個 tool`。全形標點與任何字元之間不加空格。
- 中文行文必須使用全形（中文）標點：`，。：；？！（）「」`。半形標點保留在程式碼內、按原樣引用的完整英文句子內、以及數字內（`3.5`、`1,024`）。
- 中文行文*應當*優先使用冒號、句號、逗號或括號，儘量不用破折號；只有其他標點都無法自然表達時才保留破折號。
- 頓號：中文的並列項之間使用頓號（、），而非逗號。
- 禁止使用全形數字或全形拉丁字母：永遠不寫 `１２３`，永遠寫 `123`。
- 專有名詞保持規範大小寫：GitHub、TypeScript、DeepSeek。除非引用程式碼，否則絕不寫 `github`／`Github`。
- 第二人稱用「你」，不用「您」（與 Vue、Kubernetes 中文約定及本儲存庫的直接語氣一致）。
- 強調標記（`**加粗**`、`*斜體*`）落在與對側相同的文欄位上。中文沒有斜體，渲染效果可能看不出差別，不要用引號或其他裝飾替代。

## 品質標準

- 一對文件的完成標準：一位雙語工程師只讀其中任一檔案，能獲得與另一檔案讀者完全相同的資訊（相同的事實、相同的告誡、相同的語氣），並且沒有任何多餘的內容。
- 請執行 `pnpm run verify-translation-pairing` 與 `doc-sync` 的其餘門禁。這些門禁會檢查一致性記錄、切換行、標題深度、程式碼塊、表格行列數、列表型別、有序列表起始編號、列表項數量、連結及儲存庫 Markdown 規則；列表與表格的順序、非常規列表編號、行內程式碼、強調標記、語義、術語和語體則由人工評審負責。
