# @deepseek-ai/dsh-attachment-local

[English](README.md) | 中文

## 概述

在執行 DSH 的機器上，把圖片與通用檔案附件持久儲存到 `DSH_HOME` 下。圖片經過驗證、針對模型請求完成規範化並按路由快取；通用檔案不設准入限制，按位元組原樣儲存。即使上傳時使用不同顯示名稱，相同位元組也只儲存一次；讀取會驗證檔案長度與內容，之後收緊限制也不會讓已接納的圖片不可讀。隨附的 `dsh` 組合無需設定即可使用本包。物件僅限本機，並且永遠不會自動刪除。

<a id="use-this-package"></a>
## 使用本包

在預設組合中，把圖片或通用檔案附加到提示詞或命令，它們會自動儲存到本機。自行組合時，掛載這個外掛即可獲得持久附件。

### 最小設定

掛載外掛，無需任何必填設定。下列預設值規定了可以附加的內容；生成的設定目錄完整列出了所有欄位。

```yaml
- name: '@deepseek-ai/dsh-attachment-local'
```

| 欄位 | 預設值 | 含義 |
|---|---|---|
| `dshHome` | 自動解析 | 顯式 harness home；省略時依次跟隨 `$DSH_HOME` 與 `~/.dsh` |
| `maxImageBytes` | `20 MiB` | 單張圖片接受的最大編碼源位元組數 |
| `maxImagesPerMessage` | `20` | 單條提交訊息接受的最大圖片數量 |
| `maxMessageImageBytes` | `200 MiB` | 單條提交訊息接受的最大編碼源圖位元組總數 |
| `maxImagePixels` | `64,000,000` | 源圖寬度與高度乘積的最大值 |
| `maxImageDimension` | `8192` | 源圖接受的最大寬度或高度 |
| `normalizedImageMaxPixels` | `2048 × 2048` | 已存規範化圖片的總畫素預算 |
| `normalizedImageMaxDimension` | `8192` | 應用總畫素預算後的最大長邊 |
| `normalizedImageMaxBytes` | `4 MiB` | 編碼位元組目標；沒有候選滿足時保留品質階梯中的最小輸出 |
| `imageCompressionConcurrency` | `2` | 並行規範化與請求變換的 FIFO 上限 |

生成的[設定目錄](../../../docs/config-catalog.zh.md#deepseek-aidsh-attachment-local)完整列出了所有受支援的欄位及其 JSDoc。

### 圖片儲存在哪裡、會保留多久

附加的圖片儲存在本機的 `<DSH_HOME>/attachments/v1` 下。已儲存的圖片永遠不會被自動刪除，相同圖片只會儲存一份，之後收緊限制也絕不會讓已儲存的圖片不可讀。如果你的圖片需要能從另一臺機器讀取，本包並不合適。

### 附加圖片時會發生什麼

附加圖片後，會先檢查源圖限制、媒體型別、尺寸與畫素，再完成規範化並儲存。系統應用 EXIF 方向、移除中繼資料與色彩設定、保留透明度，並按總畫素預算與長邊上限縮小光柵。帶 alpha 的圖片使用 WebP，不透明圖片使用 JPEG，共享 85/75/60 品質階梯；全部候選都超過位元組目標時保留最小輸出。被接受的圖片會重新出現在歷史和後續輪次中，重新啟動後也不例外；所選模型路由會收到快取的請求版本，並在其檔案系統可對映主機物件時收到只讀執行世界路徑。

### 可能出什麼問題

附加圖片時可能被拒絕：格式不受支援、超出位元組、畫素或單邊尺寸限制，或者位元組與宣告型別不符。之後讀取時，磁碟上被刪除或損壞的圖片會以明確錯誤失敗。每個失敗都帶有穩定錯誤碼，用戶端與協定介面卡可以用自己的措辭解釋。

<a id="understand-the-implementation"></a>
## 理解實作

<details>
<summary>實作細節——點選展開</summary>

本節解釋儲存背後的永續性與驗證設計，以及實作它的寫入與讀取路徑；可觀察行為已在[使用本包](#use-this-package)中完整說明。

### 設計決策

- **永續性靠 fsync 鏈，而非存在性。** 當目錄項從未到達儲存時，僅同步檔案無法在崩潰後存活，因此寫入路徑會在引用可能到達工作階段檢查點前，把每個祖先條目同步到程序已驗證的邊界。
- **一次規範化，按路由投影。** 准入持久儲存一份提供者無關的規範化附件；請求投影派生確定性變體而不改寫持久歷史。
- **惰性 alpha 路由編碼。** 帶 alpha 的圖片使用 WebP，不透明圖片使用 JPEG；品質候選按 85/75/60 順序執行，沒有候選滿足編碼位元組目標時保留最小輸出。
- **限制是寫入時策略。** 位元組、總畫素與單邊尺寸限制只約束准入，因此之後收緊它們絕不會讓已接納的歷史不可讀。

### 寫入與讀取路徑

物件存放在 `<DSH_HOME>/attachments/v1/objects/<sha256-prefix>/<sha256>`；相同位元組會去重為同一個物件和同一個 `sha256:` 識別符號。首次寫入前，程序會把 home 的每個祖先目錄逐級同步到檔案系統根目錄，因此絕不會把另一個程序已建立但尚未同步的目錄誤認為安全邊界。隨後，寫入過程把位元組暫存到 `v1/tmp`、同步臨時檔案、以原子且排他的硬連結釋出，並同步釋出目錄——在 Windows 上，檔案系統中繼資料日誌負責目錄項永續性。儲存操作完成後，返回的引用已具備永續性。

准入允許每條訊息最多 20 張圖片與 200 MiB 源位元組；單個源圖最多 20 MiB、6400 萬畫素與單邊 8192 畫素。系統應用方向、移除中繼資料與色彩設定，並把規範化結果限制在 2048×2048 總畫素預算、8192 畫素長邊和 4 MiB 編碼位元組目標內，因此，即使寬高比極端，圖片也會保留短邊解析度。已經滿足限制的乾淨、單幀、8-bit sRGB/sRGBA PNG、JPEG 或 WebP 會逐位元組直通；GIF、動畫、中繼資料、方向、16-bit PNG 與不相容色彩空間會觸發轉換。

請求版本位於由 `dshCachePath` 解析的 `<DSH_HOME>/cache/attachments/request-images/`；顯式 `dshHome` 設定同時適用於快取與持久儲存。在兩次請求之間清空此快取會保留持久附件，後續讀取會重新生成請求版本。`readImageRequest` 在不放大的前提下縮放到路由選定的目標尺寸，縮放只按長邊給定，短邊由編碼器按路由預測的方式推出，隨後透過相同的 alpha 路由與品質階梯應用獨立編碼位元組目標。快取身份包含附件 id、變換版本、目標尺寸、位元組目標與固定編碼參數；快取位元組會先透過檔案頭探測格式、8-bit sRGB/sRGBA、尺寸與 alpha 資訊，不匹配時重新生成。並行呼叫方共享一次變換與快取寫入，且只在沒有等待方時由取消停止共享工作。`imageHostPath` 派生規範化物件的主機路徑，掛載的檔案系統可以把該路徑對映進執行世界，而不會寫入持久歷史。

通用檔案位元組的唯一規範物件位於 `<DSH_HOME>/attachments/v1/file-objects/<digest-prefix>/<digest>`。每條引用路徑 `<DSH_HOME>/attachments/v1/files/<digest-prefix>/<digest>/<name>` 都是隻讀硬連結，所以名稱不同但位元組相同的檔案不會重複佔用磁碟。`readFileStream` 以有界分塊讀取引用路徑，並在消費方成功結束前驗證完整摘要與記錄的位元組數。物件缺失、被改寫或截斷時，消費方會失敗，不會得到位元組已經變化的完整匯出。

<a id="model-experience"></a>
## 模型體驗

本包透過請求描述符間接影響模型。執行檔案系統可以對映主機物件時，模型會隨請求位元組看到每張圖片的身份、尺寸、媒體型別、只讀程序路徑、可寫副本副檔名與規範化警告。通用檔案會投影為指出檔案身份與只讀程序路徑的文字控制代碼；無法對映時，控制代碼會說明目前執行環境不能讀取該檔案。

#### KV Cache 影響

規範化和請求投影都是確定性的。附件和路由策略不變時，之後各輪會複用相同的快取請求位元組；執行世界路徑對映可以改變描述符文字，而不會改變這些位元組或其 `variantId`。

## 已知限制與延期工作

<a id="known-limitations-and-deferred-work"></a>


這些限制描述了這份儲存能做什麼、不能做什麼；它們是目前包約束。

- **圖片會永久保留**——已儲存的圖片永遠不會被自動刪除，也沒有任何機制回收未被引用的物件。
- **僅限本機**——圖片存放在執行 harness 的機器上；其他主機無法讀取。
- **動態 GIF 變為靜態**——規範化只保留第一幀；動畫不屬於第一版圖片約定。
- **編碼器輸出帶版本**——已安裝的 Sharp/libvips 建置會固定規範化結果與請求位元組；編碼器或變換版本升級會讓未來變體產生新地址，已有物件繼續有效。
