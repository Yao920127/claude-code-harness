# @deepseek-ai/dsh-attachment

[English](README.md) | 中文

## 概述

把圖片與通用檔案附加到提示詞和命令中，同一工作階段重新啟動後仍可複用；隨附的 `dsh` 組合無需額外設定。圖片會在訊息被接受前完成驗證與規範化；部署限額內支援 PNG、JPEG、WebP 和 GIF。其他檔案按位元組原樣儲存，不設格式與大小限制；模型透過儲存的只讀路徑按需讀取，而不接收檔案位元組。持久工作階段事件不包含瀏覽器路徑、提供者 URL、本地儲存路徑和 base64。已儲存附件不會被自動刪除；音訊和影片暫無專門處理。

<a id="use-this-package"></a>
## 使用本包

圖片附件端到端可用：把圖片附加到提示詞或命令，它會自動儲存、顯示在歷史中併傳送給模型，無需你再做任何操作。在預設 `dsh` 組合中一切都已接好；自行組合時，一個外掛即可啟用該能力。

### 在提示詞中附加圖片

在用戶端 UI 中向使用者提示詞附加一張或多張圖片。每個源圖都會在你的訊息被處理前接受檢查、規範化為提供者無關的 8-bit sRGB/sRGBA 光柵並儲存；如果任何一張圖片被拒絕，整條訊息都會失敗且不會發布任何內容。支援的源格式為 PNG、JPEG、WebP 與 GIF；部署方分別控制源圖限制、規範化儲存限制與路由專用請求限制。下面這一個外掛即可啟用持久圖片附件（隨附的 base 組合已經掛載它）：

```yaml
- name: '@deepseek-ai/dsh-attachment-local'
```

### 在提示詞中附加任意其他檔案

任何非圖片檔案都以通用檔案的形式附加到提示詞：確切位元組被只讀儲存在 harness 主目錄下，訊息記錄檔名、位元組數與內容摘要，模型收到一行指出儲存路徑的文字，只在需要時用檔案工具讀取內容。沒有檔案型別白名單，也沒有大小上限；你附加什麼就原樣存什麼。

### 把附件傳給命令

宣告接受附件的命令會按選擇順序接收圖片與通用檔案。不接受附件的命令會返回錯誤，並保留輸入區的草稿與附件卡。

### 在整個工作階段中複用圖片

已儲存的規範化圖片會保留在對話歷史中，並在後續輪次投影為確定性的路由尺寸請求版本；重新啟動後，恢復的工作階段會顯示並複用相同的圖片。目前執行檔案系統可以對映已存主機物件時，請求描述符還會攜帶模型可檢查的只讀程序路徑。回讀歷史或請求版本時，已儲存的位元組會與記錄的內容比對，因此缺失、損壞或被替換的圖片會以錯誤形式呈現，而不是錯誤的位元組。

### 可能出什麼問題

附加圖片時可能被拒絕——格式不受支援、超出大小、畫素或尺寸限制，或者位元組與宣告型別不符——此時整條訊息失敗。之後，如果磁碟上的圖片被刪除或損壞，歷史讀取也可能失敗。失敗帶有穩定錯誤碼，用戶端與協定介面卡可以用自己的措辭解釋它們。

<a id="understand-the-implementation"></a>
## 理解實作

<details>
<summary>實作細節——點選展開</summary>

本節解釋 seam 背後的設計決策，以及實作使用者可見行為的服務操作；可觀察行為已在[使用本包](#use-this-package)中完整說明。

### 設計決策

- **事件前完成規範化與持久化。** 每個源圖都會在批次按序釋出前完成準備與驗證，因此工作階段日誌絕不會引用部分完成或規範化失敗的物件。
- **不可變且保留策略中立。** 物件一經發布即不可變；恢復和 fork 後的工作階段可能共享它們，因此引用感知的垃圾回收被推遲，而不是與任何單個工作階段的刪除繫結。
- **讀取時驗證。** 讀取在返回前把位元組和中繼資料與記錄的引用比對，請求投影還會完整解碼快取位元組，因此缺失、損壞或被替換的物件不會透過驗證。
- **角色無關的圖片塊。** `dsh-llm` 中的 `ImageBlock` 內容塊攜帶 `ImageAttachmentRef`；提供者介面卡按路由顯式選定的目標尺寸與位元組目標把引用解析為確定性請求版本，執行檔案系統則可以把不可變主機物件對映為模型可讀的程序路徑。
- **按錯誤碼路由。** `AttachmentError` 重新實作 `HarnessError` 的結構而不是繼承它，因為基類位於 `dsh-llm`，而後者依賴本包；消費方用 `isAttachmentError` 識別錯誤並按 `code` 路由，絕不依賴原型鏈。
- **檔案原樣，圖片規範化。**`saveFile` 提交已有位元組陣列，`saveFileStream` 以背壓和取消語義提交有界分塊，`readFileStream` 驗證並返回有界分塊，`fileHostPath` 定位儲存物件供按需讀取投影；兩種檔案寫入路徑都不設准入限制。圖片路徑保留其獨立的規範化、限額與請求版本流水線。`dsh-llm` 中的 `FileBlock` 內容塊承載 `FileAttachmentRef`，請求組裝會為每條路由將其投影為確定性的控制代碼文字。

### 服務操作

服務族執行同一條准入與儲存流程：每個入口都強制執行源批次限制與規範 base64，在釋出任何成員前準備提供者無關的規範化附件，再按輸入順序持久提交而不產生部分結果。Host 提示詞消費方把有序文字、編碼圖片和已經解析的檔案引用交給 `ctx.attachments.admitPromptContent()`；該方法持久化圖片，並讓檔案引用原樣透過。編碼協定介面卡呼叫 `ctx.attachments.admitEncodedFile()`，由該方法檢查規範 base64 後委託給 `saveFile`；介面卡透過 `ctx.attachments.isAttachmentError()` 識別附件錯誤。通用檔案呼叫方可以用 `saveFile` 提交已有位元組，或用 `saveFileStream` 提交有界非同步位元組源；兩者返回相同的持久引用，`readFileStream` 則在有界讀取過程中驗證摘要與長度。`readImageRequest` 派生確定性的路由尺寸變體，其身份包含附件 id、變換版本、目標尺寸、位元組目標及編碼參數。純函式匯出 `requestImageDimensions` 與 `longEdgeDimensions` 按總畫素預算或精確長邊計算保持寬高比的尺寸，使路由與請求定價共享同一套幾何計算。`imageHostPath` 只向需要把該位置對映到執行環境的受信任同程序消費方暴露實作擁有的主機位置。呼叫方組合有序批次，而實作負責管理壓縮並行、快取與 singleflight。讀取、流式寫入和投影保留呼叫方的取消語義。失敗帶有穩定且機器可讀的錯誤碼，執行時即可識別可由呼叫方修正的准入子集，讓每個協定介面卡對映自己的詞彙；各操作的確切約定見 [`src/index.ts`](src/index.ts) 與 [`src/error.ts`](src/error.ts)。

<a id="model-experience"></a>
## 模型體驗

該包透過提供者介面卡間接影響模型；介面卡會把每個持久圖片引用解析為確切請求版本，並在圖片旁傳送穩定附件 id 與實際尺寸。執行檔案系統可以對映已存物件時，描述符還會包含只讀程序路徑，以及可寫副本使用的匹配副檔名。通用檔案的位元組永遠不會到達提供者：每條路由都收到一行確定性的控制代碼文字，指出檔名、位元組數、摘要字首，以及供檔案工具讀取的只讀儲存路徑。

#### KV Cache 影響

新增圖片會改變提供者請求，因此會使受影響的請求字尾失效。

## 已知限制與延期工作

<a id="known-limitations-and-deferred-work"></a>


這些限制描述了附件能做什麼、不能做什麼；它們是目前包約束，而非任務積壓。

- **光柵圖片限制只作用於圖片**——圖片接受部署限額內的 PNG、JPEG、WebP 與 GIF；其他任何檔案都原樣儲存、不設型別與大小限制，音訊和影片暫無專門處理。
- **附件永遠不會被刪除**——已儲存的圖片與檔案無限期保留；沒有任何機制自動移除它們。
- **未傳送的草稿不會儲存**——輸入區草稿在提交訊息前一直留在瀏覽器中。

#### 未來：引用感知的垃圾回收

恢復和 fork 後的工作階段可能共享不可變物件，因此任何保留策略都需要一個能考慮工作階段血緣的引用模型，之後才能回收物件。目前尚未記錄任何決定；本地後端目前保留一切。

#### 未來：音訊、影片與助手側輸出

音訊與影片需要原樣檔案路徑之外的專門生命週期與提供者約定；角色無關的 `ImageBlock` 也為助手側圖片輸出保留向前相容空間——目前生產介面卡宣告只輸出文字，因此只有使用者內容攜帶圖片。兩個方向都尚未決定。
